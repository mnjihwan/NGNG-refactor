# RF-040: 서버 토큰 폐기·회전 및 역할/탈퇴 상태 최신화

## 2026-11-26 A단계 구현 및 검증 결과

**백엔드 A단계 구현과 선택 회귀 완료. 기존 결합 상태의 P2 보완 및 공유 증빙 독립 검토를 마쳤다. RF-040 단독 후보의 별도 최종 독립 리뷰도 통과했다.** 기준 커밋은 `be5c615`다. 미커밋 RF-040·RF-043의 결합 실행과 RF-040 단독 후보 실행을 아래에 구분한다. 11월 11일 항목은 분석·착수 당시의 이력이다.

`SecurityConfig`는 `TokenFilter`에 기존 `UserRepository`를 전달한다. 필터는 RF-005의 JWT 검증과 access/refresh 선택 규칙을 적용한 뒤, 선택된 JWT의 이메일로 현재 사용자 한 명을 조회한다. 사용자 존재·ID·`visible=true`·`ADMIN`/`USER`/`UNCONFIRMED_USER` 역할이 확인되면 현재 DB 역할을 인증 권한과 refresh로 발급하는 access에 적용한다. 기존 이메일 기반 principal을 유지하고 업무 서비스는 기존 방식대로 사용자 ID를 조회한다.

- 사용자 없음, ID 없음, 비활성 또는 `visible=null`, 유효 역할 없음은 빈 401로 응답한다. 해당 경로에서 추가 토큰 발급과 업무 처리를 중단한다. 유효 access가 계정 상태 검사에서 거부되면 함께 보낸 refresh는 사용되지 않는다.
- 액세스 누락·빈 헤더·유효한 서명과 claim을 가진 만료 access에서만 기존 refresh fallback이 가능하다. 무효 credential과 RF-005의 공개 skip/CORS preflight/logout에는 새 사용자 조회가 발생하지 않는다. 유효 refresh로 인증이 성립한 뒤 endpoint가 403을 반환하는 경우의 access 응답 헤더도 기존과 같다.
- 저장소 연결·쿼리·단건성 오류는 JWT 처리의 catch 밖에서 전파된다. 격리 체인에서 인증 조회 예외와 그 뒤 업무 조회의 예외 원인이 구분됨을 검증했다. 유효한 JWT를 사용하는 필터 경로는 사용자 조회가 1회 추가되고 업무 조회는 기존대로 수행된다.
- RF-042의 동일 토큰을 사용한 두 번째 탈퇴 요청은 첫 204 후 비활성 상태가 반영되어 401이 된다. 주소·계좌·탈퇴의 사용자 없음/ID 없음도 업무 전에 401로 처리한다. RF-043의 회원가입 경로는 기존 공개 skip을 따르며, RF-016 공용 smoke는 인증 전 사용자 조회와 업무 조회의 순서 및 principal 형식까지 단언한다.

Windows PowerShell·JDK 17·기존 Gradle 8.7 캐시에서 리뷰 전 오프라인 선택 테스트 21개 클래스 **1,221건 통과**, RF-043 결합 선택 테스트 2개 클래스 **37건 통과**를 확인했다. 최초 재개 실행에서 `compileJava`, `compileTestJava`, `bootJar`, `jar`, `assemble`이 실행되었고 이후 테스트 컴파일과 패키징을 다시 확인했다. 리뷰 보완에서 바뀐 테스트 클래스 3개를 별도로 컴파일·재실행해 **407건 통과**를 확인했다. 각 통과 실행의 실패·오류·skip은 모두 0이며 재실행 건수는 합산하지 않는다. 명령·XML과 콘솔·원본 보존 경로·소스 캡처·SHA-256은 [검증 증빙](../evidence/RF-040/README.md)에 있다.

리뷰 보완은 다음 테스트 경계를 확인한다.

- 결제 계정 조회는 필터에서 성공한 뒤 업무에서 사용자 없음·ID 없음 또는 저장소 장애가 발생하는 두 단계로 구성했다. 업무의 401 또는 `ServletException`의 원인과 상품·거래·잔액 조회 및 쓰기 미발생을 확인했다.
- 주소 변경에서 DB의 `ADMIN`·`USER`·`UNCONFIRMED_USER` 각각에 대해 본인과 타인, refresh를 확인했다. 비등록 JWT 역할은 현재 DB의 `USER`로 확인하는 별도 입력 행으로 구분했다. 본인 주소만 바뀌거나 거부로 기존 주소가 보존되며, 계좌·역할과 대상 계정 상태는 유지된다. 발급 access의 역할은 DB 역할과 일치한다.
- 실제 `JwtTokenProvider`가 합성 계정으로 발급한 두 토큰을 로그아웃 전·후에 그대로 사용했다. 로그아웃은 204와 삭제용 쿠키를 반환하고, 같은 access는 뒤에도 인증되며 같은 refresh도 새 access를 발급받는다. 이 검증은 격리 체인의 세션 회수 한계를 확인한다.

## 재개 후 공통 리뷰 반영 — A안의 최소 범위와 우선 한계

**A안은 현재 계정 상태·role 확인만 다루며 logout 회수/계정 세대 구별/기존 WebSocket 회수를 해결하지 않는다.** JWT sub는 email뿐이다. 사용자가 삭제되거나 email을 바꾸고 동일 email로 다른 계정이 생성되면, 옛 토큰이 새 계정으로 조회될 수 있다. DB ID가 존재한다는 검사만으로 발급 당시 계정과 동일함을 증명할 수 없다. RF043의 이메일 인증·재가입 증명도 옛 JWT의 발급 계정 결합을 자동 해결하지 않으므로 email 재사용 정책과 함께 추적한다. 불변 사용자 ID/계정 세대를 sub 또는 별도 claim으로 전환하는 것은 별도 보류이며 A안에 몰래 추가하지 않는다.

visible=null은 활성으로 취급하지 않고 거부한다. 그러나 visible=false 후 true로 재활성화하면 만료 전 옛 토큰이 다시 통과할 수 있다. A안은 이전 토큰을 영구 폐기하지 않는다. chat의 CONNECT 이후 기존 구독/idle socket 수신은 HTTP 요청마다 DB를 확인해도 해결되지 않는다. session ledger/schema 신설, 전체 기기 logout, chat 기존 WS의 추가 상태 검사/전파, 발급 subject 전환은 별도 정책·착수 범위로 보류한다.

공통 리뷰에서 구체화한 backend A안 처리 순서는 다음과 같다.

1. RF005 credential 형식·서명·type·claim·만료 분기를 먼저 유지한다. 무효 credential로 DB를 조회하거나 refresh로 우회하지 않는다.
2. 선택된 유효 access 또는 유효 refresh의 email로 현재 DB 계정이 유일하게 해석되는지 확인하고, 사용자 존재·ID nonnull·`Boolean.TRUE.equals(visible)`·유효한 현재 role을 요구한다. 유효 role은 기존 ADMIN/USER/UNCONFIRMED_USER 권한표에 맞는 값이며 새로운 역할/특권은 추가하지 않는다. 중복 email 등 단건성 위반은 인증을 진행하지 않고 데이터 오류로 구분한다.
3. access 인증 authority와 refresh로 생성하는 access의 role 모두 **DB 현재 role**을 사용한다. 유효 access의 상태 조회가 거부되면 refresh cookie가 유효하더라도 fallback하지 않는다. 누락/빈/서명 유효 만료 access만 기존 refresh 경로에 진입한다.
4. 사용자 없음/비활성/유효 role 부재 같은 명시 상태 거부는 업무 호출·새 토큰 발급 없이 인증 실패로 처리하는 계획이다. DB 연결/쿼리/단건성 오류를 credential401 catch로 삼키지 않는다. DB 장애 시 인증·업무는 진행하지 않되 장애 응답/관측은 인증 실패와 분리하며 실제 체인 회귀에서 확인한다.

이 최소 권고의 근거는 [OWASP Authorization의 매 요청 권한 검증·기본 거부](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)와 [OWASP REST Security의 JWT 상태 불일치 설명](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#jwt)이다(재개 후 열람). 공개 지침 자체가 사용자 승인은 아니다. 통합 담당이 전달한 사용자 사전 위임은 **근거 있는 최소 보안 판단**이며, 이미 DB에 반영된 비활성/role를 backend 인증 판단에 반영하는 A안은 그 범위의 권고로 구체화한다. 이는 새 사업 역할/탈퇴 복구 규칙/모든 세션 폐기를 정할 권한까지 위임받았다는 뜻이 아니다. 이번 담당 작업은 두 문서 보완이며 구현 승인·실행 완료를 주장하지 않는다.

DB 조회 증가에 따른 부하/지연·가용성 영향은 미측정이다. replica 지연·트랜잭션 snapshot·OSIV/영속성 컨텍스트에 의한 stale read와 권한 변경 commit 후 진행 중 요청의 경쟁은 미증명이다. 따라서 “매 요청 재조회”를 운영상 즉시 최신성이나 성능 개선으로 표현하지 않는다.

|---|---|---|
| A. 인증 시 현재 DB 사용자·visible·role 재조회 | backend 다음 인증 판단에서 비활성 거부/DB role 적용. refresh도 현재 상태를 확인해야 과거 role의 재발급 방지. logout별 세션 회수·재사용 탐지는 해결하지 못함. 검증 뒤 진행 중 업무와 탈퇴 commit 사이 경쟁도 남음 | 기존 repository/컬럼으로 backend 최소 구현 가능, 새 의존성/schema 불필요. chat visible 검사는 기존 필드 가능하나 DB role 활용은 매핑/조회 설계 필요. identity 중복/누락/null·장애는 거부 권고, 정상 인증/업무 실패를 일괄401로 숨기지 않음 |
| B. access 짧은 수명 + refresh에서만 상태 확인 | access 잔여 수명 동안 옛 권한 허용. refresh 수명/정책·chat 재연결 UX와 함께 정해야 함. 짧게만 바꾸면 현재 옛 role 재발급은 지속 | 설정·클라이언트 변화, 새 저장소 필수 아님. 허용 노출시간·가용성 결정 필요, 즉시 회수라고 표시 금지 |
| C. 세션/토큰 family ledger + refresh 회전 + 매 인증 회수 확인 | 세션별 logout, refresh 재사용 탐지, 전체 세션 철회 설계 가능. access도 sid/version 확인해야 즉시 회수 가능. refresh-only 회수는 기존 access를 무효화하지 않음 | 공유 내구 저장·원자적 소비/회전·고유 식별자·만료 정리·중복 재요청 정책 필요. 신규 테이블/컬럼은 별도 승인. 기존 Redis가 있다는 이유로 보안 ledger 용도/유실/eviction/복구 정책을 승인된 것으로 보지 않음 |

권고는 **A의 현재 계정 상태 검증을 첫 구현 단위로 분리**하고 C/D 중 세션 정책을 정한 뒤 회수·회전을 추가하는 것이다. A만으로 RF040 전체 완료를 선언하지 않는다. 캐시 없는 조회는 조회 부하/장애 의존을 늘릴 수 있으며 성능 개선을 주장하지 않는다. 캐시를 넣으면 TTL·stale read·무효화 실패의 허용 창이 추가되므로 먼저 최신성 계약을 정한다. DB replica/transaction snapshot/OSIV 1차 캐시가 stale 값을 주면 단순 find 호출만으로 최신성 보장도 성립하지 않는다.

공식 설계 근거(2026-11-11 열람): [RFC9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)는 refresh 회전과 관계 보존을 통한 재사용 탐지·보안 이벤트 폐기를 설명한다. [RFC7009 §2](https://www.rfc-editor.org/rfc/rfc7009.html#section-2)는 회수와 관련 토큰의 범위·전파를 다룬다. 이는 이 서비스가 OAuth 구현이라는 판정이나 새로운 endpoint 도입 요구가 아니라 설계 참고다. [OWASP JWT](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)는 명시 회수와 서명/식별자 경계를 다룬다. 원문 JWT/단순 byte hash denylist를 유일 식별자로 선택하지 말고 검증된 issuer+jti/sid 등과 변형 입력의 동일성까지 설계한다.

## 사전 위임으로 처리 가능한 판단과 별도 결정

사용자가 근거 있는 최소 안전 정책 선택을 사전 위임한 범위는 반복 승인을 요구하지 않는다. 구현 순서·기존 parser/상태코드 회귀·대역/결정적 clock·새 의존성 없는 repository 경계·명백한 무효 상태의 거부 권고는 담당자가 근거와 영향으로 구체화할 수 있다. **이번 요청은 분석/계획이므로 구현 착수까지 확장하지 않는다.**

사업/운영 정보 없이는 결정할 수 없는 항목은 다음과 같다. 이 항목을 포괄적 승인 질문으로 재포장하지 말고 실행 전 필요한 선택과 결과만 제시한다.

- logout은 현재 세션/기기만인가 전체 기기인가, 탈퇴·강등·비밀번호 변경 후 기존 세션은 언제까지 허용하는가. 재활성화 시 옛 토큰을 다시 살릴 것인가(권고: 살리지 않음). RF042 반복 toggle와 UI 복구 절차의 호환성.
- 회수 저장소의 소유·내구성·장애 시 인증 차단·복구/백업 restore·replica 읽기·허용 전파시간, 신규 schema/의존성/키 체계 변경 승인. 회수 자료가 유실되면 기존 세션을 무효화해야 하는지 운영 결정 필요.
- refresh 동시 요청/응답 유실·정상 재시도의 처리. 무조건 family 철회는 여러 탭/병렬 요청을 공격 재사용으로 오인할 수 있고 grace 허용은 replay 창을 만든다. 단일 소비 winner·후속 응답 및 재로그인 UX를 합의한다.
- 이미 인증·진행 중인 HTTP 쓰기를 철회할지, chat 기존 구독/idle socket을 언제 닫을지. 즉시 전송 중단은 backend만 수정하거나 CONNECT만 확인해서 달성되지 않는다. 각 chat 인스턴스의 inbound/outbound/transport와 전달 지연/이벤트 유실·재접속을 포함한다.
- HMAC 공유는 chat에도 발급 능력을 준다(RF022 기승인 범위). 운영 key 공급/회전 동기화는 미검증. 비대칭/JWKS·introspection 전환은 대규모 별도 설계이며 이번 기본안이 아니다.

## API·CSRF·클라이언트 호환 경계

RF005의 정상 access 우선, 허용 fallback, 정확 Bearer/type/필수 claim, 빈401 및 기존403, public/skip 구분을 유지한다. 상태 거부와 인가 거부·저장소 장애 응답은 새 계약표로 분리해야 한다. `/logout` 성공204·cookie 삭제를 유지하려면 서버 회수 실패를 성공으로 숨길지 여부도 구체적으로 정해야 하며 원격 세션 폐기 성공으로 오인시키지 않는다.

현재 CSRF 비활성, credential 허용 wildcard origin pattern, refresh cookie의 SameSite 미명시/domain localhost·Secure를 정적으로 확인했다. cookie만으로 인증을 재발급하며 같은 업무 요청을 실행하므로 stateless JWT라는 이유로 CSRF가 없다고 판단하지 않는다. [Spring logout 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/logout.html)는 LogoutFilter가 인가 필터보다 앞서고 CSRF 설정에 따라 logout 처리 방식이 달라짐을 설명한다. 열람 페이지는 현재판이므로 프로젝트 Spring Security 버전의 실제 chain으로 method/순서를 검증해야 한다. CSRF/CORS·cookie domain/SameSite 변경을 무단 적용하지 않고 R5 정책 잔여와 연결한다.

새 logout 인증을 추가할 때 현재 MyInfo의 헤더 없음/로컬 삭제 선행 및 AdminMenu의 서버 호출 없음과 호환을 확인한다. RF030 소유의 명시 logout API·응답 실패·roleToken/SWR 정리, 세션 세대별 늦은 refresh 응답 무시, 다중 탭/팝업을 공동 계약으로 정의하되 이번에 구현하지 않는다. 구 access/refresh에 새 sid/epoch가 없을 때 강제 재로그인/한시 수용 중 선택, 구버전 서버 혼재 금지 여부와 롤백 시 회수 목록 유지도 릴리스 조건이다.

## 단계별 검증과 완료 조건

1. **변경 전 대역 특성**: 실제 provider/verifier·합성 키·제어 clock·repository 대역으로 로그인 발급→logout→복사 access/refresh, active→inactive, ADMIN→USER, UNCONFIRMED→USER→옛 refresh, 사용자 삭제·중복 email·nullable visible을 기록. 기존 기준선 결과를 새 실행 없이 통과로 옮기지 않는다.
2. **최소 상태 구현 후 격리**: RF005 실제 필터체인 + RF020/041/042 객체 인가 회귀. 정상 access/refresh·401/403·skip·업무 호출0·새 토큰 없음, backend DB 현재 role 반영, 비활성 탈퇴 후 반복 요청 계약, login/confirm 발급과 rollback 전 토큰 노출 여부를 검사. 저장소 장애를 업무 예외와 분리한다.
3. **회수/회전 대역**: 선택한 sid/family/epoch 모델에 한해 두 독립 context·공유 원자 대역으로 동일 refresh 동시 소비, logout↔refresh, 회수↔발급, 두 기기, 늦은 응답·응답 유실·중복 logout·새 로그인, TTL 경계·시계차·장애/재시작·restore를 검증. 원시 JWT 로그 금지, 대역의 원자성을 실제 저장소 보장으로 확대하지 않는다.
4. **chat/프런트 격리**: REST/CONNECT 재검증, 이미 연결된 SEND/SUBSCRIBE·기존 구독 outbound·idle transport·queued frame에 회수/탈퇴가 미치는 경계, 익명 공개구독 유지, 악성 credential을 익명으로 낮추지 않음을 확인. RF022 exp/참여자 회귀, MyInfo/AdminMenu·서버 실패·다중 탭/팝업 미지원·logout 뒤 늦은 refresh 재저장을 재현한다.
5. **물리 통합 별도 재개**: RF016 승인된 격리 신원/fixture·외부차단·정확 소유행/key cleanup과 실행 허용 범위를 확보한 뒤 DB current read/commit/rollback·ledger CAS/replica·재시작/장애, 두 backend/two chat 인스턴스, 실제 HTTP/WebSocket·브라우저 cookie/rewrite/CSRF·동시 refresh를 검증. 운영자료가 필요한 key/회전·구클라이언트·혼합버전·롤백은 안전한 검증 환경과 릴리스 정책 후 실행.

후속 명령은 기존 선택 suite 이름을 확인하여 `gradlew.bat --offline --no-daemon test --tests <선택클래스>`와 assemble, frontend `node --test <선택파일>`/tsc/lint로 구성한다. 이번에는 명령을 실행하지 않았으며 미래 존재할 테스트 이름을 확정 명령처럼 기록하지 않는다. 전체 test/build·성능은 자동 확대하지 않는다.

계획 완료 조건은 근거·선택지·결정 경계·단계별 검증/증빙/잔여 추적의 작성 및 독립 문서 리뷰다. 기능 완료 조건은 선택된 보장(대상 세션/허용 지연/실시간 경계)을 명시하고 실패·경쟁 회귀와 실제 저장소 검증을 그 주장 범위에 맞게 확보하는 것이다. 미검증 운영 보장을 완료로 바꾸지 않는다. 롤백은 이 작업 소유 변경만 선택 복구하며 기존 사용자/.tmp/타 RF 변경을 보존한다. 실제 회수 정책 도입 후에는 코드 롤백으로 회수 토큰을 부활시키지 않는 별도 절차가 필요하다.
