## 2026-11-26 독립 리뷰 P2 보완 및 최신 결합 검증

- Redis와 메모리 대역의 채널 사전 검증은 저장된 코드·증명 만료 시각에 `min(현재 시각 + 5분, 가입 시도 종료 시각)` 상한을 적용한다. Lua는 발급 및 검증 전환과 같은 `TIME` 값 및 5분 상수를 사용한다. 상한을 넘는 손상 상태는 503으로 처리하며 quota·채널·증명·가입 쓰기 전에 중단한다. 이미 지난 만료는 기존 단계별 규칙대로 처리한다. 확인 후 생성된 proof는 기존 code가 만료된 뒤에도 자체 만료와 attempt 종료 전까지 유효하다. 새 발급 시각 필드를 추가하지 않았으므로, 조작된 시각이 현재부터 5분 이내라면 최초 발급 시각 기준의 위조까지 판정할 수 없다.
- 이메일 발급 요청에서 서버가 대상을 고정했을 가능성을 요청 시작부터 기억한다. 발송 503, 응답 유실, 형식이 잘못된 성공 응답은 기존처럼 이메일 증명과 challenge를 지우고 전화 증명과 가입 시도를 유지한다. 같은 이메일은 그 시도 안에서 재발급할 수 있지만, 이메일을 변경하면 시도와 양쪽 증명을 폐기하고 전화 인증부터 새 시도를 시작한다. 최초 발급 전이나 예약 쓰기를 하기 전에 반환한 429 뒤의 이메일 수정은 기존 전화 증명을 유지한다. 이전에 이메일이 고정됐을 가능성이 있으면 이후 429도 그 기록을 지우지 않는다.

RF-040 변경 적용 후 RF-043 [결합 선택 37건](../evidence/RF-040/after/signup-compatibility-console.txt) 및 [RF-016 격리 12건](../evidence/RF-040/README.md#2026-11-26-a단계-구현-결과)이 이미 통과했다. 두 결과를 2026-11-11의 이전 49건과 구분한다. 이번 보완 뒤에는 같은 RF-040 운영 코드로 백엔드 4개 클래스 **52건**(가입 서비스 35, MVC 회원가입 체인 5, RF-016 12)과 백엔드 `assemble`, 프런트 **51건** 및 타입 검사·린트가 통과했다. 실패·오류·건너뜀은 0이다. 백엔드 컴파일과 패키징을 다시 실행했고 린트의 기존 이미지 경고 3건은 유지됐다. 재실행을 합산하지 않는다. [실행 명령·원시 결과·공유 증빙](../evidence/RF-043/README.md#2026-11-26-독립-리뷰-p2-보완).

실제 Redis Lua의 구문·TTL·시계·원자 소비·복제·복원, 실 DB commit/rollback·HTTP/브라우저, SMTP/SMS 전달, 전체 테스트와 성능 검증은 남아 있다. 실행은 메모리 행동대역, Lua 구조 검사, 격리 Spring MVC 및 컴포넌트 대역으로 제한했다. 프런트 전체 배포 빌드도 수행 범위에서 제외했다. 검증을 재개하려면 승인된 격리 Redis/DB·범위가 제한된 fixture와 정리 절차를 확보하고, 실제 TTL·5분 경계와 두 채널 원자 소비, 장애 및 운영 전환을 확인해야 한다. `signup.verification.enabled`의 기본 비활성은 가입 중단을 뜻한다. 증명 없는 구클라이언트는 가입할 수 있으려면 공동 업그레이드가 필요하며 운영 개방 전에 구 writer 차단, epoch·키 동기화, 발송 품질 및 브라우저 전환 검증을 수행해야 한다.

## 범위·유지 조건·정책 결정 (최초 분석 이력)

**아래 대안·미결 설명은 최초 분석 이력이다. 현재 적용 정책은 후속 「사용자 결정 반영 계약」이며 양쪽 필수·기존 Redis·실패 선소비·5분/5회/10분3회는 더 이상 미결이 아니다. DB ledger는 채택하지 않으며 production schema 변경 금지다.**

순수 리팩토링이 아닌 인증 결함 수정 계획이다. 후속 구현 대상은 Join/Auth controller·DTO·service와 필요한 작은 저장/발송 경계, 가입 두 화면 및 합성 테스트다. 기존 비밀번호 encoding, 가입 role, 사용자+초기 포인트 DB 정합성, 정상201/Location·기존 중복400/409를 기본 보존한다. 신규 proof 오류·발송 장애·시도 초과·만료 응답과 authNumber 제거는 명시 계약 변경이며 공동 프런트 릴리스가 필요하다. RF005 공개/skip 정책을 전체 로그인 필수로 바꾸지 않는다.

사용자의 사전 위임 범위에서 CSPRNG 사용, 서버 검증, 대상/목적 결합, 원문 code 응답 제거, 시간·재사용·실패 테스트와 같은 근거 있는 최소 안전 선택은 반복 승인 없이 구체화할 수 있다. **이번 요청은 분석·명세이므로 구현은 하지 않는다.** 다음은 실제 제품/운영 정보가 없어 별도 결정이 필요한 부분이다.

| 결정 | 대안·권고·추가 결정 필요 여부 |
|---|---|
| 필수 채널 | 양쪽 필수 / 이메일만 / 전화만 / 한쪽 선택. 현재 UI와 가장 가까운 권고는 양쪽 필수지만 저장소만으로 사업 의도를 확정할 수 없다. 사용자 제품 결정 필요. 둘 다 필수라면 한쪽 proof만으로 가입 불가. 연락처 확인을 실명·법적 본인확인 또는 MFA 인증 수준으로 표현하지 않는다. |
| 발급·검증 경계 | 기존 공개 send→신규 verify→가입용 opaque proof 권고. 최종 join에서 두 원시 코드를 검증하는 대안은 서버 단순화가 가능하나 현재 단계별 UI 의미가 달라진다. verify 성공이 가입 완료가 아니며 purpose=signup·채널·정확 대상·가입시도 식별자를 결합한다. 새 endpoint/DTO는 구체 계약표 작성 후 적용한다. |
| 유효기간·시도/발송 한도 | 유한 code TTL·proof TTL·시도 수·재전송 cooldown 및 대상/가입시도/네트워크별 발송 제한 권고. 정확 시간·횟수는 전달 지연/고객지원/비용 자료 없이 규범값으로 정하지 않는다. 재전송으로 시도/총량 제한을 초기화하지 않는다. 사용자 운영 수치 결정 필요. |
| 대상 표준화 | 발급/검증/최종가입에 동일 규칙 적용. 전화 하이픈·국가코드, 이메일 공백/대소문자·Unicode를 임의 변경하면 기존 중복/로그인 계약이 달라진다. 허용 입력·canonical 비교·기존 계정 호환을 확정하고 RF032와 연결한다. |
| 저장·복구 | 아래 DB ledger와 기존 Redis 대안 중 선택, 운영 namespace·내구성/유실·복원·TTL·접근권한 및 장애 차단 정책 필요. DB schema와 신규 의존성은 별도 승인. 기존 Redis 존재를 보안 상태 저장 용도 승인으로 해석하지 않는다. |

## 권고 상태 모델과 원자성 대안

서버 생성 CSPRNG challenge ID·가입시도 식별자와 코드 검증 자료, 채널/대상/purpose, expiresAt, 세대, attemptCount, 상태를 보관한다. 클라이언트 Boolean 또는 대상만으로 조회되는 전역 `verified=true`는 다른 가입 요청이 도용할 수 있어 금지한다. verify는 유효 현재 세대/대상/목적과 코드 일치를 원자적으로 확인하고 code를 재사용 불가능하게 전환한 뒤 서버 발급 opaque proof를 제공한다. 최종 join은 해당 시도와 **실제로 저장할 이메일/전화**에 결합된 모든 필수 proof를 확인한다. 다른 시도/채널/목적의 교환·검증 뒤 대상 변경·만료·이미 소비된 proof는 무쓰기 거부한다.

짧은 숫자 코드의 단순 hash는 유출 후 전수 대입을 쉽게 하므로 서버 비밀키를 이용한 검증 자료 등 저장 위협을 함께 검토한다. 고엔트로피 proof도 bearer 비밀로 취급하며 원문 DB/로그/URL/분석 이벤트/오류본문 노출을 피한다. 키 공급·회전은 운영 조건이며 JWT 키를 이유 없이 재활용하지 않는다. 이름·연락처 로그는 RF033과 연계하되 그 전체 범위를 이 작업으로 확대하지 않는다.

| 대안 | 소비와 실패 경계 / 선택 조건 |
|---|---|
| DB 인증 ledger | proof 조건부 소비와 User/초기 PointHistory를 동일 DB transaction에 포함하면 실패 rollback 때 proof도 복원할 수 있다. 두 proof 잠금 순서·조건부 UPDATE affected 수·만료 판정·유일성 필요. 가장 명확한 가입 원자성 권고지만 신규 테이블/인덱스·cleanup/schema 승인이 선행한다. 발송 자체는 DB transaction으로 rollback되지 않는다. |
| 기존 Redis 원자 소비 후 DB join | 두 필수 proof를 하나의 CAS/Lua 등으로 검증·소비한 승자만 DB 저장. GET 후 DEL 두 호출은 경쟁 방어가 아니다. Redis 소비 후 DB 실패/프로세스 종료에서는 proof가 사라져 재인증이 필요하다. **실패에도 소비하는 보수 정책**을 허용할 때 최소 대안이며 성공 시 한 번만 사용을 보장하는 범위와 물리 failover/restore 한계를 명시한다. Redis와 DB에 @Transactional 하나를 붙여 원자적이라고 주장하지 않는다. |
| Redis 예약→DB→확정/보상 | DB 결과가 불명일 때 예약 해제하면 동일 proof가 재사용될 수 있다. 내구 operation ID·결과/복구 ledger 없이는 안전한 자동 복구 불가. 복잡도가 커 기본 최소안으로 권고하지 않는다. |
| 서명 proof만 / 인메모리 Map | 서명과 exp만으로 1회 소비·재사용 방지 불가. 인메모리는 인스턴스/재시작 간 상태 공유가 없어 운영 대안으로 부적합. 단위테스트 대역으로만 사용한다. |

Redis 두 채널 key는 cluster에서 동일 슬롯 등 실제 원자 실행 조건도 확인한다. 복제 지연·failover·백업 restore가 이미 소비한 상태를 되살리는 경우의 무효화 세대/가입중복 보장을 검토한다. RF032 실제 UNIQUE 제약 검증은 별도이며 proof 소비가 중복 가입 문제를 모두 해결하지 않는다. DB 대안 역시 복원 시 proof 재사용·기존 가입행 복원 관계가 운영 재개 조건이다.

발송은 코드 생성·상태 저장·외부 접수 사이에 원자 transaction이 없다. 권고는 비검증 pending 발급 상태를 먼저 기록하고 접수 결과에 따라 사용 가능 전환하며 실패/불명 상태는 인증 가능으로 승격하지 않는 것이다. 전달 성공 뒤 상태 전환 실패, 응답 유실, 동시 재전송·역순 공급자 응답을 테스트하고 구세대 결과가 신세대를 복구하지 않게 한다. 새 발송 실패 시 구세대 유지/즉시 폐기는 계약으로 정한다(권고: 재전송 개시로 구세대 폐기, 실패 시 재발급 안내). 공급자 접수 성공은 verify 성공을 의미하지 않는다. 서버 저장 장애 시 발송/가입을 허용하는 fallback은 두지 않는다.

공식 설계 근거(2026-11-11 조회): [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)는 코드/토큰의 안전한 난수·보관·유한 수명·단일 사용과 남용 방어를 설명한다. 이는 복구 흐름 자료를 가입 채널 소유 증명 설계에 적용하는 추론이며 양쪽 인증 의무나 특정 TTL의 근거가 아니다. [Redis Transactions](https://redis.io/docs/latest/manual/transactions/)는 CAS와 rollback 미지원, [Redis Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)는 스크립트 원자 실행을 설명한다. 이 원자성은 MySQL commit·외부 발송까지 확장되지 않는다.

## 검증 순서·완료 조건

1. **무외부 기준선**: 실제 JoinService+repository/encoder/point 대역으로 proof 없는 요청이 저장 경로에 도달하는 특성 확인. 실제 mail service+메모리 sender로 응답 code=메일 code, SMS는 SDK 생성/네트워크를 분리한 대역으로 status2000/실패/예외 확인. 기존 RF016 테스트가 code 노출을 단언하므로 변경 시 계약 테스트도 갱신한다. 기존 UserControllerTest의 실제 주소 포함 발송 테스트는 실행 금지 상태로 두고 합성 fixture만 쓴다.
2. **서버 상태/계약**: 제어 Clock·CSPRNG 대역·공유 저장 대역으로 정상/미발급/미검증/빈값/잘못된 코드/다른 대상·채널·시도·목적/만료 직전·정각·직후/attempt 한도/재사용을 검증. 거부 시 User·Point 쓰기0, code 원문 응답 및 code/proof 로그 없음. proof는 인증된 verify 최초 성공 응답에만 전달한다. 검증 성공은 proof만 발급, 가입201·Location/role/encoding/초기 포인트 유지. 별도 코드 검증 실패와 저장소 오류를 혼동하지 않는다.
3. **결정적 경쟁·실패**: 같은 code verify 2회, 같은 proof join 2회, 한쪽 유효/한쪽 무효(부분 소비 금지), resend↔verify/join, 역순 응답, 두 context 공유 상태, 발송 직전/직후 장애, DB save·point·commit 실패, 소비/DB commit 뒤 응답유실. 선택한 저장 대안의 rollback 또는 재인증 계약에 맞춰 검증한다. 대역 CAS 통과를 Redis/JPA 물리 보장으로 표시하지 않는다.
4. **프런트**: 서버 verify만 성공 판단, 응답에 code 없음, 연락처 수정/이전 단계/재발급 시 proof 무효화, 늦은 응답 무시, 중복 클릭·빈값·선행0 코드·만료·429/409/5xx·네트워크 오류 복구. 최종 가입은 성공 확인 뒤 이동하며 실패 시 비밀번호/code를 로그로 남기지 않는다. 기존 사용자 로그인·RF005/RF016 선택 회귀 포함.
5. **별도 물리 통합**: RF016 안전 identity/전용 namespace·소유 fixture·외부발송 차단·정확 cleanup 및 실행 허용 후 실제 저장소 TTL/CAS/cluster/rollback/동시성·재시작/복원, 실제 HTTP·rewrite·브라우저 검증. SMTP/SMS 공급자 계약은 승인된 sandbox/수신자만으로 별도 검증하며 실제 고객 발송을 테스트에 사용하지 않는다. provider 성공률·성능은 이번 범위 밖이다.

후속 실행 명령은 새 선택 클래스가 존재한 뒤 `gradlew.bat --offline --no-daemon test --tests <선택클래스>`, assemble 및 프런트 선택 node test/tsc/lint로 확정한다. 현재 테스트를 실행하지 않았고 가상의 테스트 이름/건수를 결과로 기록하지 않는다. 계획 완료는 근거·선택지·결정 경계·검증 계획과 독립 문서 리뷰이며 기능 완료와 다르다. 구현 완료에는 선택한 채널/저장/실패 계약별 회귀·독립 코드 리뷰·합의 범위 증빙이 필요하다. 운영 안전 판정은 물리 검증과 키/남용제한·혼합버전/실제 소비자 릴리스 검증 전에는 불가하다.

구버전 UI는 authNumber 제거 시 동작하지 않고 구버전 backend는 proof 없이 가입할 수 있으므로 서버·UI 공동 전환/구writer 차단을 설계한다. 롤백으로 가입 우회를 다시 열지 않으며 필요하면 가입 일시 중단 후 수정 재개한다. 문서 롤백은 이 작업 소유 두 파일만 선택 처리하고 기존 `.tmp`·다른 RF 변경을 보존한다.

## 사용자 결정 반영 계약 (2026-11-11 후속, 현재 적용)

사용자가 **이메일과 휴대폰 모두 서버 검증 필수**, **기존 Redis에서 증명 선소비 후 DB 실패·결과 불명 시 재인증**, **코드 유효 5분·시도당 확인 5회·동일 대상 발송 10분 최대 3회**를 명시 결정했다. 기존 Redis 용도와 이 사업 제한의 승인은 확보됐다. 신규 의존성·production schema·실발송 승인은 없으며 도입/실행하지 않는다. 이하 세부사항은 위 결정을 구현 가능한 계약으로 구체화한 최소 설계이며 구현·실행 완료 기록이 아니다.

### 발급·비밀 전달 및 시간/횟수

- POST `/join/auth/attempt`는 서버 CSPRNG로 공개 attemptId와 별도의 256비트 attemptSecret을 생성한다. ID만으로 발급·재발급·verify·소비·삭제할 수 없고 모든 변경은 JSON 요청 body의 `attemptSecret` digest를 상수시간 비교하는 경계를 거친다. `X-Signup-Secret` header를 별도 인증원으로 받지 않는 단일 body 계약이며, 최초 header 표현은 구현 검토에서 이 계약으로 구체화했다. 요청자가 ID를 지정하거나 ID 조회만으로 secret을 회수하는 API는 두지 않는다. 가입 시도는 생성 후 절대 30분 만료, 연장하지 않는 최소 설계다. 이 시간은 사용자가 정한 code 5분과 별개다.
- attemptSecret 및 서버 검증 성공 시 반환하는 256비트 opaque proof는 **가입용 bearer 증명**이다. 로그인 access/refresh JWT가 아니며 가입 완료만으로 로그인 JWT를 새 발급하지 않는다. HTTPS 응답 JSON과 요청 JSON body의 `attemptSecret`/proof 필드로 전달, `Cache-Control: no-store` 적용, URL/query·localStorage·sessionStorage·로그·분석 이벤트에 기록하지 않는다. 프런트 상위 가입 컴포넌트 메모리에만 보관하고 완료/이탈/오류에 따라 폐기한다. XSS 방어를 대체하는 조치는 아니다. 프록시/APM도 해당 body를 수집하지 않는 운영 확인이 필요하다.
- 발급 endpoint는 기존 `/join/auth/email`, `/join/auth/phonenumber`를 사용하되 attemptId와 secret을 요구한다. 한 attempt의 채널별 대상은 첫 유효 발급 예약 때 고정한다. 연락처 변경은 새 attempt 시작(두 proof 폐기)으로 처리한다. 모르는 ID 또는 secret 불일치는 상태를 변경하지 않고 일반 오류를 돌려준다. 다른 attempt는 대상 발송 제한에만 영향을 줄 수 있고 기존 attempt 코드/proof를 폐기할 수 없다. 공개 가입 발급에 의한 대상 quota 소진 자체는 남용 잔여이며 IP/서비스 총량 한도는 별도 운영 보완이다.
- 코드 6자리는 JDK SecureRandom으로 생성하며 선행0을 문자열로 보존한다. code TTL은 발급 예약 시각부터 300초, 발송 완료·verify·재전송 응답으로 연장하지 않는다. expiresAt 정각부터 거부한다. Redis TIME을 기준으로 저장 절대시각과 script 내 시간 판정을 함께 사용하고 자동 key TTL은 정리 보조다.
- **확인 5회는 동일 가입 attempt·채널의 실제 코드 비교 횟수**로 정의한다. 성공 비교도 포함하고 다섯 번째가 일치하면 성공, 다섯 번 실패하면 해당 채널은 잠겨 새 attempt가 필요하다. resend로 누적 횟수를 초기화하지 않는다. 잘못된 secret/없는 ID·아직 pending/만료 code는 비교 전에 거부하며 공격자가 남의 횟수를 소모하지 못한다. 두 채널 카운터는 별도다.
- 동일 대상 제한은 채널+canonical 대상별 **직전 600초의 rolling window에 예약 최대3회**다. 새 attempt/재전송/동시 요청을 합산하며 고정 window 경계에서6회 발송되는 구현은 사용하지 않는다. 발송 예약이 승인되면 실패·timeout도 1회로 유지(공급자가 이미 발송했을 수 있음). 제한초과는 외부 sender 호출0. `Retry-After`는 가장 오래된 예약의 만료까지로 반환한다. quota key에는 연락처 원문 대신 전용 HMAC digest를 사용하고 서버 키 유실/미설정은 발급 차단한다.
- 대상 canonical 비교는 이메일 앞뒤 공백 제거+domain 소문자화(로컬부 case 보존), 국내 휴대폰은 하이픈 제거한 숫자열로 제한한다. 이름·nickname·기존 password/role 규칙은 바꾸지 않는다. 발급 시 고정한 검증 대상과 가입에 실제 저장하는 값을 같은 canonical 값으로 맞춘다. 과거 raw 형식 계정과의 중복 조회 호환은 별도 확인해야 하며 새 UNIQUE/schema·기존 데이터 일괄 정규화는 금지한다. RF032의 실제 제약/동시 중복 문제를 해결했다고 주장하지 않는다.

### Redis 상태·검증 성공 유실·원자 소비

Redis에는 attempt secret/proof의 digest, 코드의 전용 키 기반 HMAC(짧은 code 단순 hash 제외), 목적 signup·채널·대상 digest·현재 generation·발급시각/만료·누적 확인횟수·상태만 저장한다. 실제 발송에는 요청 canonical 연락처를 사용하며 proof 레코드가 전화/이메일 주소록이 되지 않게 한다. 코드 digest에는 attempt/channel/generation을 포함한다. HMAC 키는 JWT 키와 분리하고 운영 공급/회전 확인이 필요하다. challengeId는 public 식별자일 뿐 비밀이 아니다.

1. 발급 Lua는 attempt 인증·대상 고정·quota를 **모두 확인한 후** quota 예약과 해당 채널 generation 증가/기존 code·proof 폐기/pending 전환을 원자 처리한다. 거부 시 기존 유효 proof를 폐기하지 않는다. 발송 대역/공급자 결과 후 generation 조건부로 pending→sent만 허용한다. 실패·불명은 usable로 만들지 않고 해당 generation은 폐기한다. 뒤늦은 구세대 접수 결과가 새 세대를 활성화하지 못한다.
2. verify POST `/join/auth/email/verify`, `/join/auth/phonenumber/verify`는 attemptId/challengeId/code와 secret을 받는다. Lua가 현재 sent 세대·목적/대상·5분·확인5회·code HMAC을 검사한다. 성공하면 code를 영구 소비하고 정확 하나의 proof digest로 verified 전환한다. proof 유효기간은 성공시각부터 최대5분이며 attempt 절대 만료를 넘지 않는다. **같은 code를 다시 보내도 proof를 새로 발급하거나 기존 proof를 재노출하지 않는다.** 성공 응답이 유실되면 해당 채널 재발급/재검증이 필요하고 기존 proof는 새 발급 예약 시 폐기한다. quota·누적 확인 한도가 부족하면 제한 만료 또는 새 attempt부터 다시 진행한다. GET proof 복구 endpoint는 없다.
3. 최종 POST `/join`은 기존5필드+attemptId/emailProof/phoneProof 및 secret을 받는다. server는 누락/형식·canonical 대상 일치를 확인하고, **단일 Lua에서 양쪽 proof digest·목적·대상·세대·5분·attempt 상태를 전부 검증한 뒤 양쪽을 한꺼번에 consumed 처리**한다. 하나라도 불일치면 양쪽 모두 미소비, User/Point 쓰기0. 두 동시 join 중 소비 승자만 DB 경로에 진입한다. GET→DEL 또는 채널별 두 script 소비는 사용하지 않는다.
4. 소비 이후에만 기존 DB transaction의 사용자/초기 PointHistory를 실행한다. 중복400, save/point/commit 예외, 프로세스 종료, Redis 소비 응답 timeout(실행 여부 불명), DB commit 뒤 HTTP 응답유실 모두 **proof 복구·자동 재시도 없음, 재인증 필요**다. Redis timeout이면 DB 저장을 시작하지 않는다. DB 결과불명 상태는 이미 계정이 만들어졌을 수 있음을 UI에 안내하고 로그인 또는 새 인증을 선택하게 한다. 재인증이 기존 계정 중복을 무시한다는 뜻은 아니다. 성공201도 실제 transaction commit 뒤 반환되어야 하며 commit 예외를 성공으로 바꾸지 않는다.

quota+attempt 다중 key 및 두 proof의 원자 스크립트는 실제 배포 topology에 맞춰 동일 Redis Cluster hash tag `{signup}`의 전용 namespace를 쓰는 최소안으로 설계한다. 모든 타입/인수·상태 검증을 쓰기 전 수행하고 실패 후 자동 rollback을 가정하지 않는다. 단일 슬롯 집중·용량 영향은 미측정이다. 기존 cache 30분 TTL을 재사용하지 않으며 인증 Redis 오류/자료누락/키 미설정 시 fail closed, 인메모리 fallback 없음. 복제 lag/failover/restore로 consumed가 되살아나는 것은 Lua만으로 방지되지 않는다. **복원·유실·불명 failover 이후에는 가입을 차단하고 복원 데이터 밖에서 관리하는 새 namespace epoch로 전환하여 이전 attempt/code/proof를 전부 무효화한 뒤만 재개**한다. 자동 epoch 전환·키삭제·FLUSH 명령은 이번 승인에 포함되지 않는다. 운영 epoch 통제와 failover 감지/재개 절차 미확인 시 운영 안전 판정은 차단 유지다.

### HTTP 오류·개인정보·프런트 공동 전환

| 요청/결과 | 구체 계약과 UI |
|---|---|
| attempt 생성 | 201, `{attemptId, attemptSecret, expiresAt}`. 비밀은 최초 응답만 전달. 유실 시 새 attempt 생성 |
| 발급 접수 성공 | 기존200 유지, `{challengeId, expiresAt}`만 반환. authNumber/name/연락처 원문 없음. 공급자 실패/불명503; 기존 중복409 유지. SMS send-disabled는 기존409 경계 유지하되 UI를 “중복 또는 현재 발급 불가”로 정정 |
| verify 성공 | 200 `{proof, expiresAt}`. 원시 code·연락처·회원 존재 여부 없음. server 성공 후에만 UI 검증 완료 |
| 무증명/틀린/만료/세대·대상 불일치 | 400 `{code:"SIGNUP_VERIFICATION_REQUIRED"}`. 어느 연락처/회원인지 추가 노출하지 않음. secret 불일치도 같은 일반 오류이며 발송·상태변경0 |
| 확인 한도·발송 한도 | 429 `{code:"SIGNUP_LIMIT_REACHED"}`. 발송 rolling window는 Retry-After, 확인 한도는 새 attempt 안내. 남은 정확 시도 횟수는 응답하지 않음 |
| 이미 검증/소비된 증명 재요청 | 409 `{code:"SIGNUP_VERIFICATION_RESTART_REQUIRED"}`. verify 응답유실/중복가입 요청은 proof 자동 회수·재발급하지 않고 재인증 안내 |
| Redis/발송/DB 장애·결과불명 | 503 또는 기존 예외의 5xx. UI는 상태 불명으로 취급, 최종 join 실패에는 두 proof 폐기 및 로그인/재인증 안내. 업무 예외 전체를 인증400으로 숨기지 않음 |
| 가입 정상/기존중복 | 기존 빈201+Location `/users/{id}`, 빈400 유지. 최종201 확인 시만 `/login` 이동. 다른400도 재인증 흐름으로 안내하며 신규 개인 정보 조회 API로 중복 대상 확인하지 않음 |

기존 발급409/가입400은 존재 여부 추측 경로를 유지하므로 열거 방어 완료라고 기록하지 않는다. 이를 성공200으로 통일하는 정책 변경은 별도 범위다. 신규 attempt/verify 응답은 불필요한 PII·code·회원 ID를 추가하지 않는다. name 포함 기존 발송 내용과 가입 로그 전면 정리는 RF033 연계이며 비밀 새 로그 추가는 금지한다.

프런트 Second/ThirdPage는 authNumber state·로컬 비교를 제거하고 서버 verify를 호출한다. proof/attemptSecret은 상위 메모리 state에서 유지하며 두 채널 완료 전 최종 submit 불가. 입력 변경은 attempt 폐기, resend 승인 시 해당 proof 폐기, 이전화면 이동도 상태를 명시 처리한다. generation/request ID로 늦은 발급·verify 응답을 무시하고 확인/발송/가입 중 중복 클릭을 막는다. TTL 표시만 믿지 않고 server 결과를 기준으로 하며 code 입력은 text+numeric inputMode로 선행0 보존한다. fetch 성공조건을 명시하여 409/429/5xx를 발송 성공으로 안내하지 않는다.

backend와 frontend는 동시 전환한다. 구버전 UI는 신규 발급 secret/proof 요구를 충족하지 못하며 구버전 backend는 무증명 가입을 허용하므로 mixed writer를 허용하지 않는다. 배포 시 기존 미완료 가입 시도는 재시작 안내, 구writer drain/차단과 모든 ingress 확인 후 개방한다. 되돌림 시 무증명 가입 경로를 복구하지 않고 가입 차단 상태로 유지한다. 실제 릴리스·운영 epoch·프록시 no-store/로그 필터 확인은 미실행이며 문서 작성이 배포 승인이 아니다.

### 공통 계획 리뷰 필수 보완 (현재 계약에 추가)

- **모든 진입점 차단**: 전용 HMAC 키·환경 namespace·독립 운영 epoch가 없거나 형식/환경 일치 검증에 실패하면 issue/verify/final join 모두 fail closed다. 설정 검증은 controller만이 아니라 발급·검증 협력자와 `JoinService.join` 자체의 필수 gate에 적용한다. enable flag=false는 가입 중단이며 기존 무증명 저장 로직으로 fallback하지 않는다. JoinService 직접 호출도 양쪽 proof의 단일 원자 소비 성공 없이는 User/Point 쓰기0, 관리자/내부 호출용 무증명 우회 생성은 추가하지 않는다. 다른 기능의 로그인·조회까지 임의 중단하는 정책은 도입하지 않는다.
- **단일 대상 입력**: canonical화 전에 이메일은 ASCII 단일 mailbox만 허용한다. 표시이름·주석·꺾쇠·인용 local-part·쉼표/세미콜론 다중 주소·CR/LF·내부 공백·복수 `@`를 거부한다. local-part는 ASCII 영숫자와 `. ! # $ % & ' * + / = ? ^ _ \` { | } ~ -` 중 공백을 제외한 문자로 된 dot-atom, 최대64자, 선행/후행/연속 점 금지다. domain은 ASCII DNS label(영숫자 및 내부 hyphen, label1~63자·양끝 hyphen 금지)이 점으로 구분된 최소2개 label이어야 하며 공백/빈 label/말미 점/IP literal/Unicode 원문을 거부한다. 정상 ASCII DNS label인 `xn--` punycode는 일괄 거부하지 않는다. 총 길이254자 이하, domain 소문자화와 바깥 ASCII space 제거만 허용한다(CR/LF/tab을 trim으로 숨기지 않음). Unicode 원문 변환 지원은 별도 정책이다. 인용 local-part 등 이 ASCII dot-atom 제한이 기존 API의 허용 입력을 축소하는지와 소비자 호환은 미검증이며 운영 전 확인한다. 메일 API가 여러 수신자를 파싱할 수 있어도 검증된 단일 canonical mailbox만 전달한다.
- 전화는 기존 UI가 처리하는 **ASCII 숫자 10·11자리** 또는 정확 `XXX-XXX-XXXX` / `XXX-XXXX-XXXX` 형식을 허용한다(X는 ASCII 숫자). 별도 prefix allowlist나 010 전용 제한은 두지 않는다. 바깥 ASCII space 제거 후 위 형식을 검사하고 hyphen을 제거해 10·11자리로 canonical화한다. `+82` 표기, 다른 길이, Unicode 숫자, 중간 공백, 임의 punctuation은 거부한다. 이는 입력 형식 계약이며 공급자가 각 prefix/번호의 실제 발송을 지원한다는 증명이 아니다. 공급자 지원 범위는 미확인이다. 이메일·전화 모두 발송/verify 대상결합/quota/final 저장에 같은 canonical 함수를 쓴다. 현재 raw 기존 계정의 중복조회·로그인과 좁아진 입력의 소비자 호환은 운영 미검증이다. 기존 데이터 일괄 정규화·DB schema 변경은 금지하며 이 제한을 숨긴 채 무변경 API 호환이라고 표시하지 않는다.
- **terminal 상태**: attempt 전체 `consumed`는 해당 epoch에서 terminal이다. join 성공 소비 후 resend/verify/발송완료/실패 callback 모두 상태·카운터·proof를 복구하지 못한다. 발급 예약·verify·join Lua와 발송 completion CAS 모두 attempt nonterminal과 generation을 먼저 확인한다. join↔resend는 하나의 직렬 순서만 이기며 resend 선행이면 구 proof join 거부, join 선행이면 resend 무쓰기·발송0이다. 이미 예약된 발송은 외부 전달 자체를 취소할 수 없지만 늦은 완료는 consumed를 되돌리지 못한다. 동시 verify는 한 요청만 verified/proof 발급 승자이며 패자는409; 성공 후 재비교로 추가 proof를 만들지 않는다. 잘못된 attemptSecret은 quota/generation/attemptCount 포함 **모든 상태 무쓰기**이며 secret 인증 전에 quota를 예약하지 않는다.
- **키·토큰 구성**: HMAC 입력은 version 및 각 필드의 바이트 길이를 명시한 UTF-8 length-prefix encoding으로 구성한다. 단순 delimiter 연결/부분 digest/전화 끝자리 사용 금지. domain separator를 `signup-target-quota`, `signup-code-verifier`, `signup-target-binding`처럼 용도별로 분리하고 environment·epoch·purpose=signup·channel 및 필요한 attempt/generation/대상을 포함한다. HMAC-SHA-256 전체256비트 digest를 key/검증값으로 사용한다. secret/proof는 고엔트로피 CSPRNG token의 SHA-256 전체 digest만 저장하며 목적별 domain prefix를 붙인다. secret 비교가 필요한 Lua에서도 고정길이 비교를 수행하고 실패 경로가 값 차이 위치를 노출하지 않도록 구현/리뷰한다.
- Redis key는 `environment:{signup}:epoch:purpose:channel:type:digest`처럼 환경·세대·용도가 분리된 형식이며 모든 관련 키는 같은 cluster slot에 놓는다. 운영·개발·테스트 환경 식별자는 고정 allowlist/안전문자 검증으로 다른 namespace를 주입하지 못한다. 공개 attempt/challenge ID도 CSPRNG 생성, **NX로 예약하여 collision 시 덮어쓰지 않고 새 ID로 재시도**한다. bounded 재시도 실패는503이며 기존 상태 유지. quota sorted-set member는 시각만 쓰지 않고 서버 생성 고유 reservationId(NX collision 검사)를 사용하여 동일 Redis TIME의 동시 요청도 각1회로 계산한다. 600초 창은 `(now-600초, now]`로 정의하여 정확600초가 지난 예약만 제외한다.
- **회전·복원 한계**: epoch 또는 HMAC 키 변경은 target quota key도 바꾸어 10분 한도를 초기화할 수 있다. 회전/복원 때 구writer를 drain/차단하고 발급을 최소600초 중단한 뒤 새 epoch/키로 개방하는 보수 절차를 기본으로 한다(다른 보존 방식은 별도 설계). code/proof가 모두 만료됐다고 quota 제한까지 충족했다고 보지 않는다. 모든 backend가 동일 새 epoch/키를 확인하기 전 재개 금지; old writer 혼재·진행 중 DB commit은 Lua epoch 변경으로 취소되지 않는다. epoch는 복원된 Redis 안의 값만 신뢰하지 않으며 과거 epoch 재사용 금지다. HMAC 키 유출 시 짧은 code 및 연락처 공간은 대입 가능하므로 암호문 수준의 개인정보 보호를 주장하지 않는다. key 이름·시각·횟수·channel·접근패턴의 메타데이터 노출도 남는다. Redis 권한/로그 접근·보관·키 공급/회전 절차는 운영 검증 대상이다.

추가 필수 테스트는 설정누락/오류/flag=false 때 controller 및 직접 JoinService 쓰기0·발송0, 잘못된 secret의 모든 상태 불변, 이메일 다중수신자/CRLF·모호 domain·전화 Unicode/잘못된 길이·hyphen 형식 거부와 10·11자리/다양한 prefix·정상 punycode 허용, canonical 동일 quota·저장 일치다. consumed terminal에 대한 join↔resend/verify/늦은 완료의 두 직렬 순서, 동시 verify 한 proof, ID collision 기존 상태 보존, 동일시각 발송4개 중3개 예약, full digest domain 분리/길이모호 입력 구별, 키·epoch 전환 후 구 proof 거부와 quota600초 대기 조건도 검증한다. code5분 만료는 Redis TIME의 정각 포함 거부이며 키 TTL 지연/시계 경계·대역과 실제 Redis script 결과를 구분한다. 기존409/400 열거 잔여는 유지하고 실제 운영 epoch·failover·writer drain은 **미검증**, 실제 발송은 **금지**다.

## 2026-11-11 구현·격리 검증 이력

사용자 확정 정책에 따라 backend와 signup UI를 함께 전환했다. 신규 라이브러리·DB schema·기존 사용자 데이터·운영 설정·키/epoch를 변경하지 않았고 실제 DB/Redis/SMTP/SMS/HTTP 서버를 구동하거나 연결하지 않았다. 다른 RF024/039/040/044 코드·공통 BACKLOG/LOG는 통합 담당 소유로 유지했다. 직접 영향을 받은 RF016 격리 config/smoke 두 테스트의 가입 분기만 통합 담당 조율 후 적응했으며, 과거 RF016 원시 자료를 덮어쓰지 않았다.

- `SignupVerification`은 CSPRNG attempt/비밀/6자리 code/proof, secret/proof의 domain-separated SHA-256 전체 digest, 전용 HMAC-SHA-256·길이명시 encoding을 사용한다. 환경 allowlist와 안전 epoch 형식, Base64 전용키 최소32byte 및 enabled gate는 issue/verify/consume와 직접 JoinService 호출에 적용된다. `signup.verification.enabled` 기본 false는 **가입 중단**이며 proof 없는 저장 fallback은 없다. 설정이 없어도 다른 기능의 startup을 임의 중단시키지 않는다.
- 운영에서 공급할 별도 property는 `signup.verification.enabled`, `signup.verification.environment`(local/development/test/staging/production), `signup.verification.epoch`(안전문자16~64자), `signup.verification.hmac-key`(별도 Base64 key)다. 실제 값을 생성·설정하거나 서비스 개방을 하지 않았다. key/epoch/환경 동기화와 외부 epoch 운용은 여전히 운영 gate다.
- `RedisSignupStore`의 Lua는 같은 `{signup}` slot에서 attempt hash와 대상별 rolling quota zset, challenge 예약 key를 사용한다. Redis TIME·명시 만료·TTL 정리, HSETNX/SET NX 충돌 재시도, 고유 quota member, secret 인증 후 reserve, generation별 pending→sent/failed, 확인 누적5회, verified code 재사용 거부와 두 proof 단일 소비·consumed terminal을 구현했다. quota 실패·잘못된 secret은 상태를 바꾸지 않는다. 물리 Redis에서 이 script를 실행한 결과는 없다.
- `JoinService.join`은 canonical email/phone에 결합된 두 proof 소비 성공 후에만 기존 중복 검사·UNCONFIRMED_USER·비밀번호 encode·User/초기 PointHistory 경로로 진행한다. 기존 transaction annotation을 유지했다. 실제 DB commit/rollback을 검증한 것은 아니며, Redis 소비를 DB rollback으로 복원하지 않는다. 중복400·save/point 예외·응답유실/불명에 proof 자동 재시도는 없다.
- 실제 EmailAuthService+memory JavaMailSender, 실제 PhoneNumberAuthService+sender adapter를 분리했다. Nurigo SDK 생성은 실제 sender 호출 시점으로 늦췄고 격리 테스트는 그 adapter/SDK bean을 생성하지 않는다. 발송 응답은 challenge/만료만 주며 authNumber를 제거했다. signup controller의 이름·연락처 로그를 제거하고 request/secret/proof/예약 객체의 toString은 비밀을 가린다. 새 응답은 no-store다.
- 기존 signup 실컴포넌트는 서버 attempt→issue→verify→proof를 사용하며 code를 text/numeric input으로 보존한다. proof/secret은 상위 메모리 state에만 둔다. 입력 수정·이전화면·명시 재시작·최종 실패 때 폐기하고, 중복 클릭·unmount/늦은 응답을 거부한다. 발송409/429/5xx를 성공으로 안내하지 않으며 최종201에서만 login으로 이동한다. 최종 가입의 실패/네트워크 불명은 자동 반복 없이 두 채널 재인증 및 이미 가입됐을 수 있다는 로그인 안내를 한다.

### 미실행·운영 차단과 재개 조건

운영 개방은 계속 차단한다. 실제 Redis에서 Lua 구문/자료형/TTL·TIME·동시 verify/join/resend·같은시각 quota·cluster slot·복제 lag·failover/restore를 실행하지 않았다. 메모리 대역 통과를 이 보장으로 확대하지 않는다. 외부에서 관리하는 epoch·키 공급/회전·구writer drain·최소600초 발급중단·모든 backend 동기화 및 복원 이후 이전 epoch 재사용 금지는 운영 증거가 없다. 별도 허용 환경에서 정확 namespace/소유 key와 cleanup 범위를 정해 실제 Lua·TTL/경쟁/장애를 검증하고 독립 사후 확인 후만 재개한다.

실DB UNIQUE/동시 중복·기존 raw 이메일/하이픈 전화 계정과 canonical 신규가입의 중복/로그인 호환·좁아진 ASCII mailbox 입력의 소비자 호환·저장/초기포인트 실제 transaction commit/rollback·Redis 선소비 뒤 DB commit 불명·commit 뒤 HTTP 응답유실은 미검증이다. 현재 테스트는 repository 예외/소비 timeout 대역과 terminal 상태를 확인한 범위다. 실제 운영 schema 읽기·소유 fixture/응답유실 실험을 승인된 격리 환경에서 추가해야 한다. RF032/040의 중복/계정세대 한계를 이 작업으로 해결했다고 보지 않는다.

### 공통 최종 리뷰 반영

서버 proof 우회는 공통 독립 코드 리뷰에서 발견되지 않았고, 프런트 P2 두 건을 반영했다. resend 예약 이후503/응답유실/잘못된 응답은 해당 proof/challenge만 폐기하며, 서버 무변경이 확정된429만 기존 proof를 보존한다. 반대 채널/attempt는 유지한다. endpoint별 응답은43자리 base64url 문자열 ID/secret/proof와 positive safe integer 만료를 엄격히 검사한다. 실제 두 컴포넌트에서 old proof+503/network/malformed/429와 반대 채널 불변·응답타입 거부25회귀를 추가해 최종 프런트47개·lint·tsc를 재검증했다. backend source는 이 리뷰에서 변경하지 않았다. 원시 자료/중간22개 보존 및 최초 frontend runner 사본 한계는 증빙 README를 따른다. 최종 통합 담당 확인 및 모든 운영 재개 gate는 여전히 별개다.

Lua의 에러 rollback을 가정하지 않도록 모든 mutation 전에 key/ARGV count·namespace/epoch/type/channel·key alias·token/digest 형태, 정수 TTL/횟수 범위, root=open, 채널 state별 필수/금지 필드, quota 자료를 명시 검사했다. 잘못된 내부 인수·손상/미지 상태는 무쓰기 failclosed다. 행동대역2개와 Lua guard 배치의 정적 구조1개를 추가하여 최신 backend49건(service32+chain5+RF016A12), failure/error/skip0 및 assemble5task 실실행을 확인했다. `after/preflight-final-*` 원시 결과·최종 source35개와 이전46개 source/결과를 구분 보존한다. 실제 Lua parser/script/TTL/cluster/부분쓰기·원자성은 여전히 **미검증·운영 차단**이며 테스트 대역 통과로 해결하지 않았다.
