# RF-037: 결제 차감과 거래 상태 변경의 원자성

- 상태: **2단계 공동 원자 결제 최소 구현·오프라인 선택 검증 완료, 공동체인6건 포함 독립 최종 리뷰 완료 / 실DB·운영 개방 미완료** (2026-11-11). 이전 분석·미착수 설명은 당시 이력이며 최하단 구현 결과가 현재 기준이다. 최신 계약은 최하단 공동 리뷰 절을 따른다. RF035 구현과 병행한 문서 전용 작업이며 DB・운영 개방 승인이 아니다. 초기 key/proof 저장・결제200 재현・PUT2 호환 대안은 검토 이력으로만 남긴다.
- 우선순위: P0, R3-거래원자성 이관. 결제 커밋 뒤 별도 상태 PUT 실패가 발생할 수 있는 호출 경로가 있다. 운영 발생 건수·피해는 미확인이다.
- 기준: `main`, HEAD `82aa7279886385bc0974ae78679ab492447f4135`. 시작 시 `.tmp/`, RF035·RF038 명세/증빙 untracked를 관찰했다. 병행 변경을 덮어쓰지 않는다.
- 지침: 루트 AGENTS, refactoring README·tasks/TEMPLATE·BACKLOG·2026-11-10 재평가, RF003/004/006/008/021/023 및 RF035/038 최신 사용자 결정 확인. 수정 허용은 본 파일과 `evidence/RF-037/README.md`뿐이다.

## 목표와 정적 근거

한 결제 명령의 포인트 차감과 거래1→2를 같은 로컬 DB 트랜잭션에서 성공 또는 실패시키는 경계를 설계한다. 응답 유실 후 동일 결과 재현은 RF036, 거래 당사자·상태 전이 정책은 RF038과 공동 계약으로 다룬다. 원자성과 멱등성을 동의어로 사용하지 않는다.

아래 B/F는 각각 `NGNG-backend/src/main/java/com/ngng/api/`, `NGNG-frontend/src/` 기준이다. RF035 병행 구현 이전에 읽은 소스의 특성이며 최종 구현 리뷰 시 다시 대조해야 한다.

| 경로·호출 | 확인 내용 |

RF003의 결제 실패 시 PUT 미호출 검증은 성공 뒤 실패를 해결하지 않는다. RF004는 수락·거래 생성 원자성, RF006은 Long 값 비교, RF008은 응답 축소, RF021/023은 각각 요청·상세 인가로 범위가 다르다. chat-server는 자체 거래 상태 조회 소비자이며 backend 단건 API만 바꿔 모든 표시 경로가 즉시 갱신된다고 주장할 수 없다.

## 확정 정책과 범위

- RF035 확정: 기록 consumer만 거래 price로 결제, body 금액 불일치·없는 거래 거부. 직접 생성 거래도 허용하며 accepted request 존재를 결제 필수조건으로 추가하지 않는다. 상품 현재가격·forSale=true 강제 없음. 기존 양수 충전은 유지한다.
- RF038 확정: 기록 seller 기준. 정상1→2 구매자 결제, 2→3→4 seller, 4→5 buyer. 역행·건너뛰기 거부. 목표6/7은 기존 상태에서 양 당사자에게 허용하고 6↔7·동일 예외 상태도 허용한다. 6/7→1~5는 거부. 취소/신고에 환불·상품 복구·재판매를 추가하지 않는다.
- RF035/038의 확정 정책은 다시 승인 대기로 돌리지 않는다. 결제 성공 proof 저장·반복 응답·공동 배포와 기존 데이터 처리 방식은 아직 결정할 설계 사항이다. 직접 생성 인가 보류 위험을 자동 해결하지 않는다.
- 성공 URL/method/응답을 가능한 한 유지한다. 새 결제 endpoint는 필수가 아니다. `check`는 호환용 참고 검사로 남길 수 있고, 클라이언트 status2 PUT만 제거해도 공개 상태 endpoint 전체 삭제는 필요하지 않다.
- 구현 후보: PointHistoryService 결제 경계, 필요한 transaction repository/current-state 읽기, TransactionDetailsService 상태 전이/잠금, BuyProductDetails 및 SWR 재조회, 선택 테스트. 신규 의존성·스키마·대규모 구조·운영 데이터 보정·정산/환불은 별도 승인한다.

## 실패 모델과 대안

| 실패/경합 | 현재 가능 결과 | 목표·경계 |
|---|---|---|
| 차감 성공 후 브라우저 종료·PUT 유실/실패 | 차감만 남고 상태1; 다시 결제하면 또 차감 가능 | 동일 DB commit으로 부분 성공 제거 |
| 결제 commit 후 응답 유실/JSON 처리 실패 | 클라이언트 실패지만 차감 완료; PUT 안 보냄 | 서버는 차감+2 유지. 동일 키 재요청의 결과 재현은 RF036 |
| PUT2 직접 호출 | 차감 없는 입금완료 가능 | 최초1→2를 public status PUT에서 생성하지 못하게 하고 결제 명령만 실행 |
| 두 payment 동시/취소와 경합 | 잔액 락만으로 거래 전제 보호 불가 | 동일 거래 규약 안에서 현재상태 검사·차감·상태 전이. 먼저6/7이면 결제 거부, 결제 먼저면 이후6/7 허용·환불 없음 |
| commit 실패·연결 단절로 commit 결과 불명 | 프런트의 실패가 rollback 증명 아님 | 동일 식별자로 결과 조회/재시도, 무조건 보상 적립·새 키 재결제 금지 |

**우선 제안 A: 기존 payment 안에서 차감+상태2를 한 transaction으로 처리한다.** 서버 내부 전용 경로로 상태를 바꾸고 public PUT의 최초1→2는 거부한다. 프런트는 payment 성공 후 포인트/거래를 재조회하며 별도 PUT2를 제거한다. 같은 DB·transaction manager를 사용하는 두 쓰기에는 분산 transaction·메시지 broker·outbox가 필요하다는 근거가 없다. 이미 외부 결제 gateway가 관여한다고 가정하지 않는다.

대안 B는 거래ID 중심 새 결제 endpoint다. 식별은 명확해지지만 기존 상품ID 결제도 같은 내부 경계를 거치게 전환해야 하며 두 독립 차감 경로를 남기면 안 된다. 새 URL은 현재 목표의 필수조건이 아니므로 우선 채택하지 않는다. 대안 C는 결제 proof를 저장하고 후속 PUT이 검증·복구하는 방식이다. 두 요청 사이 불일치 기간과 재처리 상태를 별도로 관리해야 하므로 단일 로컬 commit보다 복잡하다. 보상 적립은 성공 여부 불명·반복 보상·이미 배송 진행 등 업무 문제가 있고 새 환불 정책이 필요하여 자동 도입하지 않는다.

### A의 구체 경계와 잠금 순서

1. 기존 controller→Spring proxy의 단일 public 결제 service 진입을 유지한다. RF035 입력·실제 인증 사용자 검증 후 상품 PK scalar lock을 획득한다. RF004와 일관된 RC transaction 후보이며 임의 outer RR/사전 로딩 entity 지원은 별도 검토한다.
2. 상품 잠금 뒤 유일 거래를 새로 읽고 buyer/price/상태1을 재검증한다. 0/다건/불완전 관계·상태는 무쓰기 거부한다. 캐시 DTO 또는 잠금 이전 entity의 값을 결제 권위로 쓰지 않는다.
3. 권고 순서는 **상품→거래 보호→user→최신 point 이력**이다. 거래 보호를 공통 상품 잠금으로 할지 거래 행 잠금도 둘지 구현 전에 확정한다. 전자는 모든 상태 writer의 동일 상품 잠금 준수가 필수다. 후자도 상품보다 거래를 먼저 잡는 역순을 만들지 않는다. transId PUT은 상품ID scalar 조회→상품 잠금→거래 재조회/관계 재검증으로 stale entity와 역순 락을 피한다.
4. user·최신잔액 잠금 후 잔액 검사, 이력 append와 managed status2 변경을 같은 persistence transaction에서 수행한다. status 조회 실패·flush/commit 실패는 둘 다 rollback되어야 한다. REQUIRES_NEW로 차감을 먼저 확정하거나 예외를 삼킨 성공 응답을 만들지 않는다. 자기 메서드 호출에 annotation만 붙여 새 경계가 생긴다고 기대하지 않는다.
5. RF036 durable key/result를 채택하면 proof·키 성공결과도 같은 commit에 포함한다. 키 선점/unique 충돌의 잠금 순서는 RF036과 공동 설계한다. user 잠금을 쥔 뒤 상품을 잡는 재진입·별도 키 transaction을 임의 추가하지 않는다. 실제 unique/FK·자동 flush lock까지 확인하기 전 deadlock 없음이라 판정하지 않는다.
6. 충전은 user→point만, create/수락은 상품→거래를 유지한다. 주소/상품 삭제/일반 수정/외부 SQL writer와 bulk status UPDATE의 실제 동시 동작은 후속 조사다. 적용하지 않은 writer까지 보호된다고 확대하지 않는다. deadlock/lock timeout을 돈 명령의 무조건 자동 재시도로 감싸지 않고 RF036 식별/전체 transaction 재시도 정책과 맞춘다.

### proof·기존 데이터·호환성

스키마 없이도 통제된 신규 경로의 차감+상태2 원자 commit과 상태1 재진입 차단은 구현할 수 있다. 그러나 status2만으로 기존 거래가 결제되었다고 증명하거나 과거 결제 응답을 복원할 수는 없다. 상태3~7도 결제 proof를 대신하지 않는다. 기존 데이터에는 (a) 차감 없는2 이상, (b) 차감 있으나1, (c) 중복 차감, (d) 거래 없는/오염된 이력 가능성이 있으며 실제 존재·규모는 미확인이다. 특히 기존 상태1을 모두 신규 미결제로 간주하면 고아 차감의 재결제가 발생할 수 있다.

권고는 RF036의 영속 결제 식별/결과와 거래·구매자·금액·point_history 참조를 공동 검토하는 것이다. 새 테이블/FK/고유키가 필요하면 별도 스키마 승인을 받는다. typeDetail 파싱, timestamp cutoff만으로 기존행을 정상 결제로 이관하거나 중복을 자동 환불하지 않는다. schema 없이 진행하는 대안은 불명 상태를 보수적으로 거부·조사하고 재요청 성공을 보장하지 않는 것으로, 기능 제한·기존 거래 분류 방법까지 사용자와 합의해야 한다. 새 proof 도입도 과거1+차감행을 자동 식별해 주지는 않는다.

구클라이언트는 새 payment 뒤 추가 PUT2를 보낸다. 호환 no-op 200을 제공하려면 당사자 검사와 권위 있는 해당 결제 증거가 필요하고 추가 차감/전이를 해서는 안 된다. 기존 status2만 확인해 결제 성공으로 회신하는 방식은 채택하지 않는다. 또는 중복 PUT2를 거부하고 UI를 함께 배포할 수 있으나 구클라이언트 오류·재시도 영향은 고지/전환 계획이 필요하다. 결제 응답 유실을 status 조회만으로 성공 판정하지 않는다. 새로운 키로 무조건 재결제하도록 안내하지 않는다.

### 선후관계와 배포

RF035 구매자/금액 구현은 독립 의미가 있지만 원자성·멱등성 완료로 표현하지 않는다. RF038 정책→RF036 key/proof·RF037 단일 commit 공동 계약→선택 테스트·실DB 격리 검증→프런트 전환 및 배포 계획 순서다. RF038의 PUT2 차단만 먼저 배포하면 기존 결제는 차감 뒤 실패하고, payment만 통합한 채 기존 PUT 역행을 남기면 재결제 우회가 남는다. 같은 릴리스 경계 또는 명시적인 전환 통제가 필요하다.

혼합 버전 서버가 기존 payment·status writer를 계속 처리하면 새 서버 규약만으로 보장할 수 없다. 오래된 인스턴스/진행 요청을 배제하는 전환 절차와 구클라이언트 처리, 기존 불명 거래의 분류·대응, RF036 proof의 수명/재조회가 배포 선행 조건이다. 롤백 시 구 payment/무제한 PUT을 다시 켜면 불변식이 깨진다. 사용자 변경을 보존해 해당 릴리스 diff만 되돌릴 수 있도록 준비하되, 금전 쓰기 재개는 호환·데이터 상태 확인 후 결정한다. 운영 쓰기 제한/데이터 보정 자체는 이번에 실행하지 않는다.

### cutover·확인·검증 순서

1. 실제 운영 writer·DB·구버전 인스턴스·진행중 transaction·외부 SQL/복원 경로를 조사한다. 아직 수행하지 않았다. 단순 애플리케이션 배포 완료 시각을 cutover로 간주하지 않는다.
2. schema 표식 또는 검증된 경계/목록 방식의 구체 설계와 기존행 unknown 정책을 제시한다. DDL·기존행 UPDATE·이관·운영 중지/쓰기에 대한 별도 승인을 받은 뒤에만 실행한다. 단순 정책 확정은 이러한 실행 승인과 다르다.
3. 구 writer와 진행 요청을 정리한 실제 경계를 기록하고 전체 새 writer를 함께 전환한다. 경계 기록은 환경/DB 식별·적용 버전·in-flight 종료 근거·복원/rollback 대응을 포함한다. 이전 코드가 다시 쓰거나 DB가 복원되면 경계를 재검증하며 불명 상태는 차단한다.
4. 기존 status1은 자동 재차감하지 않는다. 검증자는 신뢰 가능한 거래별 결제 기록·원시 기록 출처와 교차 근거를 확보하여 “미결제 확인”, “기결제 확인”, “불명”을 구별한다. 이 저장소만으로 그런 외부 증거의 존재를 보장하지 않는다. 로그/typeDetail/동액·비슷한 시각 또는 자료가 검색되지 않았다는 사실만으로 미결제를 확정하지 않는다. 불명은 계속 차단, 기결제 상태 보정·중복 환불은 별도 운영 승인 사항이다.
5. 테스트에는 old status1+차감, old status1+불명, old status2+무차감, 새 transaction+legacy 상품, cutover 직전 시작/직후 commit, 같은 timestamp, ID gap/미완료 INSERT, 표식 null/unknown·구 writer 재유입·복원, 두 결제 경합→한 차감/다른409를 추가한다. 완료된 거래의 차감 증거와 현재 상태를 별도 검사한다. 모든 검증은 미실행이다.

현재 판단: 사용자 업무 정책은 확정됐지만 **기존/신규를 신뢰성 있게 구분하는 영속 근거와 실제 cutover 방식은 미확정**이다. RF036/037 공동 구현 검토에서는 이 부분을 schema/운영 변경 승인 경계로 보고하며, 스키마를 몰래 추가하거나 임의 날짜/ID 상수로 차단을 해제하지 않는다. 공통 BACKLOG에는 RF037 기존행 보호·전환 검증 잔여로 통합 담당이 연결한다.

## 2026-11-11 추가 확정: 신규 여부와 무관한 검증 기반 허용

사용자는 **신규 여부와 관계없이 이전 차감 위험을 확실히 판별하지 못하는 거래는 차단하고, 검증 근거가 확보된 거래만 결제를 허용**하도록 확정했다. 따라서 신규 protocol 표식·생성 시각·cutover 이후 생성은 단독 허용 근거가 아니다. 안전한 근거를 확보하지 못하면 해당 거래를 계속 차단한다. 이 절이 앞선 신규 경로 허용 후보보다 우선한다. 실행 근거 없는 허용목록 자동 부여, 직접 생성/수락 때 자동 등록, 기존행 일괄 등록은 금지한다.

### 무스키마 후보: 배포별 서버 검증 거래 허용목록

다음은 실제 구현 가능한 **설계 후보**이며 운영 목록을 만들거나 거래를 허용한 결과가 아니다. DB DDL/수동 데이터 수정 없이 서버 설정의 불변 manifest를 읽고, 기본 전부 차단한 상태에서 정확히 일치하는 항목만 기존 결제 검증으로 진행시킬 수 있다. 목록 항목은 결제 자체의 승인 증거가 아니므로 아래 자료와 배포 통제가 모두 필요하다.

| 요소 | 구체 조건 |
|---|---|
| manifest 범위 | 명시적 환경 식별자·DB 인스턴스/데이터 세대 식별자·릴리스/검증 세대·manifest version·유효기간과 제한된 항목 수를 포함. 값 누락/알 수 없음/중복키/파싱 실패/빈 목록/환경 불일치는 전체 허용을 하지 않음. 기본 목록은 빈 값 |

**복원 시 무효화를 애플리케이션 설정만으로 자동 보장할 수는 없다.** DB snapshot이 상태1과 동일 tuple/fingerprint를 되돌리고 같은 환경 설정/manifest까지 재사용하면 서버는 과거 결제를 구분하지 못할 수 있다. 프로세스 메모리의 사용완료 집합도 재시작·다중 인스턴스·복원에 안전하지 않다. 이를 해결했다고 주장하지 않는다.

무스키마 운영안에서는 복원/클론/환경 전환/rollback 전에 결제 ingress와 모든 writer를 차단하고 manifest를 폐기해야 한다. DB와 함께 복원되지 않는 관리 경계에서 **새 데이터 세대 값**을 발급하고 기본 빈 manifest로 시작한 다음, 과거 차감 증거를 다시 확인한 항목만 새로운 검증 세대에 승인한다. 실제 복원 절차가 이 통제를 빠짐없이 수행하고 구 배포/manifest를 재활성화할 수 없다는 운영 근거가 필요하다. 단순 environment variable/DB URL/부팅시각 비교만으로 이 조건을 충족했다고 보지 않는다. 이러한 절차를 보장할 수 없거나 복원 여부가 불명하면 전부 차단을 유지한다. 자동 탐지가 요구된다면 별도 영속 세대/결제증거 구조를 설계하고 필요한 schema/외부 관리 구조 승인을 받아야 한다.

### 규모·운영 해제·감사의 한계

허용목록이 무한 증가하지 않도록 크기 상한·짧고 명시적인 유효기간·배포 단위 불변 manifest·결제 완료/만료 항목의 다음 릴리스 제거를 제안한다. 구체 상한/기간은 아직 정하지 않았고 성능 개선을 주장하지 않는다. 항목 제거는 DB 금전 보정이 아니다. 큰 목록 분할/동적 등록 서비스·외부 저장소를 자동 도입하지 않으며 규모가 수동 검증/배포 한계를 넘으면 기본 차단을 유지하고 별도 운영 구조를 결정한다.

검증 완료 항목의 등록도 실제로는 금전 기능을 여는 운영 변경이다. 사용자 정책 확정은 근거 없이 항목을 생성해도 된다는 뜻이 아니다. 검증자는 실제 증거를 확보하고 별도 운영 승인·검토 절차에 따라 정확한 tuple만 추가한다. 증거의 출처/진위/보존 범위가 불명하면 등록하지 않는다. 데이터가 결제되지 않았다는 부재 증명은 로그 일부 검색만으로 확보되지 않으므로 이 저장소만으로 자동 allowlist를 생성할 수 없다.

동적 설정을 지원하지 않는 최소안에서는 폐기된 manifest를 들고 있는 모든 인스턴스의 트래픽을 먼저 차단/종료한 뒤 새 설정으로 배포한다. reload 기능을 도입한다면 요청 전체에서 같은 immutable snapshot·세대를 쓰고, 검증 후 commit 전 폐기 경합을 막는 별도 운영/동시성 규약이 필요하다. 파일 hash는 변조 탐지 보조일 뿐 검증자의 판정 정확성/신뢰를 증명하지 않는다. 감사 기록 보존기간·PII 최소화·접근권한·책임자/이중검토는 운영 계약이며 이번에 시스템을 추가하지 않는다.

추가 검증 계획: 기본 빈/오류 manifest 모두 거부, 환경/세대/릴리스 불일치·만료·중복 거래/잘못된 Long 거부, 정확한 tuple만 통과, 가격/관계 변경 거부, 변경 후 복구/동일 timestamp의 한계를 드러내는 fixture, old manifest 재사용·복원 뒤 기본 차단, 다중 인스턴스/구버전 차단·폐기 중 진행 요청, 완료 상태 재요청409·동시1회 차감을 확인한다. 지금은 테스트/운영 설정/DB를 실행·수정하지 않았다. **정확한 허용 근거·변경/복원 통제가 없는 거래는 결제 차단**이 최종 안전 기준이다.

## 2026-11-11 공동 리뷰 확정 계약 — 최신 기준

이 절은 앞선 선택지보다 우선한다. RF036/037/038의 구현·검증은 다음 공통 계약을 사용한다. 결제200 응답 재현·키 TTL·durable proof 신규 schema는 이번 최소안의 필수 요구가 아니며 자동 도입하지 않는다. **결제 재요청409**와 아래 **상태 PUT2→2 호환200**은 서로 다른 요청이다.

### 단일 결제 transaction과 current read

고정 순서는 **상품 PK scalar lock → 거래 scalar current lock → 기록 buyer/price/현재상태1·manifest 검사 → user/최신 point lock → 차감 이력 append → 상태 조건부 UPDATE affected=1 → 단일 commit**이다. 같은 transaction manager/연결의 경계에서 수행하고 실패하면 전체 rollback한다. 거래의 scalar current read에는 id/product/consumer/seller/price/status 등 판단에 필요한 권위 값을 포함한다. 기존 일반 findById/entity가 캐시한 값이나 잠금 이전 읽기를 그대로 재사용하지 않는다.

상태 UPDATE는 같은 거래·기대 상태1 및 필요한 불변 조건으로 제한하고 affected count가 정확히1이 아니면 예외로 전체 rollback한다. 관리 entity 변경을 쓰는 동등 대안은 current state·캐시/flush 안전성을 입증한 경우에만 사용한다. native/bulk update 뒤 persistence context의 오래된 거래가 나중에 flush되어 상태를 되돌리는 위험을 제거해야 한다. 새 경로에서 사전 target entity 로딩을 피하고, scalar 잠금 전에 관련 dirty entity를 두지 않으며, native query의 자동 flush·조회 후 DTO 변환으로 인한 재로딩을 검토한다. 명시 flush/clear를 무차별로 넣어 외부 변경을 유실시키는 방식은 채택하지 않는다. 임의 outer transaction/사전 stale context는 지원된다고 가정하지 않으며 HTTP/OSIV 경계와 직접 호출에서 이를 검증한다.

manifest 필수 결합은 RF036과 동일하게 **transactionId/productId/consumerId/sellerId/정확한 price + 환경/데이터 세대/검증 세대 및 검증 근거**다. seller를 생략하지 않는다. 현재 상태·tuple·만료 여부의 최종 판정은 상품/거래 잠금 획득 **후** 수행한다. 잠금을 기다리기 전 유효했다는 사실로 통과시키지 않는다. 잠금 이후 대기·장시간 transaction의 만료 경계도 검사 시점 기준을 명시하고 검증하며, 이전 manifest snapshot의 폐기 경합은 앞선 배포 통제 계약으로 차단한다. manifest 자체는 과거 미차감 proof가 아니고, 근거 없는 항목은 생성하지 않는다.

### public 상태 요청과 프런트 복구

- public PUT 최초1→2는 거부한다. 정상 최초 전이는 오직 결제 원자 명령에서 수행한다.
- 구클라이언트의 **PUT2→2는 기록 당사자에게200·무쓰기·기존 거래 DTO**로 응답한다. 이 응답은 현재 상태를 그대로 돌려주는 호환 계약이며 결제 성공/정상 차감 증거가 아니다. 그러므로 이 no-op에 status2의 과거 결제 proof를 요구한다는 앞선 대안은 채택하지 않는다. 완전한 기록 당사자 검사, 제3자 거부, 상태 setter/bulk UPDATE/이력/updatedAt 변경0을 검증한다.
- 신규 프런트는 payment 이후 추가 PUT2를 제거하고 포인트/거래를 재조회한다. 결제409, 네트워크 실패/응답 유실, 사전 `/check` 부족 응답에서는 **거래 상태를 먼저 재조회**하여 이미 처리된 요청 가능성을 확인한다. `/check` 부족은 현재 결제가 실패했다는 최종 증거가 아니다.
- 조회 실패는 결제 rollback·확정 실패로 단정하지 않으며 자동 재결제/보상 적립을 하지 않는다. 상태2 이상도 과거 정상 차감 proof로 표현하지 않고, 현재 상태와 결제 결과 확인 불가를 구분한다. 사용자가 새로고침해도 근거 없는 허용목록 생성/차단 해제는 하지 않는다.

### 구분해 검증할 실패와 배포 조건

1. 차감 INSERT를 실제 flush한 후 상태 UPDATE 실패/affected0·복수 오류를 주입해 차감과 상태가 모두 rollback됨을 새 연결로 확인한다. commit 실패를 주입하는 경우도 실제 DB 결과를 확인한다. commit 시 연결 단절처럼 결과가 불명하면 단순 실패 예외를 rollback 증거로 삼지 않는다.
2. **commit 성공 후 응답 유실**은 별도 시나리오다. 이미 차감1건+상태2가 남고 재결제는409여야 하며, 상태/포인트 조회 실패를 자동 재결제로 연결하지 않는다. mock transaction advice의 rollback 호출은 물리 DB rollback 증거가 아니다.
3. 거래 current scalar 조회·조건부 UPDATE·auto-flush/첫 수준 캐시·OSIV, 동일 거래 동시 요청, 잠금 대기 중 manifest 만료, seller 포함 tuple 불일치, 구클라이언트2→2 무쓰기, `/check` 부족 후 거래 재조회 순서와 조회 실패 UI를 추가 검증한다. 미실행이며 RF035 선택 테스트 성공을 이 검증으로 대체하지 않는다.
