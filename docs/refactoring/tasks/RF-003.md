### 호출·데이터·트랜잭션 경계

- 저장소 전체 Java 검색에서 PointHistoryRepository의 운영 쓰기 사용자는 PointHistoryService 하나다. 쓰기 메서드는 가입 초기화, updateCost, payment다. updateCost/payment의 직접 Java 호출자는 PointController이며 거래 서비스에서 호출하지 않는다. 외부 SQL·배치·다른 배포 버전의 쓰기는 미확인이다.
- 충전 화면 `NGNG-frontend/src/app/my_page/_compoenets/modal/PointModalContent.tsx` → `_api/api.ts:addFetchPoint` → POST `/api/points`. 화면은 음수·NaN을 막지만 0/빈 입력은 별도 금지하지 않는다. 서버 정책 변경 시 이 입력은 실패할 수 있다. 프런트 수정은 별도 범위 합의 대상이다.
- 결제 화면 `NGNG-frontend/src/app/my_page/_compoenets/modal/BuyProductDetails.tsx:onPayment` → `isPayment` → `paymentProduct` → 거래 상태 변경. 세 단계는 별도 HTTP 요청이고 원자적이지 않다. paymentProduct는 HTTP 성공 여부 확인 없이 JSON을 반환하며 호출 화면은 그 뒤 상태 변경을 요청하므로, 새 실패 응답 도입 시 거래 상태를 잘못 바꿀 수 있는 경계가 있다. 사용자가 이 프런트 실패 처리의 최소 수정·검증을 승인했다.
- `TransactionDetailsService.updateTransactionStatus`의 트랜잭션은 별개다. 포인트 결제와 상품/거래/판매자 잔액 변경을 통합하지 않는다. 요청의 상품 ID와 가격을 서버에서 조회·대조하지 않는 현행 경계 역시 이번 금액 정책 승인만으로 변경하지 않는다.
- 조회 영향: `/points`, `/points/all`, 사용자 목록/상세/마이페이지가 최신 이력과 잔액을 소비한다. RF-002 단건/일괄 조회와 최신 ID 의미는 보존한다. 채팅 서버 소스 검색에서 포인트 쓰기 경로는 발견하지 못했다.

### 확인된 사실과 미검증 가설

**구조상 위험:** 두 요청이 B를 각각 읽고 B+a, B+b를 저장하면 최종 최신 잔액은 B+a+b가 아닐 수 있다. 동시 충전·결제 혼합에도 동일하다. 새 이력 append 모델이므로 마지막 이력 한 행에만 잠금을 거는 것으로 사용자 전체를 직렬화한다고 단정할 수 없다. 이력 없는 경우에도 잠글 안정적인 대상이 필요하다.

**미검증:** 실제 동시 누락·잠금 대기·교착, DB 버전/격리수준/쿼리와 잠금 범위/외부 쓰기, 운영 JSON·오류, 사용자별 이력 누락 및 금액 이상 데이터 분포. 본 문서의 동시성 숫자는 테스트 입력 계획이며 실측 결과가 아니다. 성능 개선·저하 모두 판단하지 않았다.

## 접근 및 위험

1. 기존 동작 특성 테스트와 승인된 정책의 실패 테스트를 분리한다. 변경 전 mock 결과를 실DB 동시성 재현으로 세지 않는다. API/금액 경계를 먼저 확정하고 최소 수정한다.
2. 후보안은 **안정적인 사용자 PK 행을 잠근 뒤 최신 이력을 읽고 검사·저장하는 하나의 서비스 쓰기 트랜잭션**이다. 두 메서드가 반드시 같은 사용자 잠금 규칙을 사용한다. 한 사용자만 처리하며 성공 커밋 또는 실패 롤백까지 잠금을 보유한다.
3. 사용자 잠금만 추가한 뒤 일반 최신 조회를 쓰면 충분하다고 단정하지 않는다. 메서드 시작 뒤 AuthService의 이메일 조회가 먼저 수행된다. 실제 DB가 REPEATABLE READ라면 잠금 대기 전에 만들어진 읽기 snapshot 때문에 이후 일반 조회가 이전 잔액을 볼 가능성을 검증해야 한다. 쓰기용 최신 조회도 current/locking read로 수행하는 안을 우선 검토하며 전역 격리수준은 변경하지 않는다.
4. User/PointHistory의 eager 연관이 실제 SQL에서 role 등까지 잠그는지, 최근 이력 조회의 range/gap lock이 다른 사용자까지 막는지 확인한다. 필요하면 사용자 PK만 잠그는 전용 최소 쿼리를 택한다. 검증 없이 쿼리 하나를 확정하거나 외부 사용자 독립성을 주장하지 않는다.
5. 단순 `@Transactional`만 적용, JVM synchronized, 매번 바뀌는 마지막 이력만 잠금, 새 append 행의 Version만 추가하는 대안은 사용자별 다중 프로세스 쓰기 직렬화의 충분한 근거가 없다. 별도 잔액 테이블/낙관적 버전/분산 락은 스키마·의존성·재시도 설계를 키우므로 이번 최소안에서 제외한다.
6. validation/부족 잔액/저장 예외/커밋 실패 시 미완성 이력이 남지 않아야 한다. 검사 후 저장 전에 외부 결제 호출은 현행에 없으며 새로 추가하지 않는다. 성공 로그는 서비스 내 출력 시점과 커밋 확정이 다를 수 있어 로그만으로 성공을 집계하지 않는다.

위험: 사용자 행을 다른 기능도 수정하면 경합할 수 있다. 동일 사용자 요청은 직렬화되어 대기가 생길 수 있고, 교착·잠금 timeout은 정상 경로와 분리해야 한다. 다른 시스템이 동일 잠금 규약 없이 point_history를 쓰면 보장이 깨질 수 있다. 가입 초기화는 새 사용자 생성 트랜잭션 안에 있으나 향후 재초기화 경로를 추가하면 같은 규약 검토가 필요하다. 이 작업은 과거 잘못된 잔액을 수정하지 않는다.

### 2026-11-04 사용자 승인 후 격리 MySQL 기능 검증

- 추가 승인: 격리 대상과 정리 범위를 확인한 뒤 **테스트 전용 사용자·포인트 이력만 생성하고 해당 행만 정리**하는 동시성·rollback 기능 검증을 승인받았다. 스키마 변경·성능 테스트와 role 생성은 승인 범위에 넣지 않았다. 앞 절의 DB 미접속/미검증 기록은 이 추가 실행 전 단계의 결과다.

- 안전 구성: `PointHistoryMySqlConcurrencyTest`는 정확한 opt-in 없이는 13건 전부 skip한다(증빙 보존). 기존 Boot/application YAML을 로드하지 않고 user/role/point 엔티티·repository·실제 AuthService/PointHistoryService의 Spring 프록시만 구성한다. 고정 `127.0.0.1:13306/ngng_local`, 실제 계정/port/datadir/RR/InnoDB 일치 및 user/point 빈 상태를 테스트 안에서 다시 확인한 뒤 JPA `validate`만 사용한다. 외부 연동 빈·SQL initializer/DDL/role 쓰기는 없다. 제한된 잠금 실패 검증을 위해 연결별 session `innodb_lock_wait_timeout=5`만 설정하며 전역 설정/성능 측정은 하지 않았다.
- fixture/정리: 실행 UUID marker의 사용자 이름·이메일과 생성 ID를 기록하고 별도 트랜잭션으로 커밋한다. 모든 worker의 종료를 확인한 뒤 실제 사용자 ID/이메일/이름을 대조하고 해당 사용자에게 연결된 marker 일치 이력의 **point_id+user_id+type_detail** 조건으로 한 행씩 삭제, 이후 **user_id+email+name** 조건으로 사용자만 삭제한다. 기존 role 행은 읽기 전후 동일성만 검사하며 삭제하지 않는다. 삭제 도중 검증 실패하면 전체 정리 트랜잭션을 rollback하고 범위를 넓히지 않는다.
- 1차 독립 안전 검토: 실행 전 별도 리뷰에서 확정된 오삭제·대상 혼동 결함은 발견하지 못했다. common role 부재는 미검증으로 남기고 proxy hook 도달·Future 미완료를 DB 내부 잠금 대기의 직접 관측으로 쓰지 않도록 확인한 뒤 실행했다.

- 남은 한계: 기존 user_role가 비어 있고 role 생성은 승인 밖이므로 **동일 role을 공유하는 두 사용자 경로는 미검증**이다. 다른 사용자 완료는 role=null fixture에서 확인했다.
