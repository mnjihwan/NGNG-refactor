# RF-008: 포인트 응답의 User 민감 필드 노출 경계

- 상태: 합의한 최소 구현·격리 검증·최종 독립 리뷰 완료 (2026-11-09). 아래 계획 당시 미실행 기록은 당시 이력이며 최신 결과는 하단을 우선한다.
- 우선순위와 선정 이유: P0. 포인트 기능에 필요하지 않은 사용자 인증·개인·계좌 속성이 엔티티 직렬화에 포함될 수 있다.
- 대상 저장소, 기준 커밋 및 관련 담당 흐름: 통합 저장소 `24dda6a7715f505e27e7cf237e1e6e0762b9c06a`; 시작 시 `git status --short` 출력 없음. backend 포인트 응답과 frontend 소비 경계, chat-server 영향 검색. 본 분석 담당은 코드·설정을 수정하지 않는다.

## 목표와 근거

- `NGNG-backend/src/main/java/com/ngng/api/user/point/controller/PointController.java`의 GET `/points`, GET `/points/all`, POST `/points`, POST `/points/payment`는 `PointHistory` 또는 그 목록을 직접 반환한다. POST `/points/check`는 Boolean이며 대상에서 제외한다.
- `PointHistory`는 `user` 연관과 getter를 가지며 `User`에는 `password`, `email`, `address`, `phoneNumber`, `accountBank`, `accountNumber`, `role` 등을 포함한 getter가 있다. 해당 엔티티에 JSON 제외 어노테이션이 없다. 정적 노출 경로는 확인했지만 운영 HTTP 유출 또는 공격 발생을 확인한 것은 아니다.
- `PointControllerContractTest`는 수동 ObjectMapper의 standalone MVC에서 `user.userId`, `user.name`을 종전 계약으로 검증한다. 민감 필드가 채워진 fixture·Boot 구성 mapper·실제 체인은 이 테스트가 보장하지 않는다.
- frontend `src/app/my_page/_api/api.ts`, `_hooks/usePointeHistory.ts`, `_compoenets/PointHistory.tsx`, `type.d.ts` 확인: 목록 UI는 `createdAt/addCost/type/cost/typeDetail`을 사용하고 IPointHistory에 user가 없다. 충전 응답은 JSON 파싱 후 본문 속성 소비가 없고, `BuyProductDetails.tsx`의 결제 호출은 완료를 await하며 반환 속성을 읽지 않는다. 저장소 밖 클라이언트는 미확인이다.
- `AuthService.readAuthUser()`는 인증 principal의 email로 DB User를 읽고 포인트 서비스가 그 ID로 조회/쓰기한다. SecurityConfig의 `/points` 별도 matcher는 없지만 TokenFilter 제외 경로에도 없으므로 실제 체인에서 토큰 검증 대상이다. permitAll만 보고 익명 공개라고 판단하지 않는다.
- 마이페이지·관리자 사용자는 별도 User DTO에서 포인트 cost를 읽는다. 서비스 반환형을 유지하고 컨트롤러에만 DTO 경계를 두면 이 내부 호출자 영향을 최소화한다.
- 공식 근거: [OWASP API3:2023](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)의 예방 지침은 객체 속성을 명시적으로 선택하고, 업무 요구에 필요한 최소 응답 구조와 응답 스키마 검증을 권고한다(2026-11-09 원문 확인). 이는 일반 보안 원칙이며 NGNG의 구체적인 필드 계약을 정의하지 않는다.
- 권고/판단: 사용자 사전 위임(공신력 있는 근거에 따른 권장 변경 진행)에 따라 포인트 전용 응답 DTO에서 user 전체를 제외한다. 현재 저장소 소비 근거상 불필요한 중첩 객체 제거가 적절하지만 외부 소비자가 없다는 보장은 아니다. 이 변경은 순수 계약 보존 리팩토링이 아닌 명시적인 보안 응답 축소다. 성능 효과는 측정하지 않았다.

## 범위와 제약

- 구현 허용 범위: PointController, 신규 `user/point/dto/PointHistoryResponseDTO.java`, 포인트 직렬화·컨트롤러·실제 체인 선택 테스트와 관련 명세/증빙. 기존 테스트의 user 존재 기대는 보안 계약에 맞춰 갱신한다.
- 유지할 최상위 필드: `id`, `beforeCost`, `addCost`, `cost`, `type`, `typeDetail`, `createdAt`, `updatedAt`. 기존 값·null·숫자 타입·날짜 표현, 목록 순서, 빈 목록, 이력 없는 GET의 기존 200/빈 본문을 보존한다. user를 null로 남기지 않고 키 자체를 제외한다.
- GET 상태200, 충전201, 결제200, check Boolean 및 오류 계약·요청 validation·인증/인가·잠금/트랜잭션·저장 계산은 그대로 둔다. 충전/결제 DTO 매핑은 서비스 반환 후 수행하고 user getter에 접근하지 않는다.
- 전역 User/PointHistory 어노테이션·ObjectMapper 설정, 서비스/repository, DB schema, 토큰 정책, 프런트 동작은 수정하지 않는다. 신규 의존성·스키마·대규모 구조 변경은 별도 승인 대상이다.
- `typeDetail`에 기존 사용자 이름이 포함되는 현상은 기존 표시 계약으로 유지한다. 모든 개인정보를 제거했다는 주장은 하지 않는다. 다른 API(신고 포함)의 User 직렬화는 별도 후보로 추적하며 자동 착수하지 않는다.

## 접근 및 위험

- 선택: 8개 속성만 가진 DTO로 명시적 매핑. 향후 User 필드 추가가 포인트 응답에 자동 반영되는 문제도 막는다.
- 대안: User.password 하나만 JsonIgnore로 제외하면 다른 개인정보와 미래 필드가 남고 전체 API 영향이 생긴다. PointHistory.user JsonIgnore는 모든 엔티티 직렬화 호출자에게 영향을 준다. 일부 User 필드를 중첩 DTO로 유지할 실사용 근거는 현재 없다.
- 실패/데이터 위험: DTO null 처리 누락은 이력 없는 GET을 500으로 바꿀 수 있다. timestamp 타입 변경은 날짜 계약을 바꿀 수 있다. user 미접근 검증과 전후 JSON 비교를 수행한다. 동시성·DB 쓰기 경로는 변경하지 않는다.
- 외부 소비자가 user에 의존하면 호환성이 깨질 수 있다. 확인되지 않은 소비자의 부재를 단정하지 않고 릴리스 시 축소 필드를 알리는 것이 후속 운영 조건이다.

## 검증 및 완료 조건

1. 변경 전: 기존 선택 테스트 기준선과 non-null 가상 민감 속성이 있는 fixture로 네 응답의 노출을 재현한다. 실제 사용자·DB·토큰을 사용하지 않는다. 원문 민감값을 로그/문서에 출력하지 않고 키 이름과 검증 결과만 남긴다.
2. `JacksonAutoConfiguration`이 생성한 실제 ObjectMapper를 `MappingJackson2HttpMessageConverter`에 명시적으로 연결한 격리 MVC 검증에서 단건/목록/충전/결제의 최상위 키 집합 8개를 정확히 확인하고 user 및 민감 중첩 키 부재를 검증한다. timestamp/non-null·null, 빈 목록/단건 null, 필드 값/순서 보존, user 접근 없는 매핑도 확인한다. 전후 비교는 제거한 user만 차이로 허용한다. `@EnableWebMvc` 기본 converter의 mapper와 Boot mapper를 혼동하지 않도록 실제 converter 연결을 확인한다. non-null createdAt/updatedAt fixture의 날짜 JSON tree를 전후 비교하고 null 속성은 키 포함 여부와 null 값을 모두 확인한다.
3. 실제 SecurityConfig+TokenFilter+AuthService 및 mock UserRepository/PointHistoryRepository 체인에서 유효 테스트 토큰의 USER/ADMIN/UNCONFIRMED_USER 3역할 × 4개 응답을 검증한다. 무토큰/불량토큰 × 4개 응답은 인증 거부 및 업무·저장소 무호출을 확인한다. 토큰 subject email에서 AuthService가 조회한 User의 ID가 이력 조회 또는 쓰기 잠금·저장에 전달되는지 검증한다. 보안 필터/인증 서비스를 통째로 mock한 테스트를 실제 인가 검증으로 표기하지 않는다. 실제 DB/운영 HTTP 검증과도 구분한다.
4. `NGNG-backend`에서 기존 의존성으로 격리 여부를 확인한 테스트 클래스만 `--tests`에 완전한 클래스명으로 각각 지정하여 실행한다. `com.ngng.api.user.point.*`처럼 외부 의존 integration까지 포함할 수 있는 광범위 선택을 금지한다. 기존 회귀 예: `./gradlew.bat --offline --no-daemon test --tests 'com.ngng.api.user.point.controller.PointControllerContractTest' --tests 'com.ngng.api.global.security.TokenFilterTest' --tests 'com.ngng.api.global.security.SecurityChainTest' --rerun-tasks`. RF-008 신규 테스트는 구현 후 실제 완전한 클래스명을 추가해 명령·선택 범위를 증빙에 기록한다. `assemble`과 관련 frontend 기존 회귀를 검토한다. 전체 test를 격리 확인 없이 실행하지 않는다.
5. 독립 리뷰: API 4개 누락 여부, user 제거 외 계약 변화, 민감 fixture 유출, 전역 설정/인증 변경 여부, 증빙 한계의 정확성을 검토한다. 계획 독립 리뷰에서 차단 결함 없음이 보고되었으며 mapper 명시 연결·날짜 JSON tree·null 키·실제 AuthService·역할/거부 교차 검증 계획을 보완했다. 구현 후 최종 독립 리뷰는 미실행이다.
6. 완료: 위 합의된 격리 기능 검증과 리뷰를 충족하고 원시 결과를 보존한다. 운영·실DB·브라우저·성능은 별도 잔여다. 성능 측정은 사용자 지시로 실행하지 않으며 개선을 주장하지 않는다.
- 롤백: 기준 커밋을 참조하여 RF-008의 DTO/controller/test 변경만 역패치한다. 사용자 변경 및 기존 작업을 덮어쓰는 reset은 금지한다. 롤백 시 노출 경계가 되돌아갈 수 있으므로 원인별 수정안을 먼저 검토한다.
