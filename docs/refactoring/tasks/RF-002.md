# RF-002: 관리자 사용자 페이지의 최신 포인트 일괄 조회

- 상태: **진행 — 최소 구현 및 오프라인 기능 테스트 15건 통과, 실제 MySQL 기능·동시 읽기·성능 검증 보류. RF-002 전체 미완료**
- 우선순위와 선정 이유: P1 성능·조회 경계 리팩토링. **사용자가 RF-001 다음 작업으로 RF-002를 지정하여 우선 선정했다.** RF-001의 DTO/Page 회귀 검증을 활용하면서 변경을 관리자 페이지 조회 한 경로로 제한할 수 있다. RF-020 등 P0 조사 후보의 위험이 해소됐다는 의미는 아니며 해당 작업을 함께 구현하지 않는다.
- 대상 저장소, 기준 커밋 및 관련 담당 흐름: 통합 저장소 `NGNG-backend`의 `GET /admin/users` → `UserService.findAll(Integer)` → 최신 포인트 조회. 명세 작성 당시 HEAD는 `ab77676ae968354c47408002926119e3f3843c69`였고, 구현 시작 HEAD는 RF-001이 반영된 `17adfc75e1315b4ad832a5114f36953837870e9f`다. 기존 로컬 환경·문서 미커밋 변경이 있어 HEAD만으로 재현할 수 없다. 변경 전 대상 원본과 작업 상태·설정 해시는 [재현 기록](../evidence/RF-002/README.md)에 보존했다.
- 실행 조건 및 사용자 지시: RF-001 완료 기록과 기존 Java/Gradle 의존성을 확인했다. 명세 확인 후 사용자가 구현을 지시했고 **성능 테스트(SQL 수·실행계획·지연 측정 포함)는 지금 실행하지 말고 후속 작업으로 기록**하도록 지정했다. 이에 성능 기준선 선행 조건은 이번 구현에서 유예한다. 격리 MySQL·fixture·외부 연동 차단은 실제 DB 검증의 조건으로 유지하며 확인 전 접속·쓰기하지 않는다. RF-016 전체 완료를 요구하지 않는다.

## 목표와 근거

관리자 페이지에 포함된 사용자 ID만 모아 각 사용자의 최신 포인트 이력을 일괄 조회하고 기존 사용자 Page에 매핑한다. API·DTO·페이지 순서와 최신 이력 선택 의미를 보존하고, 실제 SQL 수와 응답 지연을 변경 전후 같은 조건에서 검증한다.

아래 경로는 별도 표시가 없으면 `NGNG-backend/src/main/java/com/ngng/api/` 기준이다.

| 근거 | 변경 전 코드에서 정적으로 확인한 내용(원본은 재현 기록 참고) |
|---|---|
| `user/user/controller/AdminUserController.java:27-31` | GET `/admin/users`, page 기본값 0, 서비스의 Page를 200 응답으로 반환 |
| `user/user/service/UserService.java:53-63` | page 크기 5, userId ASC, visible=true 조회 후 사용자마다 `PointHistoryService.readCostByUser` 호출. 이 메서드와 서비스 클래스에는 Transactional 선언 없음 |
| `user/point/service/PointHistoryService.java:42-44`, `user/point/repository/PointHistoryRepository.java:15-16` | 사용자별 이력을 id DESC/LIMIT 1로 선택하고 없으면 null 반환 |

**변경 전 확인 사실:** N명 페이지에서 최신 이력 서비스/repository 호출이 N회 발생했다. RF-001 결과는 [기준선](../BASELINE.md)과 [RF-001](RF-001.md)에 선택 테스트 8건 통과로 기록되어 있다. 명세 작성 단계에서는 재실행하지 않았으며, 이번 구현에서는 운영 코드를 바꾸기 전 8건을 실제 재실행해 통과했다. 변경 후에는 비어 있지 않은 페이지 ID 목록을 일괄 조회 메서드에 전달한다. 실제 SQL 수는 미측정이다.

**가설·미측정:** 실제 최신 이력 SELECT 수, 전체 SQL 수, count 생략 여부, 연관 추가 로딩, DB 실행계획, p50/p95 및 처리량은 미측정이다. 전체 SQL을 단순히 N+1로 단정하지 않는다. 일괄 조회가 SQL 왕복을 줄일 가능성이 있으나 최대 5명 페이지에서 지연도 개선되는지는 실측이 필요하다. 현재 작업 트리의 OSIV·실제 DB 격리 수준·읽기 트랜잭션·캐시 상태 역시 측정 시 확인한다.

## 범위와 제약

구현 시 수정 허용 범위:

- `NGNG-backend/src/main/java/com/ngng/api/user/user/service/UserService.java`: `findAll(Integer)`만 일괄 조회 및 사용자 ID별 매핑으로 변경.
- `NGNG-backend/src/main/java/com/ngng/api/user/point/service/PointHistoryService.java`: 페이지 사용자 ID 목록에 대한 읽기 전용 일괄 조회 메서드 추가. 기존 단건 메서드와 쓰기 메서드는 유지.
- `NGNG-backend/src/main/java/com/ngng/api/user/point/repository/PointHistoryRepository.java`: 사용자별 최대 이력 ID를 선택하는 조회 추가. 기존 단건 최신 조회를 기준 비교 및 다른 호출자용으로 유지.
- `NGNG-backend/src/test/java/com/ngng/api/user/user/service/UserServiceTest.java`: 기존 결과 assertion을 보존하고 일괄 조회에 맞게 대역 입력을 조정·보강.
- `NGNG-backend/src/test/java/com/ngng/api/user/user/controller/AdminUserControllerContractTest.java`: 기존 계약 회귀 검증 유지·필요한 보강만 허용.
- 신규 `NGNG-backend/src/test/java/com/ngng/api/user/point/repository/PointHistoryRepositoryBatchTest.java`, `NGNG-backend/src/test/java/com/ngng/api/user/user/service/AdminUserPageQueryIntegrationTest.java`.
- 필요 시 위 테스트 전용 fixture/최소 JPA·MVC 구성·SQL 계측 보조 코드를 `NGNG-backend/src/test/java/com/ngng/api/user/user/support/` 안에 한정. 기존 Hibernate/JDBC/JUnit 기능만 사용.
- `docs/refactoring/`의 기준선·작업 결과·백로그·이 명세 및 변경 전 재현 기록 갱신.

범위 밖:

- 무인자 `UserService.findAll()`, 관리자 단건 상세, 일반 사용자 조회·마이페이지, 가입 시 초기 이력 생성, 충전/결제/잔액 정책과 동시 쓰기 제어.
- Controller/DTO/엔티티 필드·fetch 전략·UserRepository 페이지 쿼리·SecurityConfig/TokenFilter 수정, 전역 readOnly/트랜잭션/OSIV 변경, 캐시·인덱스 추가, 프런트·채팅 코드 변경.
- 기존 전체 SpringBootTest 복구와 외부 서비스 기동. 새로운 projection/DTO·공통 추상화가 반드시 필요하다고 판단되면 근거와 범위를 먼저 재검토한다.

호출자와 영향: 관리자 컨트롤러의 페이지 조회 및 프런트 관리자 사용자 목록이 직접 영향 대상이다. `PointHistoryService.readCostByUser`는 무인자 목록·상세·마이페이지·충전/결제에서도 사용하므로 기존 동작을 유지한다. 채팅 서버에 이번 메서드의 직접 호출은 없고 공유 데이터의 스키마·쓰기 의미를 바꾸지 않는다.

유지할 계약·규칙:

- GET `/admin/users`, page 기본값 0, 0부터 시작하는 페이지, size=5, userId ASC, visible=true, 200 및 Page JSON. Page의 content·number·size·totalElements·totalPages·pageable·sort 등 기존 메타데이터를 보존한다.
- DTO `userId/name/nickName/phoneNumber/email/accountBank/accountNumber/address/role/point`와 null 의미, role 구조, 사용자 순서 유지. 프런트가 현재 표시하지 않는 필드도 임의 제거하지 않는다.
- 사용자별 최신 이력은 **해당 사용자에게 속한 행 중 최대 point_id의 행**이다. 최대 잔액·최신 생성/수정 시각·전체 사용자 중 최대 ID가 아니다. 해당 행의 cost를 그대로 사용하고 합계·최댓값·기본 0원으로 바꾸지 않는다.
- 빈 페이지는 메타데이터를 가진 빈 Page를 반환하고 포인트 조회를 하지 않는다. 빈 ID 목록으로 `IN ()`을 실행하지 않는다.
- 이력이 없는 페이지 사용자는 현재 DTO 매핑에서 NPE가 발생한다. 이를 결함 후보로 유지·기록하고 사용자 제거, null point, 0원, 초기 이력 생성, 새 오류 응답으로 고치지 않는다. HTTP 오류 본문/상태는 현 기준선에서 관찰하며 NPE만으로 특정 HTTP 계약을 단정하지 않는다.
- 음수 페이지의 기존 예외 및 잘못된 페이지 문자열 바인딩을 유지한다. 정상 조회에서 사용자·이력·역할 쓰기 없음. ADMIN 인가·JWT/쿠키·요청/응답 인증 헤더 정책 유지.
- 트랜잭션·잠금·DB 격리 수준을 임의 추가하거나 바꾸지 않는다. 일괄화의 읽기 시점 차이는 아래 위험 항목에서 별도로 검증한다.

승인 필요한 변경: 신규 라이브러리/계측 도구 의존성, DB 스키마·인덱스·제약, 인증·인가, 포인트 이력 부재/잔액 등 비즈니스 규칙 및 API 동작, 대규모 구조 변경. 이 계획에는 포함하지 않는다. 격리 로컬 DB의 기존 스키마 생성 승인 이력은 새로운 스키마/운영 DB 변경 승인으로 확대하지 않는다.

## 접근 및 위험

1. **기준선·최소 환경 확보:** 기존 미커밋 변경을 보존하고 RF-001 선택 테스트/컴파일 결과를 다시 확인한다. 변경 전 소스 원본·환경 해시를 기록한다. 사용자 지시로 SQL·실행계획·지연 기준선과 성능 테스트는 유예하며 기존 test application.yml은 외부 자격 정보·DDL 갱신 설정 위험이 있으므로 로드하지 않는다. 실제 MySQL 기능 비교도 격리 DB를 확인한 뒤 수행한다.
2. **좁은 일괄 조회 추가:** 페이지의 사용자 ID 집합만 대상으로 각 user별 최대 id에 대응하는 PointHistory를 반환한다. 사용자별 MAX(id) 하위 쿼리를 선택해 기존 Hibernate의 JPQL 경로 해석을 오프라인으로 검사했다. 이는 MySQL 결과·실행계획·성능 적합성 검증을 대체하지 않는다. 전체 이력을 Java로 읽어 정렬하거나 사용자마다 조회를 반복하지 않는다.
3. **기존 Page에 대응:** 일괄 결과를 userId 키로 조회하고 원래 사용자 Page 순서대로 기존 DTO 매핑을 호출한다. DB 일괄 결과의 순서를 가정하지 않는다. 결과 누락을 getOrDefault(0) 등으로 숨기지 않는다. 빈 Page는 포인트 서비스/저장소 호출 전에 반환한다.
4. **회귀·실측·리뷰:** 단건 결과와 배치 결과, JSON/Page, 쓰기 없음, 이력 부재 결함 경로, 다른 단건 호출자 보존을 검증하고 동일 조건의 전후 측정 결과와 diff를 검토한다. 효과가 불분명하거나 악화되면 그 결과를 기록하고 성능 개선 완료로 처리하지 않는다.

대안 비교: 모든 사용자/이력을 join한 뒤 페이지를 다시 만드는 방식은 사용자 중복·count·정렬을 바꿀 위험이 커서 선택하지 않는다. 전역 batch-fetch나 fetch 전략 변경은 관련 없는 호출자에 영향을 주므로 제외한다. 페이지에 속한 최대 5개 ID만 별도 일괄 조회하면 기존 페이지 생성과 DTO 경계를 유지할 수 있다. 단, PointHistory.user·User.role의 eager 로딩으로 추가 SQL이 발생할 수 있으므로 repository 호출 1회만으로 개선을 증명하지 않는다.

RF-016과 환경 경계:

- 기존 로컬 작업 기록에는 격리 MySQL 8.0.35의 로컬 스키마 생성과 엔티티 validate 이력이 있지만 현재 가용성·fixture·외부 연결 차단을 증명하지 않는다. Docker/WSL의 과거 기동 제약도 현재 해소됐다고 가정하지 않는다.
- 이번 범위에 필요한 것은 사용자·역할·포인트 이력만의 결정적인 fixture, 최소 JPA/MVC 테스트 컨텍스트, 테스트 전용 JWT가 필요한 경우 합성 키, 외부 발송/Redis/ES/S3 빈 제외 또는 대역이다. 전체 서버·채팅·검색 구동을 선행 조건으로 넓히지 않는다.
- 테스트 접속값은 전용 환경 주입으로 받으며 허용한 격리 로컬 대상과 다르거나 누락되면 실패시킨다. 운영 자격값을 출력하거나 문서에 복사하지 않는다. `ddl-auto=validate`로 기존 스키마만 사용하고 운영 설정이나 기존 test YAML을 우회적으로 읽지 않도록 확인한다.
- 기존 의존성으로 필요한 격리를 만들 수 없거나 DB 대상·정리 범위가 불확실하면 미검증 상태를 기록한다. mock 통과만으로 RF-002를 완료 처리하지 않는다. 안전한 환경 준비의 범위 확대는 RF-016의 별도 명세로 정한다.

실패·동시성·데이터 위험:

- 기존 N회 포인트 조회와 새 1회 조회는 실행 시점이 다르다. 현재 메서드에는 명시적 트랜잭션이 없지만 실제 caller/OSIV/repository·DB 격리에 따라 관측 결과가 달라지므로 소스만으로 일관된 스냅샷을 보장한다고 주장하지 않는다.
- 동시 포인트 append가 없을 때 단건/일괄 결과는 동일해야 한다. 동시 갱신 시 기존 구현은 사용자마다 다른 시점의 최신 이력을 볼 수 있고 배치 쿼리는 한 statement의 관측 시점으로 모인다. 모든 interleaving의 잔액이 완전히 같다는 주장은 하지 않는다. 페이지 조회와 포인트 조회 사이에도 일관된 전체 스냅샷이 새로 보장되지는 않는다.
- 별도 연결의 append를 barrier로 제어해 포인트 조회 전/후 commit과 기존 사용자별 조회 사이 commit을 관찰한다. 각 결과가 해당 사용자에게 속한 관측 가능한 최대 ID의 행인지 기록한다. 테스트 편의를 위한 상위 Transactional이 기존 운영 경계를 덮지 않도록 한다. 수치 변화의 관찰 시점까지 엄격한 동일성이 요구되거나 더 강한 일관성이 필요하면 트랜잭션/스냅샷 정책을 별도로 결정하기 전 구현 완료로 처리하지 않는다.
- 이력 부재에서 기존 구현은 해당 사용자 매핑 중 예외로 종료한다. 일괄화 후 조회 순서·건수나 예외 stack/message는 달라질 수 있다. 사용자에게 노출되는 응답 변화를 확인하고 원치 않는 성공 응답·자동 데이터 보정으로 바꾸지 않는다.
- 일괄 쿼리의 집계·정렬/중간 결과 비용과 연관 로딩이 왕복 감소 효과를 상쇄할 수 있다. 기존 인덱스에서 실행계획·rows examined를 확인하며 인덱스 추가를 자동 대안으로 적용하지 않는다.
- 테스트는 합성 사용자·계좌·이력만 생성한다. cleanup은 기록한 테스트 소유 행만 대상으로 하고 전체 테이블 truncate, DB reset, 운영 자료 사용을 금지한다. SQL 로그에서 개인정보·인증값을 제외한다.
