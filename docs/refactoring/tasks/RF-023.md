## 목표와 근거

거래 단건 읽기 전에 요청자와 거래의 관계를 검사하는 최소 계획이다. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)는 최소 권한, 요청별 인가, 안전한 실패, 인가 테스트를 권고한다. [OWASP API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)는 객체 ID를 받는 API에서 사용자의 해당 객체·행위 권한을 확인하도록 권고한다(2026-11-10 열람). 이는 인가 추가의 근거이며 NGNG의 판매자 정의·관리자 업무·오류 코드를 정하는 근거는 아니다. 초기 제품 정책 제안과 후속 사용자 확정 사항은 아래 절에서 구분한다.

경로 약어: B=`NGNG-backend/src/main/java/com/ngng/api`, F=`NGNG-frontend/src/app`, C=`NGNG-chat-server/src/main/java/com/ngng/chat`.

## 사용자 확정 정책과 계약 경계

2026-11-10 후속 사용자 결정: 기록 seller/consumer만 허용하고 현재 product owner는 추가 허용하지 않는다. seller/consumer 중 어느 쪽 연관 또는 ID라도 불완전하면 거부한다. ADMIN 예외는 없으며 거래 부재의 기존 200 빈 DTO는 유지한다. 앞 절의 공식 자료는 일반 인가 권고이고, 이 구체 정책의 승인 근거는 사용자 결정이다. 초기 분석에서 미확정으로 남긴 권한 주체·불완전 거래·ADMIN·부재 응답을 아래와 같이 확정했다.

1. 인증된 DB 사용자 ID가 **거래에 기록된 seller 또는 consumer ID**와 같고 양쪽 당사자 연관 및 ID가 모두 완전한 경우에만 단건 상세를 허용한다. 비교는 non-null 영속 ID의 값 비교이며 두 null을 일치로 인정하지 않는다. 단건 서비스에서 DTO 변환 전에 검사한다.
2. USER/ADMIN/UNCONFIRMED_USER 모두 같은 관계 검사를 적용하며 **ADMIN 예외 없음**이 확정되었다. 현 역할 matcher에는 거래별 제한이 없으며 계좌확인 여부를 새 읽기 조건으로 만들지 않는다. 관리자라도 기록 당사자가 아니면 거부한다.
3. seller와 현재 product.user가 다르더라도 기록 seller/consumer만 허용하고 새 상품 owner만 일치하는 사용자는 거부한다. RF006 PUT의 현재 owner 기준을 복제하거나 seller OR owner OR consumer로 넓히지 않는다. 실제 불일치 데이터·소유권 이전 발생 여부는 미검증이지만 더 이상 단건 정책 선택의 차단사항은 아니다. RF021 요청 쓰기 정책과도 분리한다.
4. 정상 200 DTO 필드·값·null 표현을 유지한다. 인가 실패는 403과 개인정보 없는 응답 제안, 기존 인증 실패 401 유지. 사용자 결정에 따라 부재 거래는 기존 빈 DTO 200을 유지하며 404로 전환하지 않는다. 부재 조회에서도 인증은 요구한다. 잘못된 경로 타입의 기존 바인딩 실패는 회귀 확인한다.
5. 유효 토큰이나 DB user 없음/ID 없음은 허용하지 않는다(국소 401 제안). **seller 또는 consumer 어느 한쪽이라도 연관/ID가 없으면 다른 쪽이 요청자와 일치해도 거부한다.** 양쪽 ID가 모두 없는 경우에만 거부하는 조건으로 구현하면 안 된다. 불완전 거래 거부의 구체 오류 응답은 구현 명세에서 확정한다. product/category/thumbnail/status/collection 손상은 현 mapper 예외 가능성과 구분하고, 정상 당사자용 DTO를 임의 복구·축소하지 않는다. 제3자·불완전 당사자 거래는 손상 mapper 호출 전에 거부해야 한다.
6. 거래 status, 취소/완료, 상품 공개/판매중 여부만으로 읽기 권한을 확대하거나 축소하지 않는다. 보존기간·삭제 계정·관리자 대행·필드 마스킹·당사자별 필드 제한은 별도 정책이다.

## 범위와 접근 및 위험

- 향후 수정 후보: TransactionDetailsService 단건 read의 국소 인증/관계 검사와 새 단건 인가 테스트. 필요할 경우 controller의 오류 계약만 최소 조정. DTO 공유 변환기에 인증 의존성을 넣지 않는다. 메서드에 인가를 두어 직접 서비스 호출도 검사하고 인증 없는 과거 테스트 fixture는 새 정책에 맞춰 명시적으로 수정한다.
- 소스·설정·테스트·DB는 이번에 수정/실행하지 않는다. 신규 의존성·DB 스키마·인증 공통구조 변경 없음. SecurityConfig/TokenFilter/AuthService 전면 리팩토링, 목록/마이페이지/채팅/관리자 별도 조회, RF021 쓰기·RF041 주소, RF038 상태전이·RF004 동시성 재설계 제외.
- 거부 전에는 거래 확인에 필요한 읽기만 허용하고 DTO 매핑·개인정보 직렬화·save/delete/status setter·포인트/알림/외부 호출은 없어야 한다. readOnly 선언만으로 무쓰기 증빙을 대신하지 않는다. refresh fallback으로 필터가 발행하는 access 헤더는 기존 인증 동작이며 업무 무부작용과 구분한다.
- 외부 GET 소비자가 불명확하므로 성공 DTO를 바꾸지 않는다. 현재 owner 변경 경합·영속성/OSIV·실제 오류 직렬화는 대역 테스트만으로 보장할 수 없다. 성능 개선은 주장하지 않는다.
- 롤백은 본 작업의 변경 hunk/신규 테스트만 되돌리고 기준 HEAD 전체 reset으로 동시 작업을 덮어쓰지 않는다.

## 검증 및 완료 조건 — 향후 실행 계획

1. 변경 전 격리 fixture로 당사자/제3자 모두 같은 DTO를 읽는 현재 특성과 부재 200 빈 DTO를 보존. 고정 운영 ID를 쓰지 않는다. 기존 SpringBootTest의 DB 고정 ID·controller addFilters=false는 실제 chain 인가 근거가 아니다.
2. 서비스 테스트: 기록 seller/consumer/제3자/ADMIN 제3자, seller≠product.user, non-null 작은/큰 ID 및 같은 값 다른 Long 참조, 양쪽/한쪽 null 연관·ID, auth user 없음/ID 없음, 거래 부재, 손상 product·DTO 연관, 모든 거래 상태. 사용자 확정 정책으로 기대값을 고정하고 null/null 허용 금지 확인. 특히 seller ID 누락+consumer 일치 및 consumer ID 누락+seller 일치를 모두 거부하고, 현재 product owner만 일치해도 거부하는 기대값을 명시한다. 내부 직접 read도 검사. 거부 시 getter spy 등으로 DTO의 이름/전화 접근 미발생 및 writer/외부 상호작용 0 확인.
3. 필터 미포함 MVC는 경로/200 DTO 전체 구조·nullable address·오류 바인딩 검사로만 기록. 새 403과 부재 200의 민감정보 부재를 응답에서 확인. 실제 Boot 오류 본문을 standalone 결과와 혼동하지 않는다.
4. 실제 SecurityConfig/TokenFilter/JWT verifier/provider/AuthService/controller/service + 대역 repository의 최소 context: USER/ADMIN/UNCONFIRMED_USER × 기록 seller/consumer/제3자, 소유자 불일치, 누락·변조·만료 토큰/refresh fallback. 유효 토큰 subject→DB user 조회를 실제로 거치고 principal.userId를 채워 넣어 우회하지 않는다. 인증 거부는 거래 repository 미도달, 객체 거부는 DTO 개인정보 미반환·업무 무쓰기. 합성 key/명시 property, 운영 Boot scan·DB/Redis/ES·외부 client 금지.
5. RF006 상태 인가/RF004 생성·수락 선택 회귀와 마이페이지 DTO 계약을 확인한다. 합의 후 신규 `transaction.read` 테스트 묶음을 만들 경우 `./gradlew.bat test --offline --tests 'com.ngng.api.transaction.read.*'` 및 기존 선택 회귀, `compileTestJava`, `assemble`을 실행·기록한다. 현재 해당 신규 테스트는 없으며 명령 통과를 주장하지 않는다. 무차별 전체 통합 test/build 실행 금지.
6. git diff --check·문서/코드 독립 리뷰 및 실행 XML/로그/당시 소스/hash 보존. 완료 판정은 확정한 단건 정책·계약·필터 포함 검증에 한정한다. 실DB/HTTP·브라우저는 안전한 격리 환경 확보 후 별도 검증하며 mock 성공을 운영 검증으로 확대하지 않는다.

공통 BACKLOG·로그 갱신은 통합 담당자가 이 표와 연결한다. 이 담당은 공통 파일을 수정하지 않는다.

## 2026-11-10 승인 후 최소 구현·실행 결과

사용자가 기록 seller/consumer 한정 정책의 구현과 검증을 승인했다. 초기 분석의 문서 전용 범위는 당시 단계의 제한이다. 이번 운영 변경은 `TransactionDetailsService.readTransactionDetailsById`와 필요한 security import뿐이며 새 독립 테스트는 `transaction.read` 패키지에 작성했다. 생성자 인자는 기존 AuthService를 재사용해 변경하지 않았다. controller·공통 DTO·목록·관리자·상태 PUT·RF004 생성/수락 API·RF021 쓰기는 이 담당이 수정하지 않았다. 신규 의존성·스키마·실DB·성능 실행 없음. 공통 BACKLOG/로그는 통합 담당자가 갱신한다.

### 확정 오류 계약과 적용 순서

1. 직접 서비스 호출에서도 authenticated `CustomUserDetails` 및 nonblank email을 먼저 요구한다. 이후 **실제 AuthService가 JWT subject email로 DB 사용자를 조회**한다. 인증 구조 이상/DB 사용자 부재/DB 사용자 ID 없음은 국소401이며 거래 조회 전 중단한다. repository 장애는 catch하지 않아401/403으로 바꾸지 않는다.
2. 인증된 DB user의 non-null ID를 확보한 뒤 거래를 조회한다. 거래 부재는 기존 DTO.from(null)과 같은 **7개 필드 null의200 DTO**를 유지한다.
3. 존재 거래의 seller·consumer 양쪽 연관과 ID가 모두 완전하고 DB 사용자 ID와 어느 한쪽 ID가 값으로 같아야 한다. 그 외는 **403**, 이유는 식별자/개인정보 없는 고정 문구다. ADMIN 우회·현재 product.user 추가 허용 없음. DTO 변환 전 거부한다. 정상 DTO는 mapper를 그대로 사용하며 손상된 정상 당사자용 product/category 등을 임의 복구하거나403으로 숨기지 않는다.
4. 격리 MVC context에서 거부 응답 본문은 빈 문자열이다. 운영 Boot 오류 dispatch/프록시가 동일 본문을 만든다는 증명은 아니다. refresh fallback은 현 필터가 기존 access 헤더를 발행하므로 제3자403과 함께 헤더가 생길 수 있으며 업무 쓰기/추가 권한 허용과 구분한다.

### 보존·한계·후속 조건

- 공유 XML은 hostname을 redacted 처리하고 실패 compile console의 개인 로컬 경로 prefix를 `<workspace>/NGNG-backend/`로 정제했다. 정제 전 XML/console 원본은 Git 제외 `.local-runtime/rf023-results/implementation-20261110/`에 보존했다. baseline 전용 Java는 성공 후 실행 소스에서 제거하고 before 증빙에 보관해 after suite에 의도적인 skip/기존 취약동작 기대를 남기지 않았다. source/hash의 범위와 재실행 방법은 [증빙 README](../evidence/RF-023/README.md)를 따른다. 공유 자료의 실제 토큰형 문자열/개인 로컬 경로 검색에 일치 없음; JWT key는 공개 합성 fixture뿐이다.
- 실DB·Boot HTTP/브라우저·프록시·OSIV·실제 SQL/commit/rollback/손상행 존재·운영 피해/성능은 미실행이다. 안전한 격리 환경과 별도 범위 합의 후 인증 fixture/실제 오류 dispatch·외부 소비자를 검증한다. 현재 대역 통과를 통합/운영 완료로 확대하지 않는다.
- 기존 `TransactionDetailsServiceTest.readTransactionDetailsById`는 인증 없는 고정 DB ID 직접 호출이므로 새 승인 정책에서401이다. 이 낡은 전체 SpringBootTest는 실행/수정하지 않았다. 안전한 격리 DB로 재개할 때 기록 당사자의 합성 인증을 명시하고 실제 데이터 의존성을 제거해야 한다. 기존 controller 통합 테스트의 기록 당사자 일치도 실DB 미확인이다. 새 독립 테스트로 서비스 직접 호출의 새 계약을 검증했으며 기존 전체 suite 통과를 주장하지 않는다.
- 기존 실DB `TransactionDetailsServiceTest.updateTransactionStatus()`도75행에서 단건 read를 재호출한다. 이 테스트에는 인증이 있으므로 위 단독 read의 무인증401과 구분해야 한다. 재개 전 인증 주체가 거래의 기록 seller 또는 consumer와 일치하고 양쪽 당사자 ID가 완전한지 fixture를 확인한다. 현재 product owner만 일치하면 PUT은 기존 정책에 따라 허용될 수 있어도 이어지는 GET 서비스 호출은 승인된 읽기 정책에 따라403이다. 해당 실DB fixture의 실제 일치 여부는 미실행·미확인이고 테스트 소스는 변경하지 않았다.
