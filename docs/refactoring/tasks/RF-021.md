## 목표와 근거

정상 구매자의 요청과 상품 소유자의 처리 계약을 유지하면서, 요청자가 대상 객체에 해당 행위를 할 권리가 있는지 서버에서 확인하는 최소 계획을 세운다. 공식 권고 적용 위임은 제품 고유 정책을 임의로 확정하는 근거가 아니다.

[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)는 요청마다 권한 검사, 최소 권한, 안전한 실패와 인가 테스트를 권고한다. [OWASP API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)은 입력 객체 ID를 다루는 endpoint에서 인증 사용자가 해당 객체에 해당 동작을 할 권한을 확인하도록 권고한다. JWT와 body ID 비교만으로 모든 객체 관계를 검증할 수 없다는 점도 명시한다. 두 공식 자료를 2026-11-10 열람했다. 아래 역할 선택은 소스/UI에서 도출한 제안이며 OWASP가 NGNG 거래 정책을 정해 준 것으로 표현하지 않는다.

경로 약어: B=`NGNG-backend/src/main/java/com/ngng/api`, F=`NGNG-frontend/src/app`, C=`NGNG-chat-server/src/main/java/com/ngng/chat`. 행 번호 대신 현재 메서드를 식별한다.

| 근거 | 확인 사실 |

| F `chat/_api.ts`, `_hooks/usePrivateChatMessgae.ts` | PUT helper는 res.ok와 양수 정수 검사, hook await와 실패 전파를 수행. POST 요청 helper는 res.json만 반환하므로 새 403 JSON을 성공으로 처리할 가능성이 있음. 생성 오류 처리 최소 보완 계획 필요 |

직접 POST `/transaction`의 저장소 내 운영 호출은 controller이고 같은 create를 request.update 내부에서도 호출한다. 프런트/채팅 소스 검색에서 직접 생성 호출은 발견하지 못했으나 외부 소비자 부재를 입증하지 않는다. 실제 HTTP/프록시·DB 값·운영 피해·빈도는 미검증이다.

## 최소 인가 제안과 정책 경계

| 행위 | 최소 제안 | 근거·미확정 경계 |
|---|---|---|
| 요청 생성 | 실제 인증 user ID=body buyerId, 실제 상품 owner ID=body sellerId를 모두 검사한 뒤 저장. 저장할 buyer/seller는 검증한 서버 객체 사용. 불일치는 거부하고 조용히 교체하지 않음 | 정상 UI와 buyer/seller 필드 의미에 부합. 인증 사용자가 buyer라는 검사만으로 타인 seller 위조를 놓치지 않음 |
| 요청 수락·거절 | 잠근 상품의 **현재 owner**=인증 user. buyer·제3자·요청의 seller만 일치하는 사용자는 거부. 재수락/재거절 무쓰기 성공도 검사 뒤에만 허용 | 판매자 처리 UI, RF004 실제 생성 seller와 RF006 owner 기준을 따름. 과거 request.seller 불일치 데이터는 권한 근거로 쓰지 않으며 자동 보정하지 않음 |
| 직접 거래 생성 | **사용자 보류: API·기존 서비스 동작 유지, 인가 추가·비활성화·삭제 없음** | owner-only는 초기 검토안이며 승인 정책이 아니다. 유효 인증된 제3자가 임의 상품/buyerId로 거래를 생성할 수 있는 객체 인가 누락 위험이 남는다. 후속 사용자 재개 지시와 업무 정책 확정 전 변경하지 않음 |
| 역할 | 유효 인증 USER/ADMIN/UNCONFIRMED_USER 모두 같은 객체 관계 적용, ADMIN 제3자 우회 없음 | 현 transaction 역할 matcher 부재 및 RF006 비우회 유지. 계좌확인 사용자만 허용하는 새 역할 정책은 별도 |

인증 실패는 기존 필터 401 유지, 새 객체 인가 실패는 403 제안이다. 정상 응답·중복 요청 200/-1·기존 처리 404/409를 유지하며 타인 요청에 대한 200/409 반환은 인가 거부가 우선한다. 존재하지 않는 대상과 null/malformed 입력은 변경 전 특성을 확보하고 최소 오류 경계를 명시한 뒤 결정한다. null/null ID를 소유권 일치로 허용하지 않는다. 인증 토큰은 유효하나 DB user가 없으면 쓰기를 차단하며, 새로운 401 처리의 국소 적용 여부를 구현 명세에서 확정한다. 전역 예외 응답 재설계는 범위 밖이다.

본인 상품 구매 금지, price 양수/가격 일치, 판매중 조건, 거절 후 재요청, 탈퇴 사용자 처리, 기록 seller 불일치 데이터 정리, 직접 생성의 상대방 동의·요청 필수 정책은 별도 업무 결정이다. 인가 추가에 묶어서 바꾸지 않는다. 직접 생성은 사용자 보류로 남긴다. 요청 생성·수락·거절의 합의 범위는 검증 후 완료할 수 있으나 거래 생성 전체 객체 인가 해결이나 직접 경로 안전성을 선언하지 않는다.

## 범위와 접근

- 향후 최소 변경 후보: TransactionRequestService/create·update, 필요한 국소 인증 확인, 신규 transaction 인가 테스트. controller/DTO는 계약상 필요할 때만 변경. frontend 요청 생성 helper/hook/modal의 실패 전파에 한정한 보완은 테스트와 함께 적용 범위로 제안한다. 공통 AuthService·SecurityConfig·TokenFilter 전면 수정은 하지 않는다.
- 수락·거절은 RF004의 상품 scalar lock을 취득한 뒤 owner를 확인하고, **첫 setter/save 및 재수락 return보다 먼저** 거부한다. controller에서 권한 확인을 위해 상품/request 엔티티를 미리 로딩하면 stale 영속성 컨텍스트를 도입하므로 피한다. 상품 lock projection의 sellerId 활용 가능성을 검토하되 이후 entity owner와의 일관성도 확인한다.
- 요청 생성의 product owner 검증과 쓰기는 최소 tx 안에서 수행하는 안을 우선 검토한다. 동시 owner 변경/수락과의 직렬화가 필요하면 기존 상품 lock 사용의 효과·비용 및 모든 관련 writer 참여 여부를 검증한다. 이것만으로 동시 중복 요청을 해결했다고 주장하지 않는다. 신규 unique/스키마·중복 정책을 추가하지 않는다.
- 내부 수락은 TransactionRequestService.update에서 owner를 검사한 뒤 기존 details.create를 호출한다. 공유 TransactionDetailsService.create에 인가를 추가하거나 직접 endpoint 동작을 바꾸지 않는다. bypass 플래그/새 무인가 생성 메서드를 만들지 않는다. AuthService 조회에 따른 user 로딩이 상품/request 사전 로딩을 유발하는지 연관과 SQL 순서를 확인한다.
- 직접 생성은 기존 상품 lock·READ_COMMITTED·중복409를 유지하지만 객체 인가는 여전히 없다. 제3자의 직접 생성이 먼저 커밋되면 정당 판매자의 수락이 기존409로 충돌할 수 있다. RF004는 중복·정합성 보호이며 이 잔여 권한 우회를 해결하지 않는다. R21-정책에서 사용자 보류로 추적한다.
- 기존 READ_COMMITTED 단일 tx, 상품 PK lock 후 entity load, DTO 매핑 실패 rollback, 동일 요청 재수락 200 무쓰기, 다른 요청/기존 거래 409, 거절→후속 수락 허용, 직접 생성 시 forSale/요청 불변, RF009 commit 후 캐시 무효화 유지. 임의 active outer RR/사전 관리 객체 지원을 추가하지 않는다.
- RF006 상태 변경·RF023 상세 읽기·RF022 채팅·RF038 상태전이·RF035 가격/결제·RF004 신규 request writer 잔여·성능 측정은 자동 착수하지 않는다. 신규 의존성/DB 스키마/대규모 아키텍처 필요 시 별도 승인 및 범위 변경 전 멈춘다.

## 검증 및 완료 조건

1. **변경 전 특성/재현:** 소유자·구매자·제3자·ADMIN 제3자 합성 fixture로 실제 서비스가 현재 쓰기에 도달함을 검증한다. 성공 계약과 인가 결함 재현을 구분하고 후자의 현재 결과를 정상 보안 정책으로 고정하지 않는다. 정상 요청/중복 -1, 수락·거절·동일 재수락·409·404, 직접 201/DTO/Location과 status1/product owner seller를 고정한다.
2. **서비스 인가:** 승인된 요청 생성·수락·거절 각 행위 × USER/ADMIN/UNCONFIRMED_USER × owner/buyer/제3자, 별도 Long 객체의 같은 값, body buyer/seller/product 변조, request ID 치환, request.seller와 product.owner 불일치, 존재하지 않는 사용자/대상, null ID를 포함한다. 수락/거절·재수락·재거절 모두 인가 검사 후 진행되는지 확인한다. 내부 수락→기존 create 호출이 정당 owner에서 유지되는지 검증한다. 직접 생성에는 새 인가를 기대하지 않으며 기존201/중복409/forSale·요청 불변 계약을 회귀한다. 제3자 직접 생성 허용은 잔여 위험의 특성 확인이며 보안 통과로 집계하지 않는다.
3. **무쓰기:** 거부에서 save 미호출뿐 아니라 managed product.forSale/request.isAccepted/transaction 상태·개수/상대 요청과 캐시 invalidator 호출이 모두 불변인지 전후 snapshot과 interaction으로 검사한다. 검증용 mock은 DB flush/rollback 근거가 아니다. 인증 실패는 controller/service/repository 미도달을 별도로 검사한다.
4. **실제 필터 MockMvc:** RF006 TransactionStatusSecurityChainTest의 명시 bean 구조를 참고해 실제 SecurityConfig/TokenFilter/JWT provider/verifier/controller/service/AuthService를 연결하고 저장소만 대역화한다. 합성 키·email·JWT, 실제 body 바인딩과 200/201/Location/403/401/404/409를 확인한다. 유효 role별 객체 조합, missing/malformed/expired access·정상 refresh fallback·Authorization 재발급, JWT principal ID가 없고 email→DB ID를 사용함을 검증한다. addFilters=false 또는 @WithMockUser만으로 실필터 완료라 하지 않는다. Boot 전체 scan/운영 properties/외부 client/DB 연결 금지.
