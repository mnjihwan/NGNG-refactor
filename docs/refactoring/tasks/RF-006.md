# RF-006: 거래 상태 변경 Long 소유자 ID 값 비교

- 상태: 최소 구현·선택 회귀 완료, 독립 리뷰 완료 (2026-11-05)
- 우선순위: P0. 소유자 값이 같아도 Long 참조가 다르면 상태 변경이 거부되는 결함 경로 F03.
- 기준 HEAD: `2ef37de4ddb7a40e7b0b2e9c662c61d08b5b939a`. 분석 시작 `git status --short` 출력 없음(clean). 루트 AGENTS.md 적용, 하위 AGENTS.md 검색 결과 없음.
- 사용자 요청: RF-006만 진행, 작업별 검증·리뷰 후 merge. 공신력 있는 출처가 현 상황의 변경을 구체적으로 권고하면 추가 질의 없이 실행하도록 위임. 이는 역할·소유권 주체 변경의 포괄 승인이 아니다.

## 목표와 근거

`TransactionController.updateTransactionStatus`의 `PUT /transaction/{id}` → `TransactionDetailsService.updateTransactionStatus` → 거래 조회 → `AuthService.readAuthUser` → 상품 소유자/consumer ID 검사 → 상태 조회·setter → DTO 반환 순서다. `User.userId`는 `Long`이며 변경 전 기준 HEAD의 두 `!=`는 참조 비교였다. 저장은 기존 `@Transactional` dirty checking에 의존하며 명시 save는 없다.

- [Oracle JLS 17 §15.21.3](https://docs.oracle.com/javase/specs/jls/se17/html/jls-15.html#jls-15.21.3): 참조 비교는 같은 객체 여부를 검사한다.
- [Oracle Java 17 Long](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Long.html): value-based 클래스의 동등한 인스턴스는 상호교환 가능하게 취급하도록 명시한다. `equals`는 같은 long 값을 비교하며 `valueOf`는 -128..127을 캐시하고 범위 밖도 캐시할 수 있다.
- [Oracle Java 17 Objects.equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Objects.html#equals(java.lang.Object,java.lang.Object)): null을 포함한 동등성 비교 제공.

따라서 기존 상품 소유자 또는 구매자라는 코드의 조건을 유지하면서 **두 참조 비교만 `!Objects.equals`로 바꾸는 것**을 권고한다. 이것은 결함 수정으로 같은 값/다른 객체의 기존 401이 성공으로 바뀐다. 공식 문서는 역할 허용 범위·판매자 정의·상태 전이 정책을 정하지 않으므로 그 변경은 정당화하지 않는다. 실제 운영 발생 빈도·성능은 미측정이다.

## 호출·인가·캐싱 분석

- 판단 기준은 `transactionDetails.product.user.userId`와 `transactionDetails.consumer.userId`다. `transactionDetails.seller`로 대체하지 않는다. 두 판매자 정보가 다른 fixture로 기준을 고정한다.
- `/transaction/**`의 SecurityConfig 전용 역할 matcher는 없고 최종 permitAll에 걸리지만 TokenFilter skip 대상은 아니므로 정상 토큰이 필요하다. 서비스 자체 role 분기는 없다. USER/ADMIN/UNCONFIRMED_USER 소유자 모두 동일 비교를 거치고 제3자 ADMIN에도 우회권한이 없다. 기존 소유권 거부 401·예외 재포장도 유지한다.
- TokenFilter는 JWT email/role로 ID 없는 principal을 만들고 AuthService가 email로 UserRepository를 재조회한다. 토큰 역할 최신화는 별도 문제이며 변경하지 않는다. 해당 서비스/AuthService에 명시적 애플리케이션 캐시는 없다. 작은 boxed ID 캐시나 동일 영속성 컨텍스트의 객체 재사용이 결함을 가릴 수 있지만 운영의 객체 동일성은 이번 정적 분석에서 입증하지 않았다.
- 요청 DTO는 `{statusId: Long}`. 응답은 id/address/product/consumer/seller/status/price 및 기존 중첩 필드다. 상태 존재 조회·전이 제한 없음·DTO 매핑·트랜잭션 경계 유지.
- frontend `my_page/_api/api.ts:updateTransaction`은 `/api/transaction/{id}`에 PUT 후 200 JSON/실패 분기, `chat/_api.ts:updateTransactionStatus`는 `/transaction/{id}` PUT을 정의한다. 채팅 서버 검색에서 상태 변경 직접 호출은 발견하지 못했다. 실제 브라우저 호출·프록시 경로는 미검증, 타 저장소 변경 불필요.
- 기존 TransactionDetailsServiceTest는 SpringBootTest/고정 ID·email, TransactionControllerTest는 addFilters=false/고정 DB다. 이 테스트들은 별도 Long 참조와 실제 체인 소유권 회귀 근거가 아니다. RF-005 SecurityChainTest의 명시 bean·합성 JWT 최소 context 방식을 참고한다.

## 범위와 제약

- 운영 변경은 TransactionDetailsService의 두 비교와 필요한 JDK import만. 신규 RF-006 테스트 및 문서·증빙 허용. 신규 라이브러리·DB 스키마·설정·AuthService/SecurityConfig/TokenFilter·frontend 변경 없음.
- `&&` 순서 및 단락 평가 보존. Objects.equals의 null/null 참은 기존 참조 비교와 같으므로 별도 null 정책을 만들지 않는다. 유효한 영속 ID 기준 검증과 null fixture 특성 보존을 구분한다.
- RF-004 수락·생성/동시성/관리객체 stale flush 보류를 재개하지 않는다. RF-007/021, 역할 제한/ADMIN 우회, 탈퇴·상태 전이·거래 원자성·캐시 개선도 제외한다.

## 검증 및 완료 조건

1. 변경 전 독립 fixture로 같은 참조/다른 값은 기존 결과를 고정하고, 같은 값·다른 Long 참조의 판매자/구매자 401을 재현·보존한다. 테스트 한정 명시적 Long 생성 등으로 assertNotSame와 값 동등성을 확인한다(단순 1000L 또는 valueOf만으로 보장하지 않음).
2. 변경 후 서비스 단위: 판매자·구매자 성공, 제3자·ADMIN 제3자 거부, 작은 캐시 ID·큰 ID·서로 다른 객체, 현재 상품 소유자와 기록 seller 불일치, 두 비교의 단락 평가, 거부 시 상태 조회/변경 없음. null-ID 조합은 기존 결과 보존 확인으로만 사용한다.
3. 필터 미포함 MVC: 실제 controller/service·대역 repository/AuthService로 요청 statusId, 성공 200 JSON의 구조/값, 기존 401 및 잘못된 JSON/경로 바인딩 경계를 확인한다. 실제 필터 검증으로 표현하지 않는다.
4. 필터 포함 MVC: 실제 SecurityConfig/TokenFilter/JWT verifier/provider/TransactionController/TransactionDetailsService/AuthService와 대역 repository, 합성 키·명시 bean만 사용한다. USER/ADMIN/UNCONFIRMED_USER × 상품 소유자/구매자/제3자(9조합), 누락·잘못된 토큰 401 및 repository 미도달, 정상 refresh fallback/헤더를 확인한다. 소유권 fixture ID는 서로 별도 객체다. 필요 없는 Boot/application scan·운영 properties·외부 client·DB 연결을 만들지 않는다.
5. 선택 회귀, 전체 테스트 소스 컴파일, assemble, git diff --check 및 독립 리뷰. 구체 실행 명령/건수/XML/로그/환경·소스 hash는 실행 담당자가 증빙에 기록한다. 일반 `test`/`build`로 기존 DB 통합 테스트를 무차별 실행하지 않는다.
6. 완료는 최소 비교 수정과 선택 서비스/MVC/실제 필터 회귀 범위에 한정. mock 상태 변경은 실제 DB commit/rollback 근거가 아니다. merge는 사용자 요청 범위에서 부모 담당자가 최종 diff·증빙·리뷰 후 진행, push는 하지 않는다.

롤백은 RF-006 비교/import 및 신규 테스트의 해당 변경만 되돌린다. 기준 HEAD 전체 reset 등으로 다른 작업을 덮어쓰지 않는다.
