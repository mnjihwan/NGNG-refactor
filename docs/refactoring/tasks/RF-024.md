## 공식 근거와 공통 리뷰 반영 최소 구현 계획

2026-11-11 [OWASP API3:2023](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)의 쓰기 속성별 권한 검사, [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)의 요청별 서버 인가·안전한 거부·인가 테스트 권고를 확인했다. 이는 신고자/처리상태를 클라이언트 결정에 맡기지 않는 근거다. NGNG 신고 유형·운영자 대리신고·중복/자기신고 정책은 이 문서들이 정하지 않는다.

| 항목 | 최소 권고안 (아직 구현 안 함) | 계약/정책 경계 |
|---|---|---|
| 주체 | 서비스 저장 진입에서 유효 Authentication·CustomUserDetails·email을 확인하고 AuthService로 DB user/ID 확보. reporterId가 있으면 DB ID와 값 비교하고 불일치403. 저장은 DB ID 사용 | 호환 필드를 유지하되 ID 미제공은 서버 도출 허용 권고. ADMIN도 이 일반 신고 API에서 타인 대리신고 우회 없음. 대리신고 요구가 확인되면 별도 정책 결정 |
| 초기 상태 | 신규 report는 **서버에서 null(미처리)** 지정. 입력 생략/null 허용; true와 false는400으로 거부하여 처리상태 입력이 받아들여졌다는 오해 방지 | 조용히 무시하는 대안도 안전하나 위조 입력·오래된 클라이언트 오류를 명확히 하는 거부안 권고. 현재 정상 상품 UI는 값 생략이라 유지. 기존 false 테스트/외부 클라이언트는 의도적 계약 강화 영향 고지 |
| 역할·인증 | 기존 USER/ADMIN/UNCONFIRMED_USER에 동일한 본인 주체 규칙. 기존 access/refresh 경로 유지. 인증 없음/잘못된 principal/DB 사용자 부재401, 신원 불일치403 | 새 계좌인증·role 최신화·탈퇴/제재 제한 추가하지 않음. RF040 소유. 전역 AuthService/TokenFilter 리팩토링 없이 국소 검사 검토 |
| 구조 오류 | 현재 JSON 바인딩 오류 경계를 유지. 광범위 @Valid·새 대상 필수/비양수/404 정책은 이번 최소 범위에 추가하지 않음 | 기존 type 조회·대상 입력의 오류는 기준선으로 기록하되 정상 계약이라고 단정하지 않음. 기존 없는 type의 orElseThrow를 기존404라고 주장하지 않음 |
| 대상 정합성 | **이번 구현 범위 밖, 별도 후속**. 유형 표가 확정되면 상품 신고의 body.userId=실제 상품 owner, 메시지/방 관계 검사 등을 검토 | type1 UI 단서만으로 모든 유형을 상품 신고로 제한하지 않음. userId/productId/privateChatId의 기존 처리를 유지하는 잔여 위험을 명시하고 전체 대상 안전성을 주장하지 않음 |

이번 최소 검사 순서는 **인증/DB caller 확보→reporter 불일치403→isReport 비null400→기존 type 조회/생성 처리**다. 바인딩 가능한 JSON에서 reporter 위조와 isReport=true/false가 동시에 있으면403이며, 인증 실패는401이 우선한다. 서비스 검사 전에 @Valid가400을 반환하도록 추가하면 이 순서가 바뀌므로 도입하지 않는다. JSON 자체가 파싱 불가능한 경우는 별도 MVC 바인딩 오류이며 정상 DTO의 인가 우선순위와 혼동하지 않는다. 각 새 거부에서 report/penalty/product/image save·상태 변경·캐시 무효화·외부 업로드0이어야 한다. 애플리케이션이 repository에 전달하는 엔티티의 isReport=null을 검증하지만, **@DynamicInsert로 NULL 컬럼이 INSERT에서 생략되면 DB default가 적용될 수 있으므로 물리 NULL 저장은 미검증이며 보장하지 않는다.** 스키마/엔티티 insert 전략 변경으로 범위를 확대하지 않는다.

### 사용자/업무 담당의 결정이 필요한 경계

1. **유형별 대상 표:** 지원 reportType ID/의미와 productId/userId/privateChatId 필수·금지 조합. type1 상품 owner 검증은 권고하되 모든 유형에 확장하지 않는다. type3의 테스트는 업무 증거가 아니다.
2. **privateChatId 의미:** 메시지인지 방인지 확정 후 메시지→작성자→방→참여자/상품 관계를 조회할 신뢰 경로 결정. 메시지면 신고자 방 참여와 신고대상 작성자 일치, 방이면 상대방/상품 관계 검사가 후보다. backend에는 해당 매핑/조회 경계가 없으므로 채팅 ID를 그대로 수용한 채 전체 대상 검증 완료 선언 금지. 비활성화 또는 상품 신고만 허용하는 범위 축소도 업무 결정 없이 실행하지 않는다.
3. 자기신고·중복신고·삭제/숨김 상품·탈퇴 대상·과거 거래 상품 허용, 관리자 대리신고, 신고 내용 길이/필수·스팸 제한은 독립 업무 정책. 신고 요청만으로 상품 차단하는 현재 UI를 변경할지 역시 별도 결정이다.

2026-11-11 공통 리뷰로 **이번 구현 목표는 신고자 주체·초기 상태 입력 보호와 필요한 최소 UI 결과 처리로 확정**했다. 기존 body reporterId가 caller와 같은 요청은 허용하고 생략/null은 caller ID를 사용한다. 대상 유형 전체/privateChatId 의미·관계 인가는 별도 후속으로 남긴다. 공식 OWASP 원칙과 기존 사용자 위임에 근거한 이 기본 보호를 대상 정책 결정 때문에 막지는 않는다. 합의한 부분 범위는 검증·리뷰 뒤 완료할 수 있지만 현재는 구현 전이며, 이후에도 RF024 전체 대상 안전성 해결로 기록하지 않는다. 기존 오염 report/penalty 데이터 자동 수정·정리 없음.

## 후속 구현 범위·영향·롤백

- 계획상 최소 범위: ReportServiceImpl.save의 국소 주체/isReport 검증, AuthService의 email→DB caller 조회 재사용, 신고 전용 테스트, createReport/createImages/ReportModal 결과 처리. 새로운 대상 저장소 접근은 별도 후속이다. 신규 라이브러리·엔티티/스키마·원격 서비스 도입은 자동 승인하지 않는다.
- 201의 reportId·기존 JSON 필드/타입 및 정상 이미지 후속 순서는 유지. 응답 user/reporter 최소화는 RF044 담당이며 공유 mapper 수정 전 소유권을 조율한다. 실패는 성공 alert/닫기/이미지 요청을 막는다. 이미지 단계 실패는 이미 생성된 report를 재생성하도록 유도하지 않고 부분 성공을 알리는 안을 검토한다. 업로드 보상/멱등성 구현은 별도다.
- RF007 상품 PUT/DELETE, RF021 거래 요청, RF022 chat 인증/참여 정책 및 RF008 포인트 응답은 변경하지 않는다. 신고 이미지 별도 endpoint 인가·Penalty 요청 정합성·생성 후 응답 실패 원자성은 별도 추적 후보이며 자동 착수하지 않는다.
- 롤백은 향후 RF024 diff만 선택 복원. 전체 reset/기존 `.tmp` 삭제/자동 commit·push 없음. 이미 저장된 신고 상태의 데이터 복구는 코드 롤백과 별도이며 사용자 승인 없이는 수행하지 않는다.

### 최소 UI 결과 계약과 이미지 응답 근거

추가 정적 확인: `createImages`는 fetch Response를 반환하지 않고 `res.json()` 결과를 반환하는데 `createReport`는 그 결과의 `.ok`를 읽는다. 더구나 `ReportImageController.fileUpload`의 정상 반환은 JSON이 아닌 문자열 **`reportImages upload`**다. 따라서 단순히 기존 boolean false를 실패 표시로 바꾸면 실제 정상 이미지 HTTP 응답도 JSON 파싱 오류/undefined로 처리할 수 있다. 이 반환 계약 불일치를 함께 최소 보완한다. controller는 지원하지 않는 확장자도 건너뛰고200을 반환하므로 HTTP 성공을 모든 이미지의 영속 저장 증거로 표현하지 않는다. 이미지 저장/형식 정책 자체는 변경하지 않는다.

| 구분 | helper가 모달에 전달할 최소 결과 | 표시·후속 요청 규칙 |

| 생성 보호 규칙의 명확한 거부(401/403/400) | 생성 거부와 상태 코드 | 성공 alert/닫기/이미지 요청0. 오류를 알리고 사용자 수정·인증 확인 후 명시적 재시도 가능 |
| 생성201 + 유효 reportId + 이미지 없음 | 신고 접수 확인 | 기존 접수 성공 표시/닫기 유지 |
| 생성201 + 유효 reportId + 이미지 업로드2xx | 접수 확인과 이미지 요청 성공 | Response.ok/status로 판정, text 응답을 JSON으로 강제 파싱하지 않음. 정상 성공 흐름 유지하되 이미지별 영속 검증이라고 주장하지 않음 |
| 생성201 후 이미지 non-2xx | reportId를 보존한 신고 접수/이미지 실패 | 전체 신고 실패로 표시하거나 신고 POST 재전송을 유도하지 않음. 부분 접수 안내, 전체 재제출 차단. 업로드 재시도도 중복 가능성이 있어 자동 수행하지 않음 |
| 이미지 요청 중 응답 유실/네트워크 오류 | 신고 접수 확인 + 이미지 결과 불명 | 이미지 미저장이라고 단정하지 않음. reportId 보존·결과 확인 안내, 신고 재생성/이미지 자동 재전송0 |
| 생성 요청 중 응답 유실·5xx·201 body 파싱/ID 검증 실패 | 생성 결과 불명(201 수신은 접수 성공 응답 수신 사실도 유지) | 저장 실패를 확정하지 않음. 이미지 요청0, 접수 여부 확인 안내, 자동·무심한 재제출 차단. 멱등성/확인 endpoint 새 도입 없음 |

구체적 TypeScript 결과 타입은 구현 시 작게 정하되 단일 boolean이나 일반 catch로 이 상태들을 합치지 않는다. 생성이 확인된 뒤 이미지 실패 또는 결과 불명이면 동일 모달의 전체 신고 제출을 막아 새 report가 생성되지 않도록 한다. 새 모달/새 세션까지 서버 중복 방지를 보장하는 것은 아니며 서버 멱등성은 별도다. refresh 헤더 소비는 두 응답 단계 모두 유지한다.

## 2026-11-11 승인 최소 구현·선택 검증 결과

**합의한 신고자 신원·초기 상태 입력 보호와 필요한 프런트 결과 처리의 구현·선택 검증·공통 독립 최종 리뷰를 완료했다.** 합의 범위의 P0/P1/P2 차단 결함은 없으며 유형별 대상 정합성, privateChatId 의미·관계 인가, 물리 DB 및 브라우저 검증은 남는다. 이 절은 위 최초 분석/구현 전 서술보다 최신이다.

- `ReportServiceImpl.save`가 실제 Authentication의 CustomUserDetails/email을 먼저 검증하고, 기존 AuthService로 email에 대응하는 DB user와 non-null ID를 얻는다. body reporterId 생략/null은 caller ID, 동일 ID는 허용, 타인 ID는403이다. principal 안의 ID는 신원으로 사용하지 않는다. 인증 오류는401이며 DB 자체 장애는 인증 오류로 감추지 않는다.
- 이어 isReport가 null이 아니면 true/false 모두400이다. 검사 순서는 인증/DB caller→reporter403→state400→기존 type 조회·저장이다. repository에 보내는 새 엔티티의 상태는 명시적 null이다. `@DynamicInsert`와 실제 default를 확인하지 않았으므로 물리 NULL 저장을 보장하지 않는다.
- USER/ADMIN/UNCONFIRMED_USER에 같은 규칙을 적용한다. ADMIN 대리 POST 예외는 없다. 기존 ADMIN PATCH와 Penalty 처리 흐름·대상 userId/productId/privateChatId 처리 및 DTO/entity/전역 인증 설정은 바꾸지 않았다. 새 필수/404·유형별 대상 정책을 추가하지 않았다.
- `createReport`는 접수 확인/거부/결과 불명과 생성 후 사진 실패/사진 결과 불명을 구분한다. 기존 정상201 JSON과 기존 helper가 허용하던200의 유효 JSON reportId를 수용한다. 생성 network·5xx·불명확 JSON/ID·200 false는 성공으로 표시하지 않고 재제출을 막는다.400/401/403 등 명시4xx 생성 거부는 입력/로그인 확인 안내 후 의도적 재시도가 가능하다.
- 이미지 helper는 실제200 plain-text `reportImages upload`와 JSON 문자열 모두에서 Response.ok를 사용한다. 생성이 확인된 뒤 이미지 실패/결과 불명은 신고 번호를 유지해 안내하며 전체 신고를 재생성하지 않는다. API 응답 전체를 받기 전의 network·5xx는 저장 여부 불명으로 취급한다. 제출 중 연속 클릭과 결과 불명/부분 성공 후 같은 모달의 재제출을 ref와 disabled로 차단한다. 서버 멱등성·모달을 닫고 다시 여는 사용자의 중복까지 보장하지 않는다. 이미지200은 HTTP 성공이며 개별 파일의 물리 저장 증명이 아니다.

34개 artifact의 원본은 새 전용 `.tmp/rf024-implementation-20261111-originals/`에 보존했다. 기존 사용자 `.tmp` 파일은 열거나 고치지 않았다. 공유본의 home/hostname/compact JWT header 패턴만 치환했고 [SHA256 manifest](../evidence/RF-024/ARTIFACT_SHA256.tsv)는 원본·공유본 hash와 변환/원본 보존 여부를 구분한다. 합성 test key/email source는 재현 근거이며 운영 비밀을 사용·수집하지 않았다. 최종 원본·공유hash34개 불일치0, XML5개 strict parse 성공, home/비치환hostname/실제 compactJWT header 패턴 재검색0이다. 치환 점검 중 XML attribute에 부적합한 마커와 넓은 패턴의 Java package 오탐을 발견해 원본에서 안전한 마커/정확한 header 패턴으로 다시 생성했다.
