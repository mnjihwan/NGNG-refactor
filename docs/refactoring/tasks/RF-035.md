## 범위와 제약

- 초기 분석 단계의 허용 범위는 본 명세와 `evidence/RF-035/README.md` 두 문서였다. 이후 사용자 승인으로 아래 최소 운영 구현·필요 테스트/증빙까지 확장했다. 공통 BACKLOG/로그 상태 연결은 통합 담당이 수행한다. DB 접속·서비스 구동·성능·commit/push 없음.
- 향후 최소 구현 후보: PointHistoryService/DTO/controller 및 필요한 거래 repository 읽기와 해당 선택 테스트, 명확한 결제 실패 UI. 구체 허용 범위는 아래 정책 결정 후 확정한다. 신규 의존성·스키마·대규모 아키텍처 변경은 별도 승인한다.
- 유지: RF003 양수·동액 잔액 허용·부족 무쓰기·overflow 거부, RF008 8필드 응답과 성공 method/URL/status, RF004 수락 계약, RF021/023 확정 인가. 새 오류/추가 전제는 기능·정책 변경임을 명시한다. 무료 충전을 폐지하거나 결제 gateway를 새로 붙이는 결정을 보안 일반 위임만으로 내리지 않는다.
- 범위 밖: RF036 멱등성 키/보존, RF037 결제·상태 commit/복구, RF038 전체 전이, RF021 보류 직접 생성, 정산/환불/과거 잔액 보정·신규 가격 상한·통화/수수료 정책. 관련 위험을 숨기지 않되 자동 착수하지 않는다.

## 접근 및 위험

### 초기 선택안과 결정 경계 — 검토 이력, 현재 구현 조건 아님

사용자의 기존 보안 개선 위임에 따라 서버에서 관계·금액을 재검증하고 변조 입력을 거부하는 방향은 권고할 수 있다. 그러나 **어느 가격이 계약 가격인지, 무료 충전이 상품인지, 수락 없는 직접 거래를 허용하는지**는 보안 문헌이 결정할 업무 요구가 아니다. RF003의 양수 승인도 이 결정을 포함하지 않았다.

### 후속 사용자 확정 정책 — 위 초기 선택안에 우선

사용자는 판매자 수락 거래 가격을 서버 기준으로 하고 **기록된 구매자만 결제**, 클라이언트 금액 불일치/거래 없음은 거부하며, **직접 POST로 생성된 거래도 결제를 허용**하도록 결정했다. 충전 외부 결제 인증은 별도 작업으로 분리하고 기존 양수 충전을 유지한다. 따라서 수락 요청 존재를 모든 결제의 필수 조건으로 구현하거나 직접 거래 결제를 차단하면 승인 정책 위반이다. 권고표의 수락 필수 A안은 채택되지 않았다.

확정 구현 범위는 상품에 연결된 유일한 거래의 `TransactionDetails.price`를 권위 값으로 읽고, non-null 기록 consumer ID와 실제 인증 DB user ID를 대조하며, 양수 확정가와 body paymentCost가 일치할 때 기존 잔액 검사를 거치는 것이다. 수락 경로에서는 이 price가 판매자 수락가를 복사한 값이고 직접 생성 경로에서는 요청 body price를 저장한 값이다. 없거나 다수인 거래·불완전 buyer·유효하지 않은 가격은 무쓰기 거부한다. **RF035에서는 accepted request 존재, seller 완전성/현재 owner 일치, forSale, 상태1을 추가 결제 전제로 삼지 않는다.** 상태 전제는 별도 RF038 정책으로 다루며 본 명세에서 임의로 확대하지 않는다. ADMIN도 기록 buyer와 일치해야 하며 대납 우회가 없다.

### 고정 오류 계약과 검사 순서

아래 검사 순서는 서비스 내부 순서다. HTTP에서는 기존 TokenFilter가 MVC 바인딩/서비스보다 먼저 인증하므로 잘못된 body와 인증 실패가 함께 있으면 기존 필터401이 선행한다.

운영 `src/main`의 `ExceptionHandler|ControllerAdvice` 검색 결과 관리자 controller의 BadRequestException handler 두 곳만 확인했고 points용 공통 handler는 없다. 기존 PointHistoryService의 `ResponseStatusException`을 그대로 사용하며 새 전역 handler/에러 DTO는 도입하지 않는다. 성공은 기존200/8필드, 충전201 및 check Boolean 계약을 유지한다. 실패 reason은 ID/가격/당사자 등 민감값 없는 고정 문구로 한다. 실제 Boot 오류 dispatch 본문은 별도 검증 대상으로, standalone 빈 본문을 운영 본문과 동일하다고 주장하지 않는다.

|---|---|

프런트 `paymentProduct`는 이미 !res.ok에서 throw하고 BuyProductDetails는 결제 실패 시 별도 상태 PUT을 호출하지 않는다. 따라서 새400/401/403/404/409도 성공으로 오인하지 않아야 한다. 각 실패 status에 대해 이 계약을 회귀 검증하고, 고정 generic 알림 및 access header 처리도 유지한다. 새로운 실패를 200 성공 객체로 감싸지 않는다. check가 true여도 payment 실패 가능함은 기존 계약이다.

현재 엔티티에는 생성 출처/수락 request FK가 없다. true 수락 요청의 상품·buyer·seller·price를 대조하면 정합성 단서는 얻지만, 요청 부재를 곧 직접 생성으로 확정할 수 없다(삭제/오염된 수락 이력도 가능). 그러므로 “수락 거래만 엄격 검증하고 직접 거래는 예외”라는 조건부 정책은 현재 데이터로 확실히 구분할 수 없으며 이를 추정으로 구현하지 않는다. 출처 컬럼/수락 링크 도입은 스키마 승인과 기존 데이터 처리 정책이 필요한 별도 작업이다.

**잔여 위험은 명시적으로 수용된 범위 제한이지 안전성 입증이 아니다.** 직접 POST는 RF021 인가 보류 상태라 인증된 사용자가 buyer/price를 지정하는 경로가 남는다. 서버가 저장값을 재조회해도 그 값의 판매자 승인·생성 주체·가격 정당성이 보장되지 않는다. 기록 buyer 본인만 잔액을 차감하게 제한해도 공격자가 본인을 buyer로 저가 거래를 선점하거나 타인 buyer의 거래를 오염시키는 가능성은 남는다. 실제 피해는 미재현이며 정상 거래 방해·잘못된 금액 결제 가능성을 제거했다고 주장할 수 없다. 직접 생성 인가·가격 확정 정책의 재개는 별도 사용자 지시가 필요하다.

양수 충전 유지도 외부 입금/승인을 검증한다는 뜻이 아니다. 실제 가치를 갖는 포인트로 사용한다면 임의 적립 위험이 유지된다. RF035 완료는 저장된 거래 가격과 본인 구매자 대조의 제한된 개선만 뜻하며 RF036 중복 차감·RF037 상태 원자성·RF038 상태 전제·직접 생성 권한·충전의 실결제 증명까지 보장하지 않는다.

### 동시성·실패·롤백

현재 사용자 잠금만으로 수락/거래 가격 변경과 결제를 직렬화하지 못한다. 구현 순서는 **입력·인증 검사→기존 상품 PK scalar lock(`lockTransactionProduct`)→해당 상품의 거래 ID/consumer_id/price만 native scalar current locking read(`FOR UPDATE`, 목록 반환)→0/복수·buyer/price 검증→기존 user/latest point locks→이력 INSERT**로 고정하고 동일 PointHistoryService write transaction 안에서 수행한다. 상품 lock projection의 sellerId는 인가 조건으로 사용하지 않는다. 거래 조회는 JPA entity eager graph 또는 이전 RR snapshot/영속 컨텍스트 객체를 재사용하지 않는다. 캐시/프런트 DTO/사전 check를 최종 권위로 사용하지 않는다.

RF004의 상품→거래 생성 순서를 존중한다. RF038의 상태 writer와 RF037 결합 시 같은 잠금 순서를 다시 대조해야 하며 다른 상품 writer/사용자 삭제·eager FK 및 DB 교착은 실제 DB에서 미증명이다. 상품 lock을 먼저 잡고 거래 행까지 잠그더라도 모든 외부 writer의 순서·범위가 자동으로 보장되지 않는다. RF035는 상태를 검사/변경하지 않으며 취소와 결제 경쟁에 대한 업무 일관성은 RF038/037 잔여다. 순서 문서나 mock InOrder 성공만으로 물리 serialization/교착 부재를 주장하지 않는다.

단일 결제 저장 실패는 transaction rollback을 확인해야 하며 Mockito save 실패만으로 commit/rollback을 입증하지 않는다. 성공 응답 유실·동일 요청 반복은 RF036, 차감 commit 후 별도 PUT 실패는 RF037 소유다. RF035만 배포하면 올바른 금액의 반복 차감과 상태 불일치가 남으므로 전체 결제 안전 완료로 표시하지 않는다. 기존 오염 이력은 설명문 추측으로 환불/복구하지 않는다.
