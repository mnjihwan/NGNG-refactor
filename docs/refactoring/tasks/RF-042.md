# RF-042: 탈퇴 요청의 본인 객체 인가

- 상태: 합의 객체 인가 범위의 최소 구현·선택 격리 검증·독립 최종 리뷰 완료 — 2026-11-10 before5/after214 통과·assemble 성공. 실DB·운영 연동 미검증.
- 우선순위: P0 / 1A. 유효 인증 이후 body id로 타인 visible을 변경하는 경로.
- 대상: NGNG-backend DropOutService; frontend·관리자 호출 및 인증 체인 영향 분석.
- 기준 HEAD: `e417eaf7d476a639413414ff8f4423b89cc88e66`. 시작 작업트리는 ConfirmService.java 수정, confirmation 테스트 디렉터리 및 RF-020/021/022/023/041 명세·증빙 untracked 상태였다. 공유 변경을 보존하며 이 명세와 RF-042 증빙 README만 작성한다.
- 확인 지침: 루트 AGENTS.md, 운영 README, BACKLOG, BACKLOG_REASSESSMENT_2026-11-10.md, TEMPLATE, RF-020/041. `rg --files -g AGENTS.md`에서 하위 지침은 발견되지 않았다.
- 위임 이력: 최초에는 문서 두 개의 계획만 작성했다. 후속 구현 위임에서 DropOutService와 전용 테스트·이 명세/증빙으로 범위를 확정했다. 공통 BACKLOG/LOG·다른 RF·스키마·의존성·실DB는 변경/실행하지 않는다.

## 목표와 근거

경로 약어 B=`NGNG-backend/src/main/java/com/ngng/api`, F=`NGNG-frontend/src`.

1. `B/user/user/controller/DropOutController`는 `DELETE /dropout`, JSON `{id: Long}`를 DropOutService.dropOut에 전달한다. 필수 refresh 쿠키 인자는 없다. 성공204 빈 body, fail DTO면400 빈 body이나 현재 service는 success만 반환한다. null id의 repository 오류, 미존재 id의 UsernameNotFoundException은 통제된404 계약이 아니다. 실제 servlet 오류 응답은 미실행으로 확정하지 않는다.
2. `DropOutService.dropOut`은 `findById(request.id())` 후 `User.changeVisible()`만 호출한다. `@Transactional` dirty checking이며 save/물리 삭제/거래·잔액·상품·채팅 검사/토큰 폐기는 없다. `User.changeVisible`은 `visible = !visible`이므로 true→false, false→true이며 nullable Boolean이 null이면 unboxing 오류다. 반복 요청의 재활성화는 관찰된 코드 동작이지 승인된 사업 정책이라고 단정하지 않는다.
3. `SecurityConfig`에서 dropout은 anyRequest permitAll이지만 `TokenFilter.shouldNotFilter`에 포함되지 않는다. access 검증 또는 refresh fallback이 먼저 필요하며 유효하지 않으면401이다. USER/UNCONFIRMED_USER/ADMIN 모두 도달하고 별도 role allowlist는 없다. 필터는 알려지지 않은 nonblank role도 코드상 허용한다. 따라서 비인증 공개라고 표현하지 않는다.
4. TokenFilter는 서명·type·subject/role/exp를 검사하고 email/role만 가진 ID 없는 User를 principal로 만든다. AuthService.readAuthUser는 이 email로 `UserRepository.findUserByEmail`을 조회한다. repository에는 visible 조건이 없고 AuthService 자체는 principal null/type 방어가 없다. principal.userId와 요청 id 직접 비교는 정상 호출도 막으므로 사용하지 않는다.
5. `CustomUserDetails.isEnabled`는 visible을 반환하고 LoginFilter는 로그인 성공 처리에서 이를 검사한다. 반면 TokenFilter는 DB visible/role 최신화나 isEnabled를 검사하지 않고 기존 access 또는 refresh claim으로 인증한다. 그러므로 탈퇴 후 같은 유효 토큰으로 반복 dropout에 도달해 재활성화할 수 있는 정적 경로가 있다. 운영 재현·피해는 확인하지 않았다. 서버 토큰 폐기·최신화는 RF-040이며 이 작업의 객체 인가와 별개다.
6. frontend 전체에서 dropout/drop-out/탈퇴/withdraw 검색 결과 직접 탈퇴 UI·호출자는 발견하지 못했다. 부재를 외부 소비자 부재로 단정하지 않는다. 기존 `UserControllerTest.dropOut`이 body id=1로 호출하지만 addFilters=false 및 고정 email/실제 DB 의존으로 실제 인가 증거가 아니다.
7. 관리자 실제 업무 경로는 F `app/admin/users/page.tsx:handleDelete`의 DELETE `/api/admin/users/{userId}` → next.config.mjs rewrite → `AdminUserController.delete` → `UserService.delete`다. `/admin/**`에 ADMIN 제한이 있고 service는 `setVisible(false)` 및 save로200 ID를 반환한다. DropOutService를 호출하지 않으므로 dropout에 ADMIN 타인 우회를 추가할 근거가 아니다. 프런트 관리자 삭제는 응답 상태 확인 없이 목록을 재조회하며 이 UI는 변경 범위 밖이다.

[OWASP API1:2023 BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)를 2026-11-10 확인했다. 클라이언트 ID로 객체를 조작하는 각 함수에서 주체의 해당 객체·작업 권한을 검사하고 회귀 테스트를 두라는 원칙을 적용한다. OWASP가 NGNG 사업 정책을 정하지 않으며 ID 비교만으로 모든 BOLA를 해결한다는 뜻도 아니다. 이 객체가 사용자 자신의 행이고 타인 사용자 삭제는 별도 관리자 API라는 근거로 **이 endpoint에서는 DB로 해석한 본인 ID만 허용**을 최소안으로 정한다. ADMIN도 여기서는 본인만 허용한다.

## 범위와 제약

- 구현 범위: DropOutService.dropOut 시작 부분의 좁은 guard 및 AuthService 주입. 탈퇴 전용 unit/실제 chain 테스트만 추가했다.
- 유지: DELETE/body id, 본인 정상204 빈 body, existing transaction 및 visible 토글, USER/UNCONFIRMED_USER/ADMIN 본인 접근, refresh 쿠키 없는 유효 access 요청. 새 역할 제한이나 거래·잔액 선행 조건은 추가하지 않는다.
- 새 거부: 타인·null id·DB 주체 해석 실패는 대상 조회 이전403. 기존 필터 인증 실패401 및 malformed/missing body의 MVC400 유지.
- 제외: RF-020 계좌/역할/대상 토큰 발급, RF-041 주소, RF-040 토큰 폐기·visible/role 최신화, 멱등 탈퇴·재활성화 정책, 관리자 API/UI, 거래·잔액 정산/상품·채팅 정리, 이메일 변경 정책, 전역 AuthService/인가 개편, 성능.
- 반복 visible을 false로 고정하거나 이미 탈퇴한 본인을 차단하는 것은 별도 동작 변경이므로 이 작업에서 자동 수행하지 않는다. 소유권 보호 완료가 탈퇴 수명 전체의 안전성 완료를 뜻하지 않는다.
- 신규 의존성·스키마·대규모 아키텍처 변경 없음. 추가 정책은 근거 조사와 범위 합의 후 별도 작업이다.

## 접근 및 위험

1. 후속 구현 전 현재 소스/동일 합성 fixture의 before 기준선과 타인 mutation 후보를 격리 재현하고 raw를 보존한다. 본 문서는 재현 통과 기록이 아니다.
2. service 진입 시 authentication 존재/authenticated/non-anonymous, CustomUserDetails 및 내부 user/nonblank email을 확인한 뒤 AuthService로 caller를 조회한다. caller/caller ID/request id가 모두 non-null이고 Long 값이 같아야 허용한다. 직접 null request도 통제된403으로 방어하되 HTTP body 파싱 계약은 유지한다.
3. 실패는 좁은 ResponseStatusException(FORBIDDEN) 등 기존 RF-007 선례로 연결한다. 대상 findById 이전에 거부하며 존재하는 타인·없는 타인에 동일 응답을 준다. DB 장애 등 일반 예외까지403으로 삼키지 않는다. 통과 후 기존 findById→changeVisible→success 순서를 유지한다.
4. 거부 전후 caller/target entity 상태, target 조회 미호출 및 mutation 미호출을 확인한다. save 미호출만으로 dirty checking 무쓰기를 입증했다고 하지 않는다. 역할·계좌·주소·관련 거래 상태도 변하지 않아야 한다.
5. 서비스 자체 토큰 발급은 없으나 refresh fallback은 service 전에 호출자 access Authorization을 설정할 수 있다. fallback 거부403에서는 caller 기존 role access만 허용하고 새 refresh Set-Cookie/대상 토큰은 없어야 한다. 유효 access 거부에는 새 Authorization도 없어야 한다.
6. 기존 토큰으로 본인 반복 요청의 토글을 보존한다. DB visible false를 이번 guard에서 새로 차단하지 않는다. 동시 토글의 lost update, nullable visible, 진행 거래/잔액 정책은 별도 후보이며 인가 guard만으로 해결했다고 주장하지 않는다.
