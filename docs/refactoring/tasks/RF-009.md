# RF-009: 상품 판매상태·삭제·끌올 변경의 상세 캐시 무효화

- 상태: 합의한 정상 커밋 후 상품 무효화 기능의 최소 구현·격리 선택 검증·독립 코드/증빙 리뷰 완료 (2026-11-10). 문서 정합 최종 검토 완료. 강한 최신성/복구·운영 통합은 미해결/미검증이다.
- 우선순위: P1. 상품 변경 후 상세 응답에 과거 forSale/visible/refreshedAt이 남는 정합성 후보(F04).
- 대상: NGNG-backend. 기준 HEAD `6438b969e3901d14bdd519c16de26c44d51ba68a`; 분석 시작 `git status --short` 출력 없음. 루트 AGENTS.md만 검색됨.
- 담당 흐름: 분석·계획 → 최소 구현·격리 검증 → 독립 리뷰. 공식 근거로 권장되는 변경은 선행 사용자 위임에 따라 제안하되, 자료가 정하지 않는 업무 정책·환경 사용 승인을 구분한다. 성능 측정은 유예한다.

## 목표와 근거

### 현재 소스에서 확인한 사실

| 조회/쓰기 경계 | 현재 동작·호출자 | RF-009 영향 |

`RedisCacheConfig`는 Lettuce, String 키, GenericJackson2Json 값, 30분 TTL을 설정하며 transactionAware·오류 처리·캐시 전역 잠금은 설정하지 않는다. main에서 사용자 정의 CacheErrorHandler/CachingConfigurer는 발견하지 못했다. 현재 조회 캐시는 위 하나이며 목록/검색에 같은 annotation이 없다. 운영 다중 인스턴스·Redis 토폴로지·실제 key/TTL·오류 발생 빈도는 확인하지 않았다.

`Product.from`의 판매/표시 변경도 포함한다. RF004 직접 details.create는 판매상태를 바꾸지 않으므로 새로운 sold 처리를 넣지 않는다. 생성은 새 ID, 이미지·태그 별도 writer/사용자·채팅·신고 DTO 연관 변경은 RF010 조사 또는 별도 범위다. Penalty의 같은 트랜잭션 report 변경은 해당 상품 전체 DTO 무효화의 부수 효과로 함께 반영되지만 신고 전체 캐시 정합성 보장을 뜻하지 않는다.

RF007 `ProductAuthorizationCacheTest`는 현재 PUT 반환 DTO put과 성공 DELETE 후 기존 캐시 유지를 명시적으로 특성화한다. RF009에서 해당 기대를 바꾸는 경우 변경 전 증빙을 보존하고 인가 거부 시 무쓰기·캐시 무변경 기대는 유지한다. frontend 상품 상세·관리자 GET/PUT, my_page 수정/삭제/끌올이 영향을 받는다. 채팅 서버의 해당 REST writer 호출은 검색에서 발견하지 못했다. 프런트 SWR/Next 캐시·검색 색인의 최신성을 백엔드 Redis 무효화로 보장하지 않는다.

### 공식 근거와 해석

2026-11-10 확인한 [Spring Redis cache 설명](https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html)은 기본 비트랜잭션 캐시와 transactionAware 선택, 캐시 단위 locking writer를 설명한다. [TransactionAwareCacheDecorator](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/cache/transaction/TransactionAwareCacheDecorator.html)는 put/evict/clear를 성공 커밋 뒤 지연시키고 tx가 없으면 즉시 수행한다고 명시한다. 즉시 연산 putIfAbsent/evictIfPresent는 같은 지연 보장을 제공하지 않는다.

[Spring annotation 설명](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html)의 proxy 방식은 외부 호출에 적용된다. 메서드 정상 반환과 물리 tx 성공은 같지 않으므로 annotation의 after-invocation만으로 rollback 안전성을 주장하지 않는다. [TransactionSynchronization 6.1](https://docs.spring.io/spring-framework/docs/6.1.x/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)은 afterCommit 시 DB가 이미 커밋되었고 RuntimeException이 caller로 전파됨을 명시한다. [SimpleCacheErrorHandler](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/cache/interceptor/SimpleCacheErrorHandler.html)는 오류를 재전파한다.

현재 프로젝트 Boot는 3.2.4다. 최신 reference/API는 원칙 확인용이며 프로젝트의 실제 의존성 버전/소스와 proxy 테스트로 교차 검증해야 한다. 공식 근거는 커밋 뒤 무효화의 이유를 제공하지만 허용 stale 시간·장애 시 HTTP 정책·분산 일관성을 정하지 않는다. 위 자료로 성능 개선을 주장하지 않는다.

## 범위와 제약

- 운영 변경 후보는 ProductService, PenaltyTran, TransactionRequestService와 직접 필요한 작은 상품 캐시 협력자/RedisCacheConfig뿐이다. 최종 설계에서 불필요한 파일은 수정하지 않는다. 테스트·증빙과 RF007 캐시 특성 기대의 명시적 갱신을 포함한다.
- API DTO/응답 코드·태그/삭제 OR 규칙·인가·거래 잠금/RC·단일 tx 원자성을 유지한다. RF004 임의 stale 관리객체/outer RR 지원을 부활시키지 않는다. RF007의 본인 USER/기존 ADMIN·거부 무쓰기 유지.
- 신규 라이브러리, DB 스키마, 전역 pool/OSIV·인증 정책, outbox/메시지 인프라, 다른 캐시 소유권, 운영 데이터 복구는 제외한다. 필요 시 별도 승인/명세.
- 최초 분석 단계는 문서만 변경했다. 아래 최소 구현·격리 결과는 이후 실행 이력이다. 실DB/Redis 접속·fixture 쓰기·서버 시작은 별도 환경 승인 확인 전 실행하지 않는다.

## 접근 및 위험

1. 변경 전 실제 Spring 캐시 proxy+트랜잭션 관리자 대역으로 warm→각 writer→read stale와 update put 특성을 확보한다. DB 대역 rollback은 DB 원자성 근거로 쓰지 않는다.
2. 독립 계획 리뷰 후 선택한 최소안은 **작은 상품 캐시 협력자를 통해 변경이 성공 커밋된 뒤 해당 상품 key만 무효화**다. update의 CachePut을 제거하고 같은 협력자로 무효화한다. 반환 DTO/정상 HTTP 계약은 유지하되 PUT 성공 직후 캐시에 반환 DTO가 저장되던 내부 동작과 Redis put 오류 전파 특성은 변경된다. 이를 기존 동작 완전 보존으로 표현하지 않는다.
3. 실제 transaction과 synchronization이 모두 활성화되면 커밋 후 callback을 등록한다. tx가 없는 호출은 즉시 evict fallback을 사용한다. 같은 상품 반복 evict는 허용하며 별도 전역 registry/중복 제거를 만들지 않는다. RedisCacheConfig의 전역 transactionAware 설정이나 이벤트 인프라는 이번 선택에 필요하지 않다. private 제재 writer와 수락 변경 지점에서 협력자를 명시 호출하여 자기호출 proxy 누락을 피한다. 무효화 key는 상품 ID이며 request ID/report ID를 사용하지 않는다. 전체 clear·TTL 단축·beforeInvocation eviction·sync=true·JVM별 lock으로 정합성을 대체하지 않는다.
4. 삭제 거부·인가 거부·404/409·수락 반복/거절에는 상품 변경이 없으므로 무효화도 하지 않는 안을 우선한다. 제재는 판매상태가 이미 false라도 같은 tx의 report DTO 변경이 있어 무효화가 필요하다. tx rollback/commit 실패에는 캐시를 갱신하지 않아야 한다. 외부 active tx 참여 시 최종 커밋까지 지연하며 no-tx 호출 처리는 테스트에서 명시한다.

### 완료 판정에서 숨기면 안 되는 경쟁과 장애

- **동시 miss의 stale 재삽입**: R이 miss 후 옛 DB 값을 읽음 → W가 commit+evict → R이 뒤늦게 put. after-commit eviction/transactionAware만으로 이 순서를 막지 못한다. 두 reader/역순 writer도 결정적 latch로 재현해야 하며 단순 warm 테스트 성공을 전체 최신성으로 확대하지 않는다.
- **다중 인스턴스**: JVM lock/sync=true는 공유 Redis의 다른 프로세스 writer와 miss를 직렬화하지 않는다. Redis locking writer도 DB 읽기→커밋→캐시 저장 전체를 묶는 상품별 트랜잭션 잠금이 아니다. 현재 인스턴스 수는 미확인이다.
- **DB 성공/캐시 실패**: afterCommit Redis 실패는 DB를 되돌리지 못하며 예외가 서비스/controller로 전파되면 이미 성공한 제재·끌올·수정이 HTTP 오류로 보일 수 있다. 사용자 재시도로 중복 제재/시간 재갱신 등 부작용이 가능하다. transactionAware 자체는 이 문제를 해결하지 않으며 callback 내부 실패는 annotation CacheErrorHandler 경계 밖일 수 있다.
- 독립 계획 리뷰 후 장애 정책은 협력자의 캐시 조회/evict에서 발생한 RuntimeException을 잡고 상품 ID·캐시명을 포함해 기록하되 기존 쓰기 응답을 유지하는 것으로 선택했다. 실패가 다른 callback 실행을 방해하지 않아야 하고 no-tx fallback에도 같은 처리를 적용한다. 기존 Redis 미의존 writer에 새 HTTP 실패·재시도를 만들지 않는 프로젝트 선택이며 공식 문서가 오류 무시를 업무 정책으로 권고한 것은 아니다. PUT은 기존 CachePut 오류 전파가 제거되는 명시적 예외다. 읽기 get/put 오류 정책은 그대로 둔다. stale 잔존과 복구 미보장은 남고 자동 retry/outbox는 추가하지 않는다.
- DB commit 직후 프로세스 종료, Redis failover/장애 후 옛 key 복구도 원자적으로 보장하지 못한다. TTL은 정상 캐시 보관시간 제한이며 DB 변경부터 항상 30분 이내 최신이라는 증명은 아니다(늦은 stale put은 TTL을 재시작).
- 사용자 지시의 합의 기능은 정상 커밋 후 대상 상품 무효화다. 이 기능과 오류 처리·회귀가 검증되면 **합의 기능 한정 완료**로 판정할 수 있다. 동시 miss stale put·실패 복구·다중 인스턴스 강한 최신성은 미해결로 별도 추적하고 전체 캐시 정합성 완료로 표현하지 않는다. 강한 최신성이 필요하면 캐시 우회/제거 또는 분산 generation/fencing을 별도 설계해야 하며 DB 부하·계약 영향을 검토한 후 별도 착수한다.

### 독립 계획 리뷰 보완 (2026-11-10)

직접 `TransactionSynchronization.afterCommit`의 RuntimeException 전파와 `@TransactionalEventListener(AFTER_COMMIT)`의 실행 지점을 구별한다. [TransactionPhase 공식 API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/event/TransactionPhase.html)의 AFTER_COMMIT은 `afterCompletion(COMMITTED)` 단계이며 직접 afterCommit callback이 아니다. 이번 선택은 명시적 협력자와 callback 내 예외 차단으로 구현/검증한다. 이벤트 대안의 예외가 직접 afterCommit과 동일하게 전파된다고 일반화하지 않는다. 공식 근거는 타이밍·예외 경계이고 장애 응답 정책은 위 프로젝트 판단이다.

독립 리뷰가 요구한 검증은 실제 tx+synchronization/무tx fallback, commit 전 무변경·commit 후 대상 key만 eviction, rollback/commit 실패 무효화 없음, RuntimeException 로그·쓰기 응답 유지·뒤 callback 계속 실행, 중복 evict 허용, 인가 거부/사업조건 거부·수락 no-op 제외, private 제재/수락 실제 연결이다. synchronization만 활성화된 비transaction 경계도 분리해 확인한다. 두 독립 Spring context가 같은 대역 cache/backend를 공유하는 결정적 latch 실험으로 miss→옛 값 읽기→다른 context commit/evict→늦은 put을 재현한다. 이 재현 성공은 결함 해결이 아니라 잔여 위험의 증빙이며 실제 Redis/다중 프로세스 검증과 구분한다.

## 검증 및 완료 조건

### 외부 연결 없는 선택 검증

- 실제 proxy·실제 synchronization lifecycle과 대역 cache/repository로 warm→PUT/sale/refresh/delete/Penalty/수락→read, key 분리·타 상품 불변, rollback/rollback-only/commit 실패, 거부/없는 ID/반복·거절을 검사한다. commit 직전 cache 유지/성공 직후 eviction 순서를 관찰한다.
- read get/put 실패와 writer eviction 실패를 각각 주입하고 선택된 오류 전파 정책·DB 결과·callback 호출 횟수를 구분한다. 정상 commit 완료 후 callback 실패를 rollback 성공으로 오인하지 않는다.
- 격리 proxy context의 advisor 순서를 기록하고 annotation tx 바깥/안쪽의 적용과 기존 outer tx 참여, private 자기호출을 검토한다. 운영 Boot 전체 advisor 순서는 별도 미검증으로 둔다. 동시 miss stale 삽입은 결정적 barrier로 재현하고 해결 여부/남은 경계 표시.
- RF004 Policy/Creation, RF007 authorization service/cache/security chain, RF006/008 관련 선택 회귀를 실행한다. 실제 선택 클래스와 명령은 구현 뒤 명세·증빙에 기록한다. 기본 후보 명령은 `./gradlew.bat --offline test --tests '<검토한 격리 클래스>' --rerun-tasks`, `compileTestJava`, `assemble`; 전체 `test/build`는 외부 Boot 설정 위험 때문에 자동 실행하지 않는다.

### 실DB/Redis 검증 필요성과 안전 조건

대역은 JPA flush/commit·락, 실제 Redis serialization/key/TTL/네트워크 실패를 증명하지 못한다. 이를 주장하려면 승인된 격리 MySQL+Redis와 실제 service proxy/RedisCacheManager를 함께 실행해야 한다. RF004 과거 격리 MySQL 승인/테스트24건은 이번 신규 Redis 사용·현재 DB 접속/쓰기 승인이나 RF009 성공 증빙이 아니다.

- 문서상 후보는 local 전용 MySQL loopback13306/ngng_local, Redis loopback16379이다. 문서에 주소가 있다는 사실은 실행 중 identity나 사용 허가가 아니다. preflight 승인 후 process/listener/datadir 또는 container/volume·DB명/schema/기존 행·Redis DB index/prefix/사용자 충돌을 확인한다. 운영 credential/기본 application 설정을 사용하지 않는다.
- 기존 의존성으로 opt-in fixture만 실행하며 ddl-auto validate/none, 발송·S3/ES/외부 연결 차단. 공통 role/category/status는 소유행 또는 재사용 허용을 확인하고 기존 행을 덮지 않는다. 독립 cache namespace 또는 전용 Redis 인스턴스·정확 key 목록을 사용한다. FLUSHALL/FLUSHDB/전역 clear 금지.
- 정상 serialization 왕복/TTL·각 writer commit/rollback·두 독립 context에서 동시 miss/reader·writer 순서를 관찰한다. Redis 장애는 승인된 전용 프로세스만 대상으로 하거나 client fault 주입으로 제한하고 공유 서비스를 중지하지 않는다. 실제 네트워크 장애와 대역 오류 주입을 별도로 기록한다.
- 테스트 소유 DB행/Redis key만 정확 삭제하고 새 독립 연결로 잔여0·기존 공통행 불변을 확인한다. 자격값/실사용자 DTO를 로그·공유 XML에 남기지 않는다. 미승인·identity 불일치·fixture 충돌이면 연결/쓰기를 멈추고 미실행으로 기록한다.

완료 조건은 범위별 commit/rollback·인가/API·키 정확성·실패 정책·동시 miss 판정 및 독립 리뷰다. 검증한 제한적 보장과 강한 최신성/분산·장애 잔여를 따로 선언한다. 미검증 통합을 통과로 기록하지 않는다. 성능은 비교 환경·지표를 새로 합의한 후 별도 작업으로 수행한다.

롤백은 기준 HEAD와 작업 diff를 비교하여 RF009 변경 hunk만 되돌린다. 사용자 변경을 reset/checkout으로 덮지 않는다. 캐시 코드 롤백은 이미 커밋된 업무 데이터를 되돌리지 않으며 운영 캐시 삭제도 자동 수행하지 않는다. 독립 계획 리뷰는 위 선택·검증 조건에 반영했다. 구현 결과의 독립 코드/증빙 리뷰에서 합의 기능의 차단 결함을 발견하지 않았으며 문서 정합 최종 검토도 완료했다.
