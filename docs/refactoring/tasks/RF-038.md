### 상태 ID의 상충: 운영 정의 확인 선행

| ID | 실제 마이페이지 분기에 사용하는 `_constans/enum.ts` | chat/_api.ts의 현재 사용 미발견 statusList |
|---|---|---|
| 1 | 입금 대기 | 거래요청 |
| 2 | 입금 완료 | 입금대기 |
| 3 | 배송중 | 입금완료 |
| 4 | 배송완료 | 배송중 |
| 5 | 구매확정 | 거래완료 |
| 6 | 거래 취소 | 거래취소 |
| 7 | 거래 신고 | 거래신고 |
| 8 | 정의 없음 | 요청거절 |

backend는 생성 ID=1 외 의미를 고정하지 않는다. 아래 전이 제안은 **활성 마이페이지 코드의 의미를 가정한 잠정안**이며 운영 transaction_status 값·상품 거래 정책 확인 없이 이 표를 서버의 진실로 하드코딩하지 않는다. 기존 fixture의 임의 status 이름도 운영 seed 증거가 아니다.

### 화면에서 확인한 전이와 서버의 차이

- 구매자: 1에서 잔액 check → payment → PUT status 2, 4에서 구매확정 5. check 성공은 차감 완료 증거가 아니다. payment 실패 뒤 후속 상태 호출 차단은 RF003에서 확인했으나 payment 성공 후 상태 실패는 RF037 미해결이다.
- 판매자: 2에서 발송 3, 3에서 배송완료 4. 운송장 input은 있지만 값 전송/저장은 TODO이므로 운송장 필수를 기존 서버 계약이라고 하지 않는다.
- 양쪽: 취소 버튼은 숫자 status>=2이면 거부하여 정상 enum에서는 1→6만 가능. 신고 버튼은 전 상태에서 7 요청 가능. 7이 신고 접수인지 거래 중단/최종 상태인지, 신고 엔티티 생성과 연계되는지는 이 상태 setter에 정의되어 있지 않다.
- 서버: 두 당사자 모두 존재 status A→B를 허용하므로 판매자의 미결제 1→2, 구매자의 1→5, 5→1 역행도 정적으로 가능한 경로다. 실제 HTTP·DB 재현/운영 발생은 이번에 하지 않았다.

## 정책 선택과 의존 관계

RF006의 공식 Java 값 동등성 근거나 일반적인 요청별 인가 권고는 NGNG의 배송·신고·취소 정책을 정해 주지 않는다. 과거 역할/금액 판단 위임은 존중하되 다음 제품 고유 선택은 권고와 확정을 구분한다.

RF035는 서버가 믿을 구매자·가격·대상 거래를 먼저 정의한다. RF038은 그 결과를 결제 가능한 상태 및 상태 전이에 연결한다. RF036은 동일 거래/결제 시도 식별·재전송 결과를 정의하며, 같은 status 무쓰기만으로 중복 차감을 해결하지 않는다. RF037은 차감과 1→2를 같은 성공 경계로 묶거나 복구/보상하며 RF038의 public PUT 우회도 함께 막아야 한다. 정책 합의 후 구현 순서를 정하되 각 RF를 자동 착수하지 않는다. RF021 보류 직접 생성은 변경하지 않으며 그 경로가 만든 임의 buyer/price 거래를 RF035 검증 없이 신뢰하지 않는다.

## 접근 및 위험

최소 구현 후보는 DetailsService의 국소 전이 검사와 동일 트랜잭션의 현재 상태 재조회/동시 갱신 보호, 필요한 repository·기존 PUT 계약 테스트 및 마이페이지 실패 처리다. 상태 라벨 통합·관리자 복구·신고/환불·상품 재판매는 자동 포함하지 않는다. schema/version/결제 증빙 추가가 필요하면 별도 승인한다.

일반 read→setter만으로 두 요청을 직렬화하지 못한다. 예를 들어 1→6 취소와 결제/1→2가 경합하거나, stale 2→3과 2→7이 서로 덮어쓸 수 있다. 현재 실제 손실 발생은 미재현이다. 후보는 거래 행 잠금 후 최신 상태 검사 또는 조건부 UPDATE로 기대 상태 비교이며, version 열 추가는 스키마 승인 대상이다. 상품·거래·사용자·이력 잠금 순서를 RF004/003/035/037과 하나로 설계하고 RR snapshot/1차 캐시·OSIV·deadlock/rollback을 검증한다. transaction lock 하나만 추가해 모든 writer/결제 원자성을 해결했다고 하지 않는다. 실패 시 자동 무한 재시도·과거 오염 상태 보정·직접 생성 잠금 변경은 하지 않는다.

## 검증 및 완료 조건 — 미실행 계획

1. 운영 상태표/seed의 읽기 자료와 역할·판매자·결제·취소·신고·반복 정책을 확정한다. DB 접속/쓰기 없이 제공 자료로 우선 대조하고, 필요한 연결/fixture는 별도 격리 범위를 확인한다.
2. 변경 전 대역 특성: 존재하는 모든 상태 A→B, 동일 상태, 없는/null status, 없는 거래, DTO 필드, 기록 seller≠product.owner, null 관계/ID를 관찰한다. 3역할×구매자/owner/기록seller/제3자 및 실제 SecurityConfig/TokenFilter/AuthService 체인으로 정상·거부·토큰 갱신을 구분한다. 거부 전에 setter/point writer가 호출되지 않음을 검증한다.
3. 변경 후 승인 행렬의 허용/거부와 동일 상태 무쓰기, 미결제 1→2 및 위조 proof·타인/다른 금액/취소 거래 결제 거부, 역행·건너뛰기·신고 후 복귀를 테스트한다. RF006/021/023의 주체 차이와 RF004 생성 계약 회귀를 함께 확인한다. 전체 Boot suite를 무조건 실행하지 않는다.
4. 안전한 격리 MySQL fixture에서 각 독립 트랜잭션의 취소 대 결제, 같은/서로 다른 전이, stale snapshot, 선행 rollback·commit 실패·timeout·교착을 검증한다. 허용된 최종 상태/포인트 이력·무중복·무부분커밋으로 판정하며 작은 fixture 결과를 운영 보장/성능으로 확대하지 않는다. RF036/037 미구현 시 원자성/멱등성 통과로 기록하지 않는다.
5. 프런트 대역 후 실제 HTTP/브라우저에서 성공·409/401/서버 오류·응답 유실·빠른 반복·새로고침을 확인한다. 실패 때 완료 표시 금지, 최신 상태 재조회, Promise 전파 확인. 채팅 status 라벨·관리자 영향은 별도 소비자 확인. 상품 production build의 API 접근 경계 확인 전 실행하지 않는다.

### 결제 1→2를 안전하게 제공하는 설계 대안

정상 전이·구매자·금액 검증만 추가하고 기존 `PUT status=2`를 구매자에게 열어 두면, 구매자가 payment를 호출하지 않고 입금완료를 만들 수 있다. 반대로 payment 성공 뒤 PUT을 금지하면서 기존 프런트를 유지하면 차감만 성공하고 상태가 남는다. **RF035→RF038을 독립 배포하며 잠시 이 두 단계 틈을 허용하는 것은 안전한 완성안이 아니다.** 프런트 Promise/호출 순서나 check 결과는 서버 결제 증거를 대신하지 않는다.

| 대안 | 안전성·계약/구현 영향 |
|---|---|
| A: 기존 결제 endpoint 내부에서 차감+1→2 동일 DB 트랜잭션 (우선 검토) | 상품ID 등 기존 식별 입력으로 대상 거래를 신뢰성 있게 확정하고 기록 buyer/price·현재1 검사 뒤 차감과 status2를 함께 커밋. public PUT의 최초1→2는 거부하고 내부 결제 처리만 허용. 프런트의 추가 PUT 제거 또는 이미 완료된 동일2에 대한 안전한 무쓰기 응답을 결정. RF037과 동일 구현/배포 경계를 공유해야 하며 RF035만의 완료로 포장하지 않음 |
| B: 거래ID 중심 단일 결제 명령 | 대상 식별이 명확하고 A와 같은 원자성 가능. 새 endpoint/입력 계약·호출자 전환 필요. 기존 payment가 별도 차감 우회 경로로 남지 않도록 계약을 함께 정리. API 변경은 사용자 승인 범위 확인 필요 |
| C: 결제 성공 기록을 영속화하고 기존 PUT이 검증 | 거래/구매자/가격·성공 여부와 중복 사용 방지를 연결한 durable 결제 proof가 필요. point typeDetail 문자열·클라이언트 응답은 불충분. 차감 후 status 실패가 여전히 가능하므로 재시도/복구 및 RF036 멱등성·RF037을 함께 구현해야 함. 새 schema 필요 시 승인. 증거 검증만으로 두 요청 원자성을 주장할 수 없음 |
| D: 권한·정상 전이만 먼저 제한, 결제 PUT 유지 | 무결제1→2를 막지 못함. 이번 목표의 안전한 완료·배포안으로 채택하지 않음 |

A에서도 status2 재요청 성공은 “현재2니까 이미 결제됨”으로 무조건 판정하면 안 된다. 기존 운영 상태2는 과거 임의 PUT으로 생성될 수 있고 결제 proof가 없다. 배포 전 기존 미검증 상태/금액·출처를 어떻게 취급할지 읽기 조사와 정책이 필요하며, 이 분석이 데이터 수정 승인은 아니다. 정상 결제 endpoint에서 상태·차감을 함께 커밋한 신규 거래와 기존 상태를 구분하는 수단 또는 보수적인 재요청 실패 정책을 설계한다. 결제 응답 유실 후 금전 재요청은 RF036 키/멱등성 계약을 공유해야 한다.

사용자 잠금(RF003), 상품 잠금(RF004), 거래 상태 보호를 같은 lock 순서로 설계하고 취소/신고도 같은 거래 동시성 규약을 사용해야 한다. payment와 1→6 경합은 선행 취소면 결제 거부, 선행 결제면 기존 정책에 따라 이후6 허용·환불 없음이라는 직렬 실행 결과가 가능하다. 이를 새 취소 제한으로 바꾸지 않는다. 직접 생성 거래에도 같은 규약을 적용하되 create 인가 정책은 변경하지 않는다. 단순 @Transactional 하나로 외부 요청 두 개를 원자화하지 않는다.

### 추가 검증 계획과 현재 한계

확정 행렬의 actor·이전/목표 상태 조합, seller≠owner, 직접 생성 거래 결제 성공·타인/가격 불일치 거부, payment 생략 PUT2 거부, 차감 flush 후 상태 실패 rollback, 취소/신고와 결제 경합·기존 무환불 유지, 응답 유실/동일 상태/기존 오염 상태를 별도 테스트한다. RF006 기존 owner 기대값은 변경 승인 이력과 함께 갱신하고 RF023 기록 당사자 조회 회귀를 유지한다. 실제 실행은 하지 않았으며 정책 문서만 갱신했다. 6/7 복귀·proof/동일 요청 응답과 API 통합 방식 결정, 필요한 격리 fixture/스키마 승인 전 테스트·DB 쓰기·구현은 자동 진행하지 않는다.

## 2026-11-11 추가 확정 — 취소·신고 이후 복귀

사용자는 위 예외 상태 복귀 대안 **A를 선택**했다. 이 절이 앞선 '결정 대기' 표현보다 우선한다.

- 기존 상태에서 목표6(취소)·7(신고) 요청은 기록 구매자/판매자에게 계속 허용한다. 6→7, 7→6 및 같은 예외 상태 목적지의 허용도 유지한다. 동일 요청의 응답/실제 무쓰기 보장은 별도 기술 계약이며 허용 자체를 새로 거부하지 않는다.
- **현재 상태6 또는7에서 정상 거래 상태1~5로 복귀하는 요청은 거부한다.** 따라서 1→7→5 같은 정상 전이 우회와 6/7→1 재진입을 허용하지 않는다. 과거 API의 복귀 허용을 의도적으로 바꾸는 승인된 정책이다.
- 정상 1→2→3→4→5 및 기록 당사자별 행위는 앞서 확정한 정책을 적용한다. 정상 상태의 역행·건너뛰기는 거부한다. 취소·신고 목적지 허용은 정상 전이 행렬과 별도 규칙이다.
- 마이페이지 취소 UI의 status>=2 차단은 기존대로 두며, API의 결제 후 취소 허용을 UI에 맞춰 새로 제한하지 않는다. 신고 UI는 기존 전 상태 요청을 유지한다. 환불·상품 재판매·forSale 복구·거래 삭제·신고 자원 생성은 추가하지 않는다.

### 공통 잠금 규약과 실패 결과

상품 ID 식별(비권위 탐색) → **상품 PK scalar lock** → **거래 scalar current lock** → 현재 상태·기록 buyer/seller·대상 상품 관계 재검증 순서로 통일한다. 탐색 중 얻은 entity/상태·RR snapshot/1차 캐시를 최신 권위로 사용하지 않는다. 결제 경로만 이어서 user/point lock을 취득해 금액·잔액을 확인하고 차감+1→2를 원자적으로 커밋한다. 일반 상태 PUT·취소/신고는 사용자/포인트를 쓰지 않는다. 두 서버·외부 writer 및 생성 경로가 같은 규약에 참여하는지 확인하고, scalar 조회 결과와 DTO/entity의 stale 상태 일치를 별도로 검증한다.

### RF038 분리 범위와 공동 배포 조건

분리해서 진행 가능한 작업은 명세·상태 행렬 테스트 준비, seller 주체 인가·전이 검사·scalar lock 구현의 개발/격리 검증이다. 이는 개발 분리 가능성이지 기능별 부분 배포 승인이나 단독 완료 보장이 아니다. 최초 public PUT1→2를 막는 변경은 **결제 내 차감+1→2 구현 및 프런트 추가 PUT 제거와 같은 릴리스 경계**로 배포한다. 구 프런트가 차감 후 추가 PUT 성공에 의존하거나 구 백엔드가 별도 차감/무검증 상태 PUT을 받는 혼재 상태를 허용하지 않는다. 예외 목적지 허용과6/7 복귀 차단·기록 seller 인가는 확정된 계약으로 함께 회귀 검토한다.

다음은 구현 통과 여부와 별개의 **배포 차단조건**이다. 해소 증거가 없으면 운영에 안전하다고 판정하지 않는다.

1. 구버전 writer와 진행 중인 구 트랜잭션을 배제하는 배포/드레인·전환 절차 미확정. 신규 lock만으로 구 코드를 직렬화·정책 준수시키지 못한다.
2. 기존 상태2 이상 또는 상태1인 거래의 과거 결제/고아차감 여부 미분류. 특히 **신규 거래라도 같은 legacy 상품에 과거 고아차감이 있으면 안전한 신규 결제로 단정할 수 없다.** transaction 생성 시각·status1·새 코드 경유만으로 미결제를 증명하지 않는다.
3. 안전 처리 대상의 분류와 영속 표식/증거 전략, 기존 상품·거래·포인트 이력의 운영 확인 및 불명확 대상 처리 절차 미확정. point 설명 문자열 파싱·추정으로 결제 증명을 만들지 않는다. 영속 표식에 schema 변경이 필요하면 별도 승인을 받는다.
4. 운영 status ID 의미·FK/unique·격리수준·writer 목록 및 완전한 seller/consumer 관계 확인 미실행. 정상 상태 정책은 확정되어 있어도 기존 데이터 호환성 검증을 생략하지 않는다.

위 항목의 조회/분류·데이터 복구·schema·실서비스 전환은 이번 문서 수정 승인이 아니다. 공통 RF035/036/037 배포 문서와 동일 차단조건을 유지해야 한다. 검증 계획에 정상/예외 동일 PUT의 역할·무쓰기, 상태8→6/7, public 최초PUT2 거부, 구 호출자 호환성, 신규 거래+legacy 상품 고아차감, 구버전/진행 중 tx 차단 절차를 추가한다. 이번 결과는 문서 갱신이며 테스트·DB 연결/쓰기·소스 변경은 실행하지 않았다.

## 2026-11-11 2단계 구현 착수 — 최신 범위와 제한

사용자는 공동 리뷰 계획을 승인했다. 작업 브랜치는 `refactor/payment-integrity-stage2`이며 RF035 기존 변경과 RF036 병렬 변경을 보존한다. 이번 담당 범위는 RF038 service/repository, RF038 전용 테스트 및 이 명세·증빙이다. 공통 BACKLOG/LOG·RF035/036/037 문서, 포인트 서비스·운영 설정·schema는 이 담당자가 변경하지 않는다. commit/push·단독 merge·단독 배포는 하지 않는다.

최초 public PUT1→2는409이며 결제 내부 전이는 RF037과 결합한다. 2→3·3→4는 기록 seller, 4→5는 기록 consumer만 허용한다. 정상 역행·건너뛰기와6/7→1~5는409. 실재 미지 상태를 포함한 기존 상태→6/7 및6↔7은 기록 당사자에게 허용한다. 동일1~7은 양 당사자200 무쓰기이고 동일2의200은 결제 증거가 아니다. 양쪽 기록 당사자 ID가 완전해야 하며 product.owner·ADMIN 우회는 없다. 기존 비당사자401·새 행위자403 구분을 유지한다.

호출 검색상 상태 PUT의 운영 호출자는 TransactionController 한 곳이다. 기존 `@Transactional(REQUIRED)`에 명시 `READ_COMMITTED`를 지정하고, 상품ID scalar 식별→상품PK scalar lock→거래 scalar current lock→인가·행렬→처음 거래 entity 조회→scalar/entity 주요 값 대조→필요 시 setter→기존 DTO mapping 순으로 구현한다. scalar가 인가·상태 판단의 권위이며 불일치는409로 setter/DTO 전에 실패시킨다. 선행 target entity 로드가 없는 최상위 HTTP가 검증 대상이다. `clear/refresh/REQUIRES_NEW`나 상위 트랜잭션 거부 guard를 추가하지 않는다.

**임의 outer RC/RR 트랜잭션, 사전 관리/dirty 거래 entity·OSIV가 이미 로드한 대상, 다른 writer까지 안전하다고 주장하지 않는다.** REQUIRED에 참여한 outer의 격리수준은 메서드의 RC 선언으로 바뀌지 않는다. native 조회의 auto-flush가 scalar 대조보다 먼저 caller dirty 값을 flush할 수 있으므로 불일치 검사만으로 그 경우를 해결했다고 하지 않는다. 실제 HTTP의 선행 로드·필터·OSIV와 물리 SQL/commit/rollback은 별도 격리 검증이 필요하다. 전역 persistence context clear/refresh는 caller pending 변경을 잃게 할 수 있어 채택하지 않는다.

변경 전 실제 filter/JWT/AuthService/controller/service·repository 대역6건 및 서비스 특성14건을 준비했다. ### 구현 결과·RF037 연결 인터페이스

`TransactionDetailsRepository.findStatusProductId(id): Optional<Long>`는 잠금/인가 증거가 아닌 상품 식별만 수행한다. 상품PK scalar lock 뒤 `lockStatusTransaction(id): Optional<StatusTransaction>`로 transactionId/productId/consumerId/sellerId/statusId/price/address를 current-read한다. 355건 검증 당시 RF035의 `lockPaymentTransactions` 및 기존 projection은 미변경이었고 이후 RF037용 추가 확장은 아래 후속 절에서 구분한다.
