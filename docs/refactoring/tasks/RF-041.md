## 계획 단계 기록

아래 목표·범위·검증 계획은 최초 읽기 분석 당시 기록이다. 사용자 1A 구현 승인 이후 실제 변경·결과·남은 검증은 문서 끝의 실행 기록이 우선한다.

## 목표와 근거

경로 약어 B=`NGNG-backend/src/main/java/com/ngng/api`, F=`NGNG-frontend/src`.

1. `B/user/user/controller/ConfirmController.addressConfirm`은 `PUT /confirm/address`, JSON `{id: Long, address: String}`를 `ConfirmService.addressConfirm`에 전달한다. 계좌 경로와 달리 필수 refresh 쿠키 인자가 없다. 서비스는 `UserRepository.findById(request.id()).orElseThrow()` 후 `User.addressConfirm`으로 주소만 대입한다. `@Transactional` dirty checking을 전제로 하며 명시 save, caller 비교, 주소 validation은 없다.
2. `AddressConfirmResponse`는 success factory만 있고 서비스는 항상 성공 DTO를 반환한다. 정상 컨트롤러 응답은 204 빈 body. 컨트롤러에는 false DTO 시400 분기가 있으나 현재 실제 서비스에서 도달하지 않는다. null id의 repository 오류, 미존재 id의 NoSuchElementException은 통제된 400/404 계약으로 구현되지 않았다. 실제 servlet 오류 응답은 실행하지 않아 확정하지 않는다.
3. `SecurityConfig`의 정확한 `/confirm` authenticated matcher는 하위 `/confirm/address` 전체를 뜻하지 않는다. 주소는 anyRequest permitAll에 해당하지만 `TokenFilter.shouldNotFilter` 예외가 아니므로 access 검증 또는 refresh fallback을 먼저 거친다. 무인증·유효하지 않은 토큰은401이다. 유효 USER, UNCONFIRMED_USER, ADMIN 모두 주소에 도달하며 역할 allowlist는 없다. 현재 필터는 nonblank role claim만 요구하므로 알려지지 않은 role 문자열도 코드상 배제하지 않는다. 이를 무인증 공개라고 표현하지 않는다.
4. 필터는 검증된 JWT subject=email과 role로 ID 없는 User/CustomUserDetails principal을 만든다. `AuthService.readAuthUser`는 SecurityContext principal email로 `UserRepository.findUserByEmail`을 호출해 DB userId를 얻는다. 이 메서드 자체는 null/type 방어가 없어 호출 전에 검사가 필요하다. JWT principal.userId와 요청 id 직접 비교는 정상 사용자도 막으므로 부적절하다.
5. F `my_page/_compoenets/modal/UpdateAddress` → `_hooks/useMypageSWR.updateAddress` → `_api/api.ts:updateUserAddress`는 sessionStorage user.id를 body id로 넣고 Authorization과 함께 `/api/confirm/address`로 PUT한다. `next.config.mjs` fallback rewrite가 백엔드 `/confirm/address`로 보낸다. 주소 선택·상세주소 UI는 본인 mypage 편집이며 서버의 객체 인가를 대체하지 않는다.
6. 프런트는 `setAccessToken(res)` 후 res.ok에서만 완료 callback으로 모달을 닫는다. 실패 응답을 throw하지 않아 SWR populateCache에서 제출 주소를 임시 반영할 수 있고 revalidate한다. 실제403 화면·프록시·쿠키 동작은 미검증이다.
7. 관리자 주소 관리 업무는 별도 F `admin/users/[id]/page.tsx`의 PUT `/api/admin/users/{id}` → `AdminUserController.update` → `UserService.adminUserUpdate`이며 주소도 편집한다. `/admin/**`는 ADMIN matcher다. 이는 ConfirmService를 호출하지 않으므로 주소 확인의 본인 제한이 관리자 타인 주소 관리 경로 자체를 막지 않는다. 관리자 API의 path/body ID 불일치 등 별도 문제는 이번 변경 대상으로 확대하지 않는다.

[OWASP API1:2023 BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)를 2026-11-10 조회했다. 클라이언트 ID로 레코드를 다루는 함수마다 인증 주체가 해당 작업을 수행할 권한을 검사하고 회귀 테스트를 두라는 원칙을 적용한다. OWASP가 NGNG 관리자 정책을 정하거나 단순 ID 비교를 모든 BOLA의 해법으로 정한 것은 아니다. 이 경로의 객체는 사용자 자신의 주소이며 본인 UI와 별도 관리자 업무 경로에 근거해 **인증 주체가 DB에서 해석되고 요청 id가 본인 ID와 같을 때만 허용**하는 최소안을 선택한다. 관리자도 이 경로에서는 본인만 허용하고 별도 관리자 API는 유지한다. 기존 타인 주소 변경 가능성은 사실인 코드 경로이나 의도된 관리 기능으로 단정하지 않으며 이번 개선에서 명시적으로 차단할 대상이다.

## 범위와 제약

- 이번 수정 허용: 이 명세와 `evidence/RF-041/README.md`만. 향후 구현 예정은 ConfirmService.addressConfirm의 좁은 guard 및 주소 전용 테스트.
- 유지: endpoint, JSON id/address, 정상204 빈 body, 트랜잭션과 주소 대입, 본인 USER/UNCONFIRMED_USER/ADMIN 접근. 본인 null/빈/공백 address도 현재 서비스가 그대로 대입하므로 새 validation·정규화 금지. 실 DB null 제약은 확인하지 않았다.
- 새 객체 거부 정책: 타인·null ID·주체 해석 불가를403으로 통일하고 대상 행 조회 전에 거부. 인증 실패는 필터의 기존401 유지. 별도 role allowlist, ADMIN 우회, UNCONFIRMED_USER 배제는 추가하지 않는다.
- 제외: RF-020 계좌·역할 승격·토큰 발급, RF-042 탈퇴, RF-033 주소 로그, RF-040 stale role/토큰 폐기, 주소 유효성·동시 갱신·전역 AuthService/인가 구조·관리자 API·frontend 실패 UI 개편. 신규 의존성, 스키마 및 대규모 아키텍처 변경 없음.

## 접근 및 위험

1. 후속 구현 전 당시 소스와 격리 fixture로 본인/타인 기존 경로를 재현·보존한다. 이 문서는 재현 성공 증거가 아니다.
2. addressConfirm 진입 시 authentication 존재, authenticated, non-anonymous, CustomUserDetails, 내부 user 및 nonblank email 순으로 확인한다. null request는 직접 호출에서 통제된403으로 방어할 수 있으나 malformed/missing HTTP body의 MVC400 계약은 유지한다.
3. AuthService로 caller를 DB에서 해석한다. caller/caller ID/request id가 non-null이고 Long 값이 같아야 통과한다. null==null이나 Long 참조 비교는 금지한다. 실패는 좁은 ResponseStatusException(FORBIDDEN) 등 기존 선례 방식으로403에 연결한다. DB 연결 장애 등 일반 예외를 모두403으로 삼키지 않는다.
4. 통과 후 기존 `findById` 및 주소 변경 순서를 유지한다. 거부 시 caller email 조회는 가능하지만 요청 target `findById`, 주소 mutation, role/계좌 변경·토큰 발급은 없어야 한다. 존재하는 타인·존재하지 않는 타인 모두 같은403으로 대상 존재 정보를 노출하지 않는다. caller 조회 후 삭제 등 경합에서 본인 대상 조회 실패까지 새 정책으로 은폐하지 않는다.
5. 주소 서비스 자체는 토큰을 발급하지 않는다. refresh fallback은 서비스 전에 호출자의 access Authorization을 설정할 수 있으므로 거부 응답 헤더 전체가 없다고 단정하지 않는다. fallback 거부에서는 호출자 기존 role access만 허용하고 refresh Set-Cookie·대상 토큰은 없어야 한다.
6. RF-020과 같은 ConfirmService 파일이다. 그 작업이 추가하는 AuthService 주입은 재사용 여부를 최종 diff로 확인하되 계좌의 ROLE_UNCONFIRMED_USER 제한을 주소에 적용하지 않는다. 공유 helper 추출은 필요성을 입증하지 않고 자동 진행하지 않는다. accountConfirm hunk·생성자 의존성·계좌 테스트 context 변경 충돌을 구현 직전 확인하고 두 작업 회귀를 함께 실행한다.

### 종료 시 작업트리 재확인
