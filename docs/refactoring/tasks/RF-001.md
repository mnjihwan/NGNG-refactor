# RF-001: 테스트 컴파일 복구 및 사용자 목록 계약 테스트 확보

- 상태: **완료 — 테스트 컴파일 및 선택 테스트 검증, 독립 diff 리뷰 완료**
- 우선순위: P0 선행 작업. 회귀 테스트가 컴파일되지 않을 가능성과 외부 서비스 의존성을 먼저 줄인다.
- 대상: 통합 저장소의 NGNG-backend. 현재 재검토 기준 HEAD `ab77676ae968354c47408002926119e3f3843c69`; 이전 분석 기준 `e0c81ade16b25ec683c24320100069fd0406e682`는 현 객체 데이터베이스에서 확인되지 않았다.
- 성격: 운영 코드 리팩토링의 검증 기반 작업. 성능 개선이나 운영 동작 변경을 포함하지 않는다.

## 목표와 근거

UserControllerTest:232-235는 UserUpdateRequestDTO의 2인자 생성자를 호출하지만 현재 DTO는 nickname/address/accountBank/accountNumber 4개 필드와 Lombok 전체·무인자 생성자를 갖는다. 통합 저장소에서 `compileTestJava`를 실행한 결과 이 불일치로 컴파일이 실패했다. 이전 분석의 Wrapper 다운로드 실패는 BASELINE에 이력으로 남긴다.

기존 9개 테스트는 모두 SpringBootTest이며 고정 DB 데이터·외부 설정에 의존한다. 사용자 목록은 UserService.findAll(Integer) → UserRepository.findByVisible → 각 사용자 PointHistoryService.readCostByUser → DTO.from 흐름이다. 이후 RF-002의 반복 조회 개선에 앞서 외부 상태 없이 이 동작과 controller 응답을 확인할 테스트가 필요하다.

확인된 사실은 생성자 컴파일 오류와 호출 구조다. 실제 SQL 수·성능·기존 테스트 통과율은 미측정이다. 이 작업이 끝나도 전체 통합 검증이 확보된 것은 아니다.

## 범위와 제약

수정 허용 범위:

- `NGNG-backend/src/test/java/com/ngng/api/user/UserControllerTest.java`: 현재 DTO와 맞도록 테스트 입력 생성만 최소 수정. 기존 nickname/address를 유지하고 나머지는 null 등 기존 입력 의도를 보존한다. 테스트 삭제·Disabled로 우회하지 않는다.
- 신규 `NGNG-backend/src/test/java/com/ngng/api/user/user/service/UserServiceTest.java`.
- 신규 `NGNG-backend/src/test/java/com/ngng/api/user/user/controller/AdminUserControllerContractTest.java`.
- docs/refactoring의 작업 결과·기준선 갱신.

운영 src/main, build.gradle, security, DB 스키마, 기존 test application.yml, 다른 프로젝트는 수정하지 않는다. 다른 테스트 컴파일 오류가 나오면 원인과 최소 수정 후보를 먼저 기록하고 범위를 재평가한다. 운영 API/DTO를 낡은 테스트에 맞춰 변경하지 않는다. 기존 전체 통합 테스트의 URL/fixture/발송 문제는 RF-016으로 분리한다.

호출자: AdminUserController와 프런트 `src/app/admin/users/page.tsx`. 세 프로젝트는 현재 같은 통합 저장소 기준점을 사용한다. 채팅은 이 작업과 직접 호출 관계가 없다. 이전 프런트·채팅 기준 커밋은 BASELINE에 이력으로 남긴다.

불변 조건:

- GET /admin/users, page 기본값 0, 0부터 시작하는 페이지, 크기 5, userId 오름차순, visible=true 조회.
- 사용자 순서와 Page 메타데이터 유지. JSON의 nickName 등 현재 철자와 point 포함 필드 유지.
- 사용자별 최신 포인트 이력은 기존 repository에서 ID 내림차순으로 선택한다. 이 작업은 repository를 바꾸지 않으며 실제 SQL 선택 의미는 후속 MySQL 통합 테스트 대상이다.
- 정상 요청의 DB 쓰기 없음. 실제 인가 ADMIN 조건과 토큰·트랜잭션 정책은 변경하지 않는다.
- 포인트 이력 부재 시 DTO.from의 null 역참조는 결함 후보로 구분해 관찰한다. 0원/빈 DTO로 자동 변경하거나 이를 승인된 비즈니스 규칙으로 명명하지 않는다.

승인이 필요한 범위: 신규 의존성, DB/운영 설정 변경, 보안 정책 변경, 대규모 구조 변경. 현재 계획에는 포함하지 않는다.

## 접근 및 위험

1. Java 17, Wrapper 8.7 및 기존 의존성을 사용할 수 있는 환경을 준비하고 compileTestJava부터 실행한다. 환경 제약이 남으면 통과했다고 보고하지 않는다.
2. 생성자 호출을 최소 수정해 전체 테스트 소스 컴파일을 복구한다.
3. 기존 starter-test의 JUnit/Mockito로 UserService를 직접 생성하고 의존 서비스를 mock 처리한다. Spring 컨텍스트·실제 DB·Redis·ES·SMTP·SMS·S3를 열지 않는다.
4. AdminUserController는 standalone MockMvc와 mock UserService로 요청 바인딩·반환 상태·프런트 사용 JSON 필드를 검사한다. 실제 SecurityFilterChain을 붙이지 않으므로 인증 검증 결과로 보고하지 않는다. 테스트용 Jackson 설정은 Page/시간 타입 직렬화를 지원하도록 기존 의존성 내에서 구성한다.

전체 SpringBootTest 복구보다 범위가 좁고 새 의존성이 필요 없어 이 방법을 선택한다. H2 도입은 MySQL 의미 차이와 승인 문제가 있어 선택하지 않는다. 구현을 그대로 따라 쓰는 assertion보다 서로 다른 사용자/잔액/페이지 입력의 결과를 검증한다.

위험은 낮지만 mock은 실제 쿼리, 지연 로딩, Spring 직렬화 설정, 보안 필터를 재현하지 못한다. 서비스 null 결과 등 의심 동작은 `known defect characterization` 성격으로 분리해 이후 정책 확정 시 변경 가능하게 기록한다. 누락된 DTO 필드를 추가하는 것만으로 기존 통합 테스트가 통과한다고 가정하지 않는다.

## 테스트 및 검증 계획

| 시나리오 | 기대 결과 / 관찰 대상 |
|---|---|
| visible 사용자 2명, 서로 다른 역할·포인트 | 사용자별 DTO 모든 필드와 대응하는 잔액, 입력 순서 유지. ID를 섞어 잘못 매핑해도 잡히는 fixture |
| page=0 / page=2 | repository에 visible=true, size=5, userId ASC와 요청 페이지 전달; 반환 Page의 totalElements/totalPages/number/size 유지 |
| 빈 페이지 | 빈 Page 유지, 포인트 개별 조회 없음. HTTP는 현재 controller의 200 및 빈 content 확인 |
| 이력 없는 사용자 | 현재 DTO 변환의 예외를 관찰·기록. 0원으로 바꾸지 않음; 정상 계약 테스트와 분리 |
| 음수 page | 현 PageRequest 경계 예외 관찰. 새로운 HTTP 400 계약을 만들지 않음 |
| GET /admin/users에서 page 생략 | controller가 기본값 0으로 서비스 호출, 200 |
| GET /admin/users?page=2 | controller 전달값과 content/pageable.pageNumber/pageable.pageSize/totalPages, nickName/point 확인 |
| 잘못된 page 문자열 | standalone MVC의 바인딩 실패 관찰. 실제 필터 포함 응답은 미검증으로 표시 |
| 데이터 쓰기 방지 | 읽기 시나리오에서 repository save/delete 및 포인트 충전/결제 경로가 호출되지 않음 |

최신 이력 SQL의 max ID 의미, 숨김 사용자가 실제 DB에서 제외되는지, 동시 갱신 결과는 이 mock 테스트가 증명하지 못한다. RF-002/RF-016의 실제 MySQL 검증으로 보완한다. 현재 사용자별 호출 횟수 N은 RF-002 전 기준 관찰로만 기록하며 미래 구현에 N회를 강제하는 영구 테스트로 만들지 않는다.

실행한 명령 (작업 디렉터리 `NGNG-backend`):

```powershell
./gradlew.bat --no-daemon compileTestJava
./gradlew.bat --no-daemon test --tests 'com.ngng.api.user.user.service.UserServiceTest' --tests 'com.ngng.api.user.user.controller.AdminUserControllerContractTest'
```

변경 전 정상 동작 기록은 위 신규 테스트를 운영 코드를 건드리지 않은 상태에서 실행해 확보한다. 해당 커밋/fixture·명령·XML 테스트 수/실패/skip를 BASELINE에 기록한다. 실행 후 `build/test-results/test/` 및 `build/reports/tests/test/`의 새 결과를 확인한다. 추가 반복은 수정이나 실패 원인 확인이 필요한 때만 수행한다.

완료 조건:

- 전체 테스트 소스 컴파일과 위 선택 테스트가 성공하고 실패/누락을 보고한다.
- 선택 테스트가 외부 설정·고정 DB 사용자·실발송에 의존하지 않는다.
- 허용한 테스트 파일·문서 외 diff가 없다. 기존 테스트 비활성화·운영 소스 변경이 없다.
- 외부 API·인가·DB 상태가 바뀌지 않았음을 diff로 확인한다.
- 기존 전체 test/build, 실제 JSON/SQL/보안 검증의 미완료 상태를 명시한다. 성능 개선을 주장하지 않는다.

독립 리뷰: 구현 담당자와 별도로 DTO 필드, 페이지 fixture와 JSON 단위 검증 범위, 결함 후보의 분리, 기존 테스트 우회 여부를 확인했다. 수정이 필요한 지적 사항은 없었다. 테스트의 무쓰기 검증은 mock 호출 경로에 한정되며 실제 DB 쓰기 부재를 증명하지 않는다.

## 작업 결과 — 2026-11-04

- 시작 시 기존 로컬 환경 작업의 미커밋 변경이 존재했다. 통합 HEAD는 `ab77676ae968354c47408002926119e3f3843c69`이며 이 HEAD만으로 해당 작업 트리를 재현할 수 없다. 기존 변경은 보존했고 RF-001에서 운영 코드·설정·DB를 변경하지 않았다.
- 변경 전 `compileTestJava`는 기존 2인자 DTO 생성자 호출로 실패했다. 테스트 입력에 null 두 인자를 추가한 후 전체 테스트 소스 컴파일이 성공했다. 기존 테스트를 삭제하거나 비활성화하지 않았다.
- 새 서비스 테스트 5건과 standalone MockMvc 테스트 3건을 실행했다. XML 기준 총 8건, 실패 0, 오류 0, skip 0이다. XML timestamp는 각각 `2026-11-04T04:22:04`, `2026-11-04T04:22:07`이며 XML에 시간대는 명시되지 않았다. 선택 테스트의 첫 실행에서 PageImpl 총 건수 보정으로 fixture 2건이 실패해 fixture를 정정한 후 최종 재실행에 성공했다.
- 실제 SecurityFilterChain, 운영 ObjectMapper, DB 쓰기·정렬·최신 이력 SQL, 기존 전체 통합 테스트와 build는 검증하지 않았다. 포인트 이력 부재의 예외는 기존 결함 후보의 관찰이며 승인된 정책이 아니다.

롤백: 이 작업에서 추가한 테스트와 생성자 수정·문서만 선택적으로 되돌린다. 기준 커밋으로 전체 reset/clean하지 않고 그 사이 생긴 사용자 변경을 보존한다. DB/캐시 변경·마이그레이션이 없어 데이터 롤백은 필요하지 않다. RF-001 완료 후 멈추며 RF-002를 자동 실행하지 않는다.
