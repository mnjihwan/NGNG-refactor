## 목표와 정적 근거

### 호출자·기존 테스트

- frontend `app/login/loginPage.tsx`는 `/api/login`에 form POST하고 401을 처리하며 `my_page/_utils/auth-header.ts`의 setAccessToken으로 Authorization을 저장한다. 해당 helper는 토큰 부재에 빈 문자열을 반환한다. `product/_utils/auth-header.ts` 등 일부 helper는 부재값을 문자열 `undefined`로 만들 수 있다. 서버가 이 문자열을 누락으로 취급할지는 별도 결정이다.
- my_page/product/chat API에는 재발급 헤더를 저장하는 호출이 있다. 헤더를 보내는 모든 호출자가 저장하는지는 전수 검증하지 않았다. 브라우저 refresh cookie 전송·재발급 후 다음 요청·동시 응답 순서는 미검증이다. 프런트 동작 개선을 자동 포함하지 않는다.
- chat frontend의 STOMP publish와 HTTP 호출은 별도다. chat-server main에서 TokenFilter/JWT/Authorization 연결은 검색으로 찾지 못했다. 이것은 chat-server 전체 보안 검증이나 배포 라우팅 확인을 뜻하지 않는다. websocket 인증 변경은 범위 밖이다.
- backend 기존 controller 테스트는 `addFilters=false`, RF-001/003/004 계약 테스트는 standalone MVC 중심이다. 기존 test 소스에서 TokenFilter/JwtToken 직접 테스트를 찾지 못했다. 기존 통과 건수를 RF-005 인증 증빙으로 사용할 수 없다.
- build.gradle에는 starter-test, spring-security-test, JJWT 0.11.5가 이미 있다. 새로운 라이브러리 없이 격리 테스트를 설계할 수 있으나 현재 의존성 캐시·실행 가능성은 확인하지 않았다.

## 범위·불변 조건·접근

최초 분석 담당 범위는 계획 문서 작성뿐이었다. 이후 사용자 지시에 따라 아래 세 정책의 최소 구현과 외부 연결 없는 변경 전후 JWT/필터·실제 SecurityConfig 체인 회귀를 수행했다. 운영 수정은 TokenFilter·JwtTokenVerifier 2개, 신규 테스트는 TokenFilterTest·SecurityChainTest 2개다. 기존 SecurityConfig/matcher·발급기·로그인/로그아웃·frontend/chat-server·의존성·스키마는 변경하지 않았다. DB·외부 서비스·성능 실행은 하지 않았다.

최소 구현은 TokenFilter의 입력/검증 분기와 JwtTokenVerifier의 raw compact JWT 파싱 경계다. 기존 verifier getter/parseToken API는 유지했다. `SecurityConfig`는 실제 회귀검증 대상이며 matcher·권한표·CORS·CSRF는 변경하지 않았다. claims를 재사용하지만 성능 개선으로 주장하지 않는다. JWT 입력 처리만 catch하며 downstream chain은 catch 밖에 두었다.

불변 조건: 정상 access의 principal/authority 및 endpoint 결과, 정상 refresh의 동일 요청 계속 처리와 Authorization 재발급, access 우선순위, 기존 로그인/로그아웃·발급 응답/쿠키 속성, 역할별 인가 표, 비즈니스 서비스 호출 및 DB 규칙. 재발급 성공 후 downstream 실패에서도 헤더가 이미 설정되는 현재 경계는 관측 후 기록한다. 승인 없는 claim 필수값·role whitelist·폐기 목록·회전·DB 재조회 추가 금지.

RF-006/007/008/020/021, RF-004 보류 결함, 쿠키 배포 속성·CSRF/CORS·브라우저 저장 방식·외부 writer는 별도 후보다. 과도한 공통 인증 추상화나 전체 예외 처리 재설계를 하지 않는다.

## 사용자 정책 결정 — 2026-11-05 세 항목 승인

1. **refresh fallback**: 권고안은 Authorization 누락·빈 값·정상 서명이지만 만료된 access에 한해 유효 refresh로 같은 요청을 계속한다. 변조/형식 오류/잘못된 type/`undefined`/공백-only 헤더는 refresh가 있어도 401로 거절한다. 누락 헤더를 재발급 대상으로 만드는 것은 현재 NPE 경로의 동작 변경이므로 승인 필요. 대안은 모든 access 실패에 fallback 또는 누락도 즉시401이다.
2. **토큰 형식·type**: 권고안은 헤더에 정확한 `Bearer `+type=access, refreshToken 쿠키에 raw JWT+type=refresh를 요구한다. 무접두사 access·교차 타입의 기존 수용을 중단하는 변경이다. subject/role/exp 부재 및 잘못된 자료형은 인증 불가로 401 처리하는 안까지 승인 범위를 명확히 한다. 허용 role 확대/축소는 별도다.
3. **실패 응답·공개 경로**: 권고안은 인증 입력 거부를 기존 명시 분기와 같은 빈 본문401로 통일하고, 권한 부족은 기존 chain의 403 계약을 검증·유지한다. 새로운 JSON body·WWW-Authenticate·cookie 삭제는 추가하지 않는다. skip/matcher 불일치는 이번에는 현행 유지·특성 기록하고 공개 범위 조정은 별도 결정한다. 실제 기존 응답이 예상과 다르면 관측을 보고하고 승인 없는 통일을 하지 않는다.

사용자는 위 세 항목을 각각 승인했다. 승인 내용은 누락/빈/서명 유효 만료 access만 fallback, 형식·타입 오류/변조 거부, Bearer access/raw refresh 및 필수 claim 검증, 빈본문401·기존403 유지·공개 접근 범위 유지다. 앞선 권고안 표현은 결정 경위를 남긴 것이며 현재 이 세 정책은 확정됐다. 이 분석 담당은 문서만 작성했으며 구현·검증 착수와 결과는 후속 담당이 별도 기록한다.

## 변경 전후 검증 계획

1. 먼저 운영 코드 무변경 상태의 직접 필터/JWT 특성 테스트를 확보한다. 실제 verifier/provider, 테스트 전용 임의 키와 결정적 미래/과거 exp, mock servlet request/response 및 chain spy를 사용한다. Spring application.yml·실서비스 키를 로드하지 않고 DB/Redis/ES/메일/SMS/S3 bean이나 서버를 생성하지 않는다. SecurityContext는 각 테스트 전후 정리한다.
2. 별도 최소 web context에 실제 SecurityConfig/FilterChain과 대역 AuthenticationManager·업무 controller/service를 구성한다. 애플리케이션 컴포넌트 스캔 없이 필요한 bean만 명시하며 신규 의존성은 추가하지 않는다. `@WithMockUser`만으로 JWT 경로를 우회하지 않고 실제 서명 토큰으로 검사한다. 이 구조가 외부 연결 차단을 입증하지 못하면 실행 전 멈춘다.
3. 승인 정책으로 수정 후 같은 정상/인가 회귀와 실패 기대값을 검증한다. 결함 특성 테스트의 변경 전 결과와 승인 후 기대값을 별도 보존한다. MockMvc는 실제 Boot 오류 dispatch/컨테이너/브라우저 검증이 아님을 표시한다.
