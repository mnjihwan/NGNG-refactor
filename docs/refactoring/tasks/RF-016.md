# RF-016: 사용자·포인트·인증 최소 격리 검증 기반

- 상태: 부분 완료 — A 제한 기반·선택 검증·독립 최종 리뷰 완료. B는 준비 코드만 있으며 runtime identity 미확인으로 실행 보류. 물리 MySQL/전체 RF016은 미완료다.
- 우선순위: P1, [재평가 1B](../BACKLOG_REASSESSMENT_2026-11-10.md)의 R1-통합 선행 기반. 기존 선택 mock 테스트를 전체 통합 통과로 바꾸지 않는다.
- 대상: NGNG-backend. 분석 기준 HEAD `82aa7279886385bc0974ae78679ab492447f4135`, 시작 `git status --short`는 `?? .tmp/`뿐이며 기존 파일을 보존한다.

## 목표와 근거

`UserControllerTest`와 `point/PointControllerTest`는 기본 `@SpringBootTest`, `addFilters=false`, 고정 `jin@gmail.com` 및 사용자 ID 1에 의존한다. User 테스트는 수동 transaction과 테스트 transaction을 함께 사용하고 `sendEmail()`에 실제 `@Test`가 붙어 있다. `sendMessage()`는 현재 `@Test`가 없어 실행되지 않지만 안전 발송 대역이 있다는 뜻은 아니다. 기존 테스트를 그대로 실행하면 최신 RF020/041/042 주체 정책과 fixture도 맞지 않을 수 있다.

기본 SpringBootTest가 있는 기존 클래스는 사용자/포인트/검색/신고/제재/상품/거래 controller와 거래 service 2개, 총 9개다. `src/test/resources/application.yml`은 로컬에 존재하지만 `git ls-files`에는 없고 `spring.jpa.hibernate.ddl-auto: update`가 있다. 실제 자격값은 증빙에 복사하지 않는다. 테스트 전용 profile 이름만 붙이거나 loopback 주소로 바꾸는 것만으로 기본 설정·자동 구성·실발송 격리를 보장할 수 없다.

|---|---|---|
| DB/JPA/DDL | test application.yml, `build.gradle` JPA/MySQL; User/Point Boot 전체 탐색 | 명시 테스트 classes, 기본 config 파일 비로딩, 자동 구성/컴포넌트 scan 없음. A에는 DataSource/EMF/transaction manager 없음. B에서만 검증된 DataSource+제한 엔티티/repository 등록, Hibernate validate 및 JPA schema generation none·SQL init never |

## 범위와 제약

- 우선 구현 허용 제안: `src/test/java/com/ngng/api/isolation/`의 RF016 전용 configuration, 합성 fixture, safety guard 및 선택 테스트와 RF016 문서. 기존 production 설정/소스·기존 Boot 테스트를 일괄 변경하지 않는다. 구현 담당이 실제 허용 파일을 결과에 확정한다.
- 인증 필터/주체/업무 계약은 유지한다. A의 실제 JWT→SecurityConfig/TokenFilter→AuthService→point service 경로와 repository 대역을 분명히 표시한다. `@WithUserDetails` 고정 외부 계정 대신 fixture별 합성 JWT/role을 쓴다.
- 신규 라이브러리·스키마·인가 정책·대규모 구조 변경은 별도 승인 대상. H2/Testcontainers 등 신규 의존성을 자동 추가하지 않는다. commit/push 없음.
- 성능, 전체 test/build, 실서버 HTTP/브라우저, Redis/ES/거래/상품/채팅 전체 기반은 이번 최소 단위 밖이다. R2 관리자 Page 물리 기능 잔여도 별도 후속 시나리오이며 A 통과로 닫지 않는다.

## 접근 및 위험

### A. 지금 가능한 로컬 기반

기존 Spring/Mockito/JUnit만으로 `@SpringBootTest(classes=전용 Configuration, webEnvironment=MOCK)`와 명시 MVC/Security/필요 bean을 구성한다. 운영 `@SpringBootApplication`/`@EnableAutoConfiguration`/광역 scan을 가져오지 않는다. test 전용 config location과 합성 property만 허용하고 기본 application.yml 유입 여부를 검사한다. Boot test bootstrap을 거쳤더라도 제한 context이며 전체 운영 Boot 통합이라고 부르지 않는다.

외부 `spring.config.import`, additional-location, profile별 config와 환경/시스템 property를 통한 재유입은 context refresh 전에 거부하거나 테스트 전용 값으로 고정한다. 명시 import의 전이적 `@Import`/auto-configuration도 등록 전 검토하고, 필요한 Jackson/MVC만 선택한다. context 생성 뒤 bean inventory 검사는 이 예방 조치를 보완한다. 이 제한된 구성 검증은 임의 외부 JVM agent/전역 코드의 네트워크까지 통제하는 OS 수준 방화벽 증거가 아니며, 설정 출처나 import 경계를 확인할 수 없으면 context를 실행하지 않는다.

구성 후 등록 bean뿐 아니라 bean definition·자동 구성/프로퍼티 출처도 검사하여 DB/Redis/ES/SMTP/AWS/Nurigo 생성 경로가 없는지 확인한다. 예상 밖 bean을 찾고 나서야 네트워크를 막는 사후 assertion은 예방책으로 충분하지 않다. 예방은 명시 등록/자동 구성 미활성화로, assertion은 회귀 감지로 구분한다. 대역 호출 횟수·합성 상태/응답을 검사하고 test마다 reset, SecurityContext 정리, context close를 확인한다.

작은 smoke 범위는 사용자 조회·포인트 최신/이력/충전 및 잘못된 인증 거부, 실제 메일 service+sender 대역의 중복/신규 분기다. SMS service 대역 응답은 실제 SMS 구현 검증으로 세지 않는다. 모든 사용자/role/point는 테스트 내 소유 객체이며 email은 `example.invalid`, key는 합성 전용이다.

### B. 물리 MySQL 최소 fixture와 실행 gate

현재 읽기 전용 host 조사에서 선택 포트 listener 출력이 없었지만 조회 오류 억제 상태여서 서비스 부재로 확정하지 않았다. Win32_Process CIM 조회는 접근 불가였다. **현재 process/listener/datadir 및 DB identity가 미확인**이다. DB 연결·서버 구동·쓰기는 이 단계에서 하지 않는다. 사용자의 일반 1B 기능검증 요청과 특정 환경의 안전 확인을 구분한다. 과거 승인을 새 작업으로 자동 확대하지 않으며, 반대로 작업 번호가 달라졌다는 이유만으로 모든 로컬 검증에 새 승인을 요구하지 않는다.

1. 실제 실행 전 대상 주소·port·schema·계정·전용 process/datadir·현재 실행 여부, 사용할 테이블(user/point_history/user_role), fixture/정리 범위와 DDL 미실행을 구체적으로 보고한다. 현 세션 지시 범위와 안전성 확인을 통합 담당이 판단한 뒤 연결을 진행한다. 새 서비스 시작·스키마 생성·권한 확대가 필요하면 자동 실행하지 않는다.
2. endpoint를 allowlist하고 loopback listener 소유 PID·실행 파일·datadir/기동 인자를 읽기 전용 확인한다. 확인 실패/불일치는 연결 전 중단. 연결 허용 뒤 DB명/CURRENT_USER/version/port/datadir/isolation, engine·PK/FK/DELETE rule 및 필요한 컬럼을 읽기로 재확인한다. 자격값/개인 절대경로는 출력하지 않는다.
3. user/point는 전용 빈 대상 원칙, role 원본 전체를 보존한다. 기존 role은 읽기 전용 참조 가능 여부를 확인하고 없으면 고유 marker role을 생성하는 범위를 보고한다. 실제 Security/JWT 역할 시험에 임의 marker role을 USER로 오인시키지 않는다. 역할 정책과 fixture identity를 분리하고, 기존 역할행 UPDATE/DELETE 금지.
4. identity 검증 후에만 제한 JPA context를 만들고 DDL validate, SQL init never, schema-generation none을 명시한다. schema 불일치는 실패로 종료하며 update/create fallback 없음. 식별된 대상이 바뀌면 기존 guard 결과를 재사용하지 않고 재확인한다.
5. 고유 run marker+생성 PK+불변 필드를 commit 전부터 추적한다. 테스트 소유 사용자·초기 포인트와 `updateCost`가 생성하는 이력의 추적 방법을 실행 전에 정의한다. 실제 repository save에 위임하는 테스트 관찰 경계에서 반환 PK·user ID·beforeCost/addCost/cost/type/typeDetail 등 삽입 불변값을 즉시 ledger에 기록하고 flush 이후에도 유지한다. 사용자 하위 행 전체를 사후 조회하여 소유행으로 간주하지 않는다. 생성 PK를 얻지 못한 실패·commit 결과 불명·ledger 밖 행이 있으면 cleanup을 중단한다. timeout/실패/부분 setup에도 추적표를 유지한다.
   정상 service 호출은 테스트 외곽 transaction 없이 완료시키고 새 독립 연결에서 해당 PK/값이 commit되어 보이는지 확인한다. rollback은 실제 service가 INSERT/flush까지 수행한 뒤 테스트 관찰 경계가 의도한 예외를 던지게 하여 service transaction 종료 후 독립 연결에서 해당 행 미반영과 기존 잔액/이력 불변을 관측한다. 단순 테스트 transaction의 자동 rollback을 service commit/rollback 검증으로 대체하지 않는다.
6. 모든 worker 종료 후 대상 identity 재확인, 소유행/유입 FK를 먼저 검사한다. 알 수 없는 참조·identity 변경은 전체 cleanup transaction을 중단한다. point→user→생성한 role 순서로 정확한 PK+identity 조건 DELETE하고, 별도 조회로 commit된 삭제와 기존 role 원본 불변을 확인한다. TRUNCATE/전체 DELETE/auto_increment reset/광역 key clear 금지. 미정리 시 PK/marker만 남기고 수동 읽기 검토 조건을 보고한다.

RF003의 특정 사용자 ID 하위 이력 삭제 방식을 무검토 복사하지 않고 RF004의 미추적 참조 거부를 적용한다. 향후 Redis 묶음은 전용 namespace·정확한 생성 key ledger·값/소유권 확인·해당 key만 삭제가 필요하며 FLUSHDB/FLUSHALL을 금지한다.

A는 실제 JWT/filter와 repository 대역, B는 실제 JPA/service transaction과 합성 SecurityContext 인증을 사용하는 별도 구성이다. 각각 통과하더라도 두 결과를 합쳐 JWT→실DB 전체 통합 통과라고 기록하지 않는다. 실제 JWT/filter+JPA를 같은 요청에서 검증하는 연결 범위는 추가 명세·안전 설정이 필요한 잔여다.

## 검증 및 완료 조건

- A 실행은 새 클래스 이름을 명시한 `gradlew.bat test --offline --no-daemon --rerun-tasks --tests <RF016 전용 클래스>`만 사용한다. 전체 suite 또는 기존 MySQL opt-in을 함께 켜지 않는다. 실제 클래스·명령·결과를 증빙에 기록한다.
- A 완료: config 유입/bean 경계·합성 fixture·성공/거부 응답·발송 대역·정리가 실제 실행되고 독립 리뷰됨. A만 완료하면 **RF016 전체/물리 통합은 미완료**.
- B 완료: 현 identity 기록, DDL/외부 부작용 차단, 소유 fixture 성공/실패·rollback·정확 cleanup/별도 사후 조회를 실제 실행하고 원시 XML/console 및 비밀 제외 검증 근거를 보존, 독립 리뷰됨.
- 환경 guard의 missing opt-in/잘못된 endpoint/identity mismatch/미추적 참조 거부는 실제 외부 주소 접속 없이 fake metadata/데이터 소스로 단위 검증한다. skip은 통과가 아니다.
- 롤백: RF016 테스트·문서에서 본 작업 diff만 되돌린다. DB 실패 정리는 위 소유 identity 절차로만 수행하고 사용자 변경/기존 role을 덮어쓰지 않는다.

## 작업 결과와 검증 한계

2026-11-10 현재 이 작성 담당은 정적 분석 및 host 읽기 시도만 수행했다. 소스/설정/테스트 변경·실행, DB 접속·쓰기·서비스 구동은 없다. 상세 [증빙](../evidence/RF-016/README.md). 공통 독립 계획 리뷰는 A 착수 가능, B는 환경 gate 확인 뒤 가능으로 판정했다. 리뷰의 commit/rollback 독립 연결 관측·service 생성행 ledger·A/B 해석 분리·외부 config 재유입 지적을 위 계획에 반영했다. 이는 구현/실행 완료 리뷰가 아니며 B 안전 확인 실패 시 보류한다.

## 2026-11-10 A 구현·B 준비 — 최신 기록
