## 목표와 근거

한 상품의 거래 요청 수락을 반복하거나 경합시켜도 승인된 정책에 따라 하나의 거래와 일관된 요청 상태를 유지하고, 중간 실패 시 상품·요청·거래 쓰기가 함께 rollback되는지 확인한다. 정상 최초 수락의 요청/응답과 거래 생성 정보는 유지한다. 성능 개선은 목표가 아니며 측정하지 않았다.

다음 backend 경로는 `NGNG-backend/src/main/java/com/ngng/api/` 기준이다. 행 번호는 위 HEAD 기준이다.

확인된 것은 **보호 검사 없이 생성이 다시 시도되는 코드 경로**다. 실제 중복 행 생성·unique 위반·교착·HTTP 500 발생은 재현하지 않았다. local DDL과 같은 unique가 실제 DB에 있으면 반복 생성은 중복 저장 대신 제약 오류로 끝날 수 있다. 따라서 “중복 거래가 이미 발생했다”거나 “트랜잭션이 없어서 부분 커밋된다”고 단정하지 않는다. 현재 수락의 바깥 트랜잭션이 정상 적용된다면 unchecked 예외 시 rollback되는 구조이며 실제 flush/commit 결과는 별도 검증한다.

### 호출 관계와 사용자 동작

1. frontend `src/app/chat/[roomId]/_components/RequestProcessModal.tsx`는 “다른 요청은 모두 거절됩니다” 안내와 수락/거절 버튼을 표시한다.
2. `[roomId]/PrivateChat.tsx:64-90`의 onAccept/onDismiss → `_hooks/usePrivateChatMessgae.ts:98-138`의 updateTransactionRequest → `_api.ts:140-165`의 PUT `/transaction/request`. `next.config.mjs:35-36` fallback rewrite가 backend로 보낸다.
3. API helper는 Authorization 요청과 갱신 헤더를 처리하지만 res.ok를 검사하지 않고 JSON을 반환한다. hook은 응답 숫자를 사용하지 않고 수락 시 임시 transactionDetails(id=-1)를 넣으며 mutate Promise를 반환/await하지 않는다. 화면의 then은 실제 수락 완료를 기다리지 않고 모달을 닫을 수 있다. 새 409 JSON을 성공처럼 처리하지 않도록 최소 실패 처리가 필요하다.
4. SWR 재조회는 chat-server `/private-chats/...`를 읽는다. `privateChat/service/PrivateChatMessageService.java:143-152`, `PrivateChatRoomService.java:92-124`는 상품의 거래 및 구매자별 요청을 반환한다. 채팅 엔티티도 같은 테이블명/OneToOne을 매핑한다. 실제 두 서버의 DB 연결 일치와 브라우저 갱신은 이번 정적 분석으로 확인되지 않았다.
5. `TransactionStatusToActiveButton.tsx`는 transactionDetails 유무, request.isAccepted, 판매자 여부로 버튼·거절/진행 표시를 결정한다. 프런트 화면에서 버튼이 숨겨지는 것은 API의 반복·동시 호출 보호가 아니다.
6. 저장소의 main 소스에서 거래 생성 호출자는 수락 service 및 직접 POST controller 두 곳이다. frontend에서 직접 POST `/transaction` 호출은 검색되지 않았다. 외부 소비자 부재를 의미하지 않는다.

인증/인가 확인: update/create 서비스는 요청자 소유권을 검사하지 않는다. SecurityConfig:94-111은 거래 경로에 명시 matcher가 없고 anyRequest().permitAll()이다. 필터를 포함한 실제 도달성은 미검증이며 RF-021의 별도 조사 범위다. 이번 변경으로 인증/인가를 임의 보강하지 않는다.

## 범위와 제약

분석 산출물은 이 명세, `evidence/RF-004/README.md`, BACKLOG와 REFACTORING_LOG다. 아래는 **사용자가 승인한 최소 구현 범위**이며 분석 담당은 현재 소스를 수정하지 않았다.

- backend `transaction/service/TransactionRequestService.java`, 해당 request/details repository, 상품 PK 잠금을 위한 `product/product/repository/ProductRepository.java`, 선택 테스트. 승인된 직접 생성 보호를 위해 DetailsService.create 및 필요 최소 controller 계약 테스트까지 포함한다.
- frontend `_api.ts`의 updateTransactionRequestAPI만 성공 상태/숫자 응답 확인, hook의 Promise 전파, PrivateChat의 실패 표시·성공 후 닫기/재조회가 후보다. 필요 시 요청 모달 버튼 pending 처리의 최소 범위를 먼저 합의한다. 다른 API helper·전역 SWR 키/채팅 UI 재설계는 범위 밖이다.
- chat-server는 호출자 영향 분석만 한다. DTO/메시지 형식·채팅 로직은 유지한다.
- REST 경로와 입력 필드, 정상 최초 수락 200+요청ID, 미존재 404, 최초 거래의 consumer/seller/price/status=1, 다른 기존 요청의 거절 처리를 보존한다. 직접 생성 포함 시 최초 201+Location+DTO를 유지한다. 신규 반복·충돌 응답은 아래 합의가 선행한다.
- 신규 의존성, DB DDL/인덱스, 인증·인가 정책, 캐시 무효화(RF-009), 기존 데이터 복구, 결제·거래 원자성/결제 멱등성, 거래 상태 소유자 ID 비교(RF-006), Exception 상속 정리(RF-019)는 제외한다.
- 요청 생성 중복 방지·수락 도중 새 요청의 처리·상품 재판매/취소 후 새 거래·다른 상품 writer까지의 전역 잠금 규약은 별도 범위다. 승인 없이 추가하지 않으며 “모든 writer의 정합성 보장”으로 결과를 확대하지 않는다.

### 사용자 승인 정책과 위임받은 응답 결정

2026-11-05 분석 중 사용자 답변: 동일 수락 재요청은 거래 구매자/가격 일치 시 무쓰기 기존 성공(200), 충돌 응답 코드는 에이전트 판단에 위임, 직접 거래 생성 경로의 최소 보호·검증과 채팅 API/화면의 실패 시 성공 처리 방지 최소 수정·검증을 승인했다. 인증/인가·스키마·추가 작업은 승인 범위에 포함하지 않았다.

충돌은 **HTTP 409**로 선택한다. 요청 자체의 형식이나 리소스 부재가 아니라 이미 확정된 같은 상품의 거래/요청 상태와의 충돌이므로 400/404나 DB 제약 500보다 의미가 정확하다. 기존 미존재 404, 최초 성공 200/201은 유지한다. 오류 body는 새로운 공통 계약을 만들지 않고 기존 예외 처리 경로의 실제 관찰을 기록한다.

| 결정 | 권장안 및 계약 영향 |
|---|---|
| 같은 요청 재수락 | 사용자 승인: 요청이 이미 true이고 해당 상품의 거래가 구매자/가격과 일치하면 200+같은 요청ID, DB 쓰기 없음. 거래가 없거나 불일치하면 자동 생성/복구 대신 409. 판매자는 최초 거래 생성 때 상품 소유자로 정하는 기존 규칙을 유지한다. request FK가 없으므로 과거 오염 데이터의 진짜 인과관계까지 증명할 수 없음. |
| 같은 상품의 다른 요청 동시 수락 | 상품 잠금으로 직렬화하고 먼저 성공적으로 커밋된 수락만 반영. 후발 요청은 409·무쓰기. 네트워크 도착순/FIFO 우선권은 보장하지 않음. 선행 트랜잭션 rollback이면 후발이 정상 진행 가능. |
| 수락 뒤 거절 | 이미 확정된 수락/거래와의 충돌로 409·무쓰기를 선택한다. 미수락/이미 false인 요청 거절은 기존 200 유지. 기존 TransactionRequestServiceTest.update는 수락 뒤 거절 성공을 기대하므로 기존 특성과 새 기대를 구분해 기록한다. |
| 이미 거절된 요청 다시 수락 | 거래가 없는 경우 현재 코드는 허용한다. 첫 제안은 이 동작을 유지하고, 거래가 있으면 충돌 처리. “거절은 최종” 정책은 추가 기능 변경이므로 묵시 도입하지 않음. |
| forSale=false·visible=false이나 거래가 없는 상품 | 현재는 수락 가능하다. 이번 중복 보호의 단독 guard로 쓰지 않고 기존 동작 유지 권장. 판매상태/제재/삭제에 따른 수락 금지 정책은 별도 확인 필요. |
| 직접 POST `/transaction` | 사용자 승인: 상품 단위 잠금과 거래 존재 검사를 같은 서비스 트랜잭션에 포함해 중복 생성 409·무쓰기. 정상 201 유지. 요청 수락 상태를 자동 변경하거나 forSale을 추가 변경하지 않음. 동일한 직접 POST 재전송도 요청 수락의 멱등 응답과 혼동하지 않고 기존 거래가 있으면 충돌 처리. |
| 프런트 실패 처리 | 사용자 승인: 위 세 파일의 최소 수정·오프라인 검증을 함께 수행. 409/404/서버·네트워크·JSON 오류에서 임시 거래 성공 표시/성공 모달 닫기를 하지 않고 오류를 표시, 필요 시 최신 상태 재조회. 오류 body를 새 공통 DTO로 고정하는 변경은 제외. |

최초 초안은 정책 응답 대기 상태였으나 위 답변을 반영해 최소 구현·오프라인 검증으로 진행할 수 있다. 구현 담당에게 이 명세를 전달하고 독립 리뷰는 실제 diff·증빙을 대상으로 수행한다. 실제 DB 접속/fixture 쓰기는 아래 안전 조건·범위를 확인한 후 진행한다. 합의되지 않은 잔여 후보나 성능 테스트는 자동 착수하지 않는다.

## 접근 및 위험

권장 구현 방향은 기존 쓰기 트랜잭션 안에서 **상품 PK 행을 먼저 잠근 뒤 최신 요청·거래 상태를 재확인하고 변경**하는 것이다. 상품을 공유하는 서로 다른 요청끼리도 같은 직렬화 기준이 필요하다. 요청 행만 잠그면 다른 request ID 경합을 막지 못하고, 단순 `@Transactional` 추가는 이미 존재하는 경계를 반복할 뿐이다. JVM synchronized는 여러 서버 인스턴스를 포괄하지 못한다. version 필드/unique 추가는 스키마 승인 대상이며 이번 최소안에서 자동 도입하지 않는다.

- 요청ID→상품ID 탐색은 먼저 할 수 있으나, 그 단계에서 읽은 관리 엔티티를 잠금 획득 후 최신으로 간주하지 않는다. EAGER 연관/OneToOne 역방향 조회가 먼저 만든 RR snapshot, persistence context의 stale 엔티티, 자동 flush를 고려한다. 잠금 전 target=true로 바꾸지 않는다.
- 상품 PK만 지정한 scalar/current locking read 등으로 잠금 범위를 좁히는 방안을 검토한다. entity PESSIMISTIC_WRITE를 쓰면 eager join에 의해 사용자·역할 등 공통 행까지 잠기지 않는지 검증한다. 실제 SQL·DB 검증 없이 독립성을 주장하지 않는다.
- 상품 → 요청/거래의 동일 lock 순서를 수락·거절과 승인된 직접 생성 경로에 적용한다. 잠금 뒤 요청·거래의 current read/refresh 및 다른 요청 거절의 최신 대상 선택을 검토해 RR snapshot/1차 캐시 결과를 재사용하지 않는다. native bulk 갱신 사용 시 관리 엔티티·updatedAt 의미와 후속 flush 덮어쓰기 위험도 확인한다.
- 비즈니스 충돌과 실제 DB 장애를 구분한다. unique 예외를 같은 rollback-only 트랜잭션에서 잡고 성공으로 반환하거나 모든 저장/잠금 오류를 409로 바꾸지 않는다. 잠금 대기/교착/커밋 실패에는 성공을 반환하지 않고 자동 무한 재시도도 추가하지 않는다.
- 기존 local DDL의 unique는 보조 방어일 수 있으나 현재 실DB·운영과 동일하다고 가정하지 않는다. 스키마가 예상과 다르면 승인 없이 DDL을 실행하지 말고 계획을 재평가한다.
- 수락과 신규 request.create 경합, 상품 수정/제재/삭제, 운영 외부 writer는 이 최소 잠금 규약을 공유하지 않는다. 관측한 기존 요청들의 상태 일관성, 승인된 create/update 경로의 거래 생성 보호를 전체 운영 일관성과 구분한다.

### 실행·DB 안전 계획

1. 위 정책·최소 구현/검증 범위는 사용자 답변으로 확정했다. 실제 DB 대상/fixture 범위는 별도로 확인한다. 기존 RF-003의 user/point/role fixture 승인으로 RF-004 상품·거래 fixture 쓰기를 승인받았다고 해석하지 않는다.
2. 오프라인 기준선과 신규 선택 테스트는 기존 의존성만 사용하고 Boot 전체 설정/YAML·외부 연결을 로드하지 않는다. 전체 기존 test/build는 외부 서비스·고정 데이터·DDL 위험 때문에 실행하지 않는다.
3. 실DB 기능 검증은 별도 대상·행 범위 확인 뒤 수행한다. 후보는 기존 로컬 loopback `127.0.0.1:13306/ngng_local`이나 현재 프로세스/전용 datadir·계정/포트·서버 버전·isolation·InnoDB·PK/FK/unique와 시작 데이터를 새로 확인한다. 과거 RF-003 확인을 현재 안전성 근거로 대체하지 않는다. 자격값/datadir 원문은 공유 로그에 쓰지 않는다.
4. 최소 JPA + 실제 서비스 프록시와 기존 JDBC/MySQL driver로 격리한다. `hbm2ddl.auto=validate`, SQL initializer 없음, Redis/ES/S3/SMTP/SMS 및 Boot autoconfiguration 없음. 신규 테스트 전용 opt-in이 없으면 연결 전 skip해야 하며 skip을 통과로 세지 않는다.
5. 예상 fixture는 user, category, 상품 status, product, product_thumbnail, transaction_request, transaction_details와 transaction_status다. 공유 seller/category/status를 사용하는 다른 상품 독립성 사례를 포함한다. productImages/tags는 빈 연관 collection으로 충분한지 매핑을 확인한다. 인증/role 검증은 범위 밖이며 필요 없는 role/point/chat 행은 생성하지 않는다.
6. **거래 생성은 transaction_status ID=1을 고정 참조한다.** 기존 ID1의 유무·의미를 읽기 확인한다. 없으면 테스트 전용 ID1 행 생성/정리의 명시적 범위 합의가 필요하다. 기존 ID1을 수정하거나 삭제하지 않는다. 이미 존재하는 행을 읽기 재사용하는 경우 전후 불변을 확인하고 fixture로 소유했다고 간주하지 않는다. 일반 generated ID로 만든 status를 hardcode 1의 대체물로 가장하지 않는다.
7. 실행 UUID marker와 생성 PK를 commit 전부터 추적한다. 요청·거래는 marker 열이 없으므로 소유 product ID, user ID, price, request/details PK를 함께 확인한다. cleanup은 worker 모두 종료 후 정확 소유 행만 자식부터 삭제한다: details/request/thumbnail → product → 불필요 FK 참조가 없는 전용 category/status/user 및 직접 생성한 transaction_status. 전체 테이블/볼륨/TRUNCATE/DDL·기존 데이터 삭제는 금지한다.
8. setup/commit/cleanup 실패 시 소유권이 불명확한 행은 삭제 범위를 넓히지 않고 실패·남은 PK를 기록한다. afterAll 및 별도 새 읽기 연결로 marker/소유 ID 잔여0와 기존 참조행 불변을 확인한다. 실제 실행 전 안전성 리뷰와 실행 후 독립 결과 리뷰를 수행한다.

## 검증 및 완료 조건

### 변경 전 기준선

기존 `TransactionRequestServiceTest`는 `@SpringBootTest`와 고정 product6/request9 등 실제 fixture에 의존하며 수락→거절 성공을 기대한다. controller 테스트는 addFilters=false, 고정 계정/ID이며 HTTP 상태만 주로 확인한다. 동시성·반복·중간 실패 원자성 기준선으로 충분하지 않다. 이번 분석에서는 재실행하지 않았다.

구현 전 무외부연결 특성 테스트로 정상 수락의 요청/상품/거래 정보, 다른 요청 거절, 정상 거절, 미존재 -1/404와 최초 직접 생성 201 계약을 확보한다. 반복 생성 호출 및 기존 수락→거절 변이는 **기존 결함 후보 기록**으로 남기고 승인 후 기대와 구분한다. 같은 fixture에서 현재 코드가 항상 중복 행을 저장한다고 가정하지 않는다.

### 합의 후 필요한 검증

| 계층 | 사례 및 판정 |
|---|---|
| 오프라인 service/MVC | 최초 수락/거절·미존재, 승인된 반복/충돌 정책, 기존 DTO·ID/Location 계약. 거부·재시도는 불필요 쓰기/생성 호출 없음. save·매핑·commit 예외를 성공으로 바꾸지 않음. null/바인딩 경계는 기존 관찰과 변경 여부 기록. |
| 실제 MySQL 반복/경합 | 동일 요청 반복·동시 수락, 같은 상품 서로 다른 요청 동시 수락: 승인 응답과 정확 거래 건수/consumer/seller/price/status 및 선택 요청 true·다른 기존 요청 false 확인. 순서는 latch/barrier로 조율하고 sleep만으로 경합이 있었다고 주장하지 않음. |
| 거절/다른 writer | 수락 대 거절 두 순서, 반복 거절, 이미 false인 요청 수락, 기존 거래 불일치/직접 생성 뒤 수락. 직접 경로 포함 시 직접 생성 대 수락/직접 생성 경합도 검사. 승인된 상태 전이와 무쓰기 판정. |
| 최신성/독립성 | 선행 일반 read로 RR snapshot/관리 엔티티를 만든 후 다른 worker commit을 거친 상태도 잠금 후 최신 검사. 같은 seller/category/status인 서로 다른 상품은 한 상품의 미커밋 잠금에 함께 막히지 않는지 확인. Future 상태는 DB 잠금 직접 관측과 구분. |
| 실제 rollback/실패 | 상품 변경 뒤, 거래 insert 실제 flush 뒤, 다른 요청 변경 뒤 오류 및 rollback-only/commit 실패를 분리. 새 연결에서 상품·모든 요청·거래가 전부 이전 상태이고 다음 요청이 잠금을 얻는지 확인. timeout/교착 여부는 의도적으로 검증한 경우만 기록. |
| frontend | 정상 숫자/409/404/500/네트워크/JSON·비숫자 응답에 따른 Promise 전파, 임시 성공 표시/모달 닫기 차단 및 성공 재조회. 기존 TypeScript/Node 도구 대역 테스트, 변경 파일 ESLint·tsc. 브라우저/E2E와 혼동하지 않음. |
| 독립 리뷰 | 승인 정책과 구현 diff, lock 순서·RR/current read·eager 연관·예외/commit 경계, fixture/cleanup 안전성, XML 실제 실행/skip과 전후 확인자료, frontend 오류 전파 및 미검증 기록 확인. |

선택 명령은 새 테스트 파일이 만들어진 뒤 실제 클래스명을 고정한다. 예상 형식은 backend에서 `.\gradlew.bat --offline --no-daemon compileTestJava test --rerun-tasks --tests '<RF004 오프라인 클래스>'`, DB는 별도 opt-in을 설정한 한 클래스만 `--tests '<RF004 MySQL 클래스>'`다. 와일드카드가 기존 SpringBootTest를 포함하지 않도록 명령을 리뷰한다. frontend는 RF004 전용 Node 스크립트와 변경 파일 lint/tsc를 사용한다. 서버 API를 조회할 수 있는 production build는 사전 환경 확인 없이 실행하지 않는다. 명령 예시는 **미실행 계획**이다.

완료는 승인 정책·범위, 오프라인 회귀, 실제 격리 DB의 반복·동시·rollback·cleanup, 필요한 frontend 기능 검증 및 독립 리뷰가 충족된 때 판정한다. 실DB를 실행하지 못하면 오프라인 완료/전체 미완료로 기록한다. 실제 HTTP 보안 필터·Boot 오류 본문, 브라우저, 운영 DB/다른 writer 및 성능은 별도 한계이며 자동 실행하지 않는다. 성능 수치/처리량 효과를 주장하지 않는다.

롤백은 기준 HEAD와 실제 diff를 대조해 RF-004 변경만 선택 복구한다. 전체 reset/checkout으로 사용자나 다른 작업 변경을 덮어쓰지 않는다. 테스트 fixture 삭제는 위 소유권 확인 절차이며 코드 롤백과 별개다. 자동 commit/push 없음.

원시 테스트 XML/실행 로그는 아직 생성되지 않았다. 분석은 소스 경로/기준 HEAD와 이 서술 기록을 근거로 하며 후일 실행 결과는 별도 날짜·환경·원시 증빙으로 추가한다. 기존 작업 원시 결과를 RF-004 통과로 재사용하지 않는다. 이후 결과 변경 시 명세·증빙·BACKLOG·로그를 함께 갱신하며 후속 후보는 자동 착수하지 않는다.

## 2026-11-05 구현·검증 갱신

현재 판정은 **사용자 지시로 보류, 전체 미완료·현재 변경 배포 부적합**이다. 사용자는 Hibernate 내부 API를 사용하는 추가 설계·구현·검증은 진행하지 않고 현재 결과를 기록하도록 결정했다. 이후 운영코드/테스트 수정·테스트 재실행·DB 접속/쓰기는 중단했다. 아래 기록은 위 초기 분석 이력 이후 수행한 실제 결과이며 초기 미실행 기록을 소급 통과로 바꾸지 않는다. 기준 HEAD와 시작 문서 변경을 보존했고 commit/push는 하지 않았다.

### 추가 승인과 구현

- 사용자는 격리 대상·정리 범위 확증 뒤 테스트 전용 user/product/request/details 및 필수 연관 fixture 생성·해당 행만 정리를 승인했다. transaction_status ID1이 없으면 테스트 전용 1행 생성/정리도 승인했으며 기존 행은 변경하지 않는다.
- 첫 구현은 상품 PK 잠금 뒤 요청/거래 scalar current read와 상품·요청 native 조건부 UPDATE를 사용했다. 실제 RR 실험에서 다른 상품과의 gap/next-key 잠금 충돌이 드러나 완료 처리하지 않았다.
- 이 결과를 설명한 뒤 사용자는 **기존 쓰기 트랜잭션을 유지하면서 짧은 별도 읽기 트랜잭션·추가 연결을 사용하는 설계·구현 및 격리 DB 재검증**을 RF-004에 포함하도록 승인했다. pool 설정 변경·의존성 추가·스키마 변경은 승인 범위에 없다.
- 수정안은 상품 행만 scalar PK로 잠근 뒤 flush하여 상위 트랜잭션의 자체 쓰기를 포함한다. request/details ID는 상위 트랜잭션의 own-visible 조회와 repository의 별도 `REQUIRES_NEW/READ_COMMITTED/readOnly` 조회를 합친다. details는 발견한 정확 PK별 current locking read, 다른 요청은 발견한 정확 PK별 조건부 UPDATE를 수행한다. 부재 product_id 범위의 details `FOR UPDATE`와 sibling product_id 범위 UPDATE는 제거했다.
- 직접 create도 같은 상품 잠금·거래 검사 및 기존 쓰기 트랜잭션 안에서 insert/DTO 매핑을 수행한다. 정상201/Location/DTO, request 정상200+ID/미존재404, 기존 create의 상품 부재 assert/NPE 경계와 null requestId의 기존 IllegalArgumentException 경계를 보존한다. 충돌409와 동일 재수락200은 승인 정책이다.
- native 갱신의 updated_at은 DB `CURRENT_TIMESTAMP` 대신 기존 Hibernate6.4.4의 VM Timestamp 생성과 같은 원천인 `Timestamp.from(Instant.now().truncatedTo(MICROS))`를 바인딩한다. 같은 시계 원천·정밀도를 뜻하며 실제 생성 시각이 이전 구현과 동일하다는 주장은 아니다. 근거는 로컬 기존 Hibernate sources.jar의 CurrentTimestampGeneration/ClockHelper다.
- native UPDATE 뒤 기존 관리 객체를 자동 clear/refresh하지 않는다. 현재 controller는 ID만 반환하고 판정은 scalar 최신 조회를 사용하지만, **승인된 service proxy를 상위 트랜잭션에서 사용할 때 관리 Product/Request를 후속 dirty flush하면 native 변경을 덮어쓰는 실제 결함**이 발견됐다. 이는 범위 밖의 단순 후보가 아니라 완료를 막는 정합성 결함이다.
- 프런트 세 파일은 HTTP/숫자 응답 검증, Promise 전파, 실패 표시와 성공 때 닫기/재조회를 최소 변경했다. chat-server·API DTO·인증인가 정책·캐시·DB 스키마·의존성을 변경하지 않았다.
- `.gitignore`는 원시 `local/rf004-results/`의 향후 커밋 혼입을 막고, 정제한 RF004 증빙 로그만 예외로 포함하도록 수정했다. 원시 파일을 삭제하지 않았다. 이 경로는 처음부터 ignored였던 것이 아니며 변경 전에는 untracked였다.

검토만 한 대안: affected1행에 한정한 pending flush 뒤 무락refresh는 own-write 가시성을 이용하지만 affected0/반복 무쓰기·과거RR snapshot까지 해결하지 않는다. 단순 setter는 불필요 dirty write, clear/detach는 caller 후속 변경 유실, 잠금refresh는 eager/gap 잠금 재발 위험이 있다. `@DynamicUpdate`는 엔티티 전체 writer SQL에 영향이 있고 getter stale은 남는다. Hibernate EntityEntry.loadedState와 보호필드를 함께 정렬하는 helper는 불필요 UPDATE 없이 관리 상태를 맞출 가능성이 있지만 내부 SPI·버전 의존·auto-flush 순서·유지보수 부담이 있다. 사용자는 이 추가 설계·구현·검증을 보류했고 **어느 대안도 구현·검증하지 않았다**.

후속 기능·운영 writer·캐시/인가·재판매 정책과 보류된 동기화를 자동 착수하지 않는다. 현재 코드는 실패가 남은 검토용 작업 트리이며 배포/완료 대상으로 표시하지 않는다. 완료는 사용자 재개 지시 뒤 수정안의 실제 DB·정리와 독립 리뷰까지 합의 범위를 충족한 때 판정한다.
