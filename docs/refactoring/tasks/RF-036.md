동일 거래 재전송에서 차감이 반복되지 않는 보장과, 응답을 잃은 클라이언트가 최초 성공 결과를 다시 받는 보장을 구분한다. 사용자별 잔액 잠금은 두 요청을 순서대로 실행하지만 두 번째 차감을 중복으로 판별하지 않는다. RF003의 기존 `repeatedRequestsRemainIndependentAndExistingSingleAndBatchReadsAgree` 및 명세가 이 한계를 기록한다. 이번에 그 테스트를 재실행하지 않았다.

## 범위와 불변 조건

이번 수정은 이 명세와 `../evidence/RF-036/README.md`뿐이다. 소스·테스트·공통문서·Git commit/push·서비스 실행·DB 연결/DDL·성능은 제외한다. 신규 의존성, DB 스키마 및 대규모 구조 변경은 별도 승인 대상이다.

RF035 확정: 기록 consumer 본인만 거래 price로 결제, body 금액 불일치 거부, 직접 생성 거래도 허용한다. 수락 proof/상품 표시가/현재 owner/forSale를 새 필수조건으로 넣지 않는다. 양수·동액 잔액 허용·부족 무쓰기(RF003), 응답8필드(RF008)를 보존한다. 타인이나 ADMIN 제3자에게 이전 성공 결과를 재생하지 않는다. 직접 생성 인가 및 임의 양수 충전 위험은 별도이며 본 작업이 해결하지 않는다.

RF038 확정: 정상1→2→3→4→5, 기록 buyer/seller 행위 제한, 정상 역행·건너뛰기 금지, 6/7→1~5 복귀 금지. 기존 상태→6/7 및6↔7은 허용하며 자동 환불은 없다. 이는 승인된 정책이며 다시 미정으로 만들지 않는다. 결제 proof·같은 상태 응답·RF037 통합 배포는 아직 설계 선택 대상이다.

## RF037과 공동 구현 경계 및 API 호환

1. 입력·인증→상품 PK 잠금→유일 거래 current locking read→buyer/가격 확인→기존 성공 판정(B/C) 또는 상태1 확인(A)→user/latest point 잠금→잔액 검사→이력 append+상태2+receipt(B/C)를 **같은 DB 트랜잭션**에서 commit한다. 저장 receipt/상태만 먼저 별도 commit하거나 afterCommit으로 성공 표식을 남기면 차감과 틈이 생긴다. 성공 replay에는 잔액 재검사·차감이 없어야 한다.
2. RF035 예정 상품→거래→user→point 순서를 기준으로 RF037/038 및 거래 생성/수락·취소/신고 writer를 함께 검토한다. C 키가 다른 거래에 동시에 재사용되는 경우 키 UNIQUE 충돌도 필요하며 단순 존재 조회 후INSERT만으로 충분하지 않다. UNIQUE 예외를 같은 rollback-only transaction에서 삼키고 계속 쓰지 않는다. key/거래 잠금 순서와 재조회 경계는 구현 설계 시 확정한다.
3. public 상태PUT의 최초1→2는 결제 없이 성공하지 못하게 하고, 결제 내부 경로만 실제1→2 수행한다. 프런트의 후속PUT 제거가 우선 후보다. 구버전 호환으로 동일2 무쓰기 성공을 제공하려면 proof가 없을 때 성공을 꾸미지 않는 정책을 별도 결정한다. RF036 단독 잠금·RF038 단독 정상 전이 검사로 두 HTTP 요청을 원자화할 수 없다.
4. A/B는 기존 payment body·URL·성공200/8필드를 유지할 수 있으나 중복409 또는 최초 응답 재생은 의도적 의미 변경이다. C 필수헤더는 기존 소비자를 깨뜨리므로 caller 목록/전환 기간·누락 동작을 확정해야 한다. 선택 헤더만 추가하고 legacy 경로를 무방비로 두면 전체 멱등성이라고 할 수 없다. 프록시 전달·CORS 및 Next API 전달도 검증한다.
5. 전환 시 구버전 writer 제거/차단과 과거 status1/2~7의 불명확 결제 확인을 포함한다. 확인되지 않은 이력에 receipt를 추정 생성하지 않는다. 결제 route만 되돌리고 엄격 상태 route를 남기는 롤백도 부분 기능 장애를 만들 수 있으므로 RF035/037/038 호환 단위로 계획한다. 금전 이력 삭제로 롤백하지 않는다.

## 검증·완료 조건

## 2026-11-11 사용자 확정 및 기존 거래 전환 gate

사용자는 **거래당 한 번만 차감, 처리된 거래의 결제 재요청409 및 거래 상태조회, 응답 재현/요청 키 저장 없음**을 선택했다. A안으로 확정하고 B/C는 비교 이력으로만 남긴다. **변경 전 차감 성공 후 status1로 남았을 수 있는 기존 거래는 확인 전 재결제를 차단**한다. 부족/검증 실패/완전 rollback된 신규 거래의 재시도와, 성공 commit 뒤 재전송409를 구분한다. 상태조회가 과거 포인트 영수증이나 이전 결제 성공을 확정해 주는 것은 아니다. 신고·취소 상태에서도 이미 결제됐다고 단정하지 않는다.

이 선택에는 DB 조회 실행·운영 배포·기존 거래 수정 승인이 포함되지 않는다. 신규 schema는 필요하지 않은 방향이지만 **현재 컬럼만 보고 기존 status1 거래가 미결제임을 자동 확정할 수는 없다.** point_history에 거래 연결이 없고 type_detail 파싱·동액/시각 근접·이력 부재·구매자의 '미결제' 진술만으로 음성 증명은 성립하지 않는다. 기존 거래를 모두 안전한 신규 거래로 간주하거나 임의 날짜 전후만으로 풀지 않는다.

### 무스키마로 가능한 전환과 전제

권고는 **신뢰 가능한 전환 경계가 검증되기 전 결제를 기본 차단하고, 경계 이전 거래를 일괄 격리하는 서버 gate**다. 기존 DB에 표식 컬럼을 추가하는 대신 배포 환경의 통제된 설정/검증 기록으로 경계를 관리할 수 있다. 단순 기능 플래그를 켰다는 사실은 데이터 확인 증거가 아니다.

| 방법 | 정확성·조작방지 조건 / 판단 |
|---|---|
| 모든 결제 fail-closed | 유효한 검증 완료 전환 설정이 없거나 환경 식별이 맞지 않으면 결제 차감0. 충전/조회 등 무관 기능을 함께 중단하지 않는다. 미설정·잘못된 설정을0 또는현재시각으로 기본값 처리해 전부 신규로 열지 않는다 |
| 거래ID high-water mark | 모든 writer 차단/drain 후 검증한 최대ID H는 ID≤H를 기존 거래로 차단하는 보조 기준일 뿐이다. **ID>H도 기존 상품에 대한 과거 고아 차감이 있을 수 있어 자동 허용하지 않는다.** 신규 buyer/price/status1 검사와 별개로 해당 상품·구매자의 과거 미확정 차감 위험 확인이 필요 |
| 상품 생성 경계 추가 | 기존 상품까지 격리하는 데 도움은 되지만 단독 충분조건이 아니다. 변경 전 payment는 존재하지 않는 payProductId도 설명문에 기록하며 차감할 수 있었으므로 미래 상품ID를 참조한 과거 차감 가능성도 있다. 신규 상품/거래라는 이유만으로 과거 차감 부재를 확정하지 않는다 |
| 시각 cutoff 단독 | created_at은 로컬 DDL에서 nullable, clock/timezone·DB 복원·기존 writer 시차 문제. HTTP 요청 시각/클라이언트 날짜·서비스 시작시각만으로 기존 차감 부재를 입증 못 함. 단독 자동 허용 기준으로 채택하지 않음 |
| 기존 거래 개별 해제 | 검증 담당자가 거래·buyer·price·상품·관련 원장/운영 자료를 대조한 기록을 남기고 승인한 명시적 대상만 서버가 허용. 미결제 여부를 확정할 자료가 부족하면 계속 차단. 일반 사용자가 보내는 checked=true·헤더·ID 목록·관리자 역할 자체로 해제하지 않음 |

high-water mark는 **불충분한 보조 경계**이며 이번에 MAX 조회나 운영 확인을 수행하지 않았다. 변경 전 payment는 거래 존재를 검사하지 않아 기존 상품의 고아 차감 뒤 ID>H 거래가 생성될 수 있다. 따라서 writer를 완전히 차단/drain해도 H만으로 이 위험이 해소되지 않는다. 진행중 결제를 남기거나 구버전 결제를 다시 열면 위험은 더 커진다. 기존 endpoint 외부 writer·동일 DB 다른 서비스·배치도 조사 범위다. ID 자동증가만 믿고 배포 중 생성/삭제·복원/수동 PK INSERT·ID 재사용·DB 교체를 허용하지 않는다. 경계 변경은 감사 대상이고 재시작마다 H를 자동 재계산하지 않는다. DB 복원/환경 변경/구버전 재배포가 있으면 gate를 닫고 다시 검증한다.

**안전한 허용 기준은 거래의 나이가 아니라 해당 결제 대상에 과거 미확정 차감이 없다는 확인이다.** 무스키마 최소 구현은 검증된 허용 대상이 없으면 신규ID를 포함해 결제를 차단할 수 있다. 운영 대조(reconciliation)는 상품·구매자·거래와 전체 관련 원장 및 신뢰 가능한 외부 기록의 완전성을 확인하고, 고아 차감·미래ID 참조·동액 다건·자료 누락을 구분해야 한다. 설명문 검색은 조사 단서일 뿐 자동 미결제 증명/해제 기준이 아니다. 충분한 근거가 없는 대상은 계속 차단한다. 사용자 정책에 없는 '신규 거래면 과거 차감 무시' 예외를 만들지 않는다.

검증된 허용 집합을 서버 전용 배포 파일/설정으로 기록하는 대안은 schema 변경 없이 가능하나, 환경·대상 buyer/seller/product/거래·검증 근거·검증자·승인 이력과 변조/복원 방지 운영이 필요하다. 기존 결제 이력 전체가 없음을 확인할 수 있는 신규 구매자 등 별도 안전 집합도 신뢰 가능한 생성/원장 근거와 writer 통제가 확인된 경우에만 검토한다. 자동 추정하지 않는다. 영속 reconciliation 기록을 DB에 추가하는 대안은 감사·운영을 단순화할 수 있지만 별도 schema 승인이 필요하며 선택되지 않았다. 현재 자료만으로 무중단 전체 신규 거래 허용이 안전하다고 입증할 수 없다.

경계 설정은 클라이언트 입력이 아니라 서버 전용 배포 설정이어야 한다. 대상 DB/환경·코드 규약 버전·검증자/검증 시점·writer 차단/drain 확인·H 근거를 보존하고 모든 인스턴스에 같은 값을 적용한다. 필수 값 누락/형식 오류/환경 불일치/허용되지 않은 규약 버전이면 fail-closed를 검증한다. 단순 임의 숫자를 넣은 설정만으로 '검증 완료'를 자동 선언하지 않는다. 서버 설정 권한자가 값을 조작하는 위험은 앱의 일반 사용자 인가로 해결되지 않으므로 운영 권한/감사 통제가 필요하다. 현재 이러한 설정·gate·배포 절차는 구현되어 있지 않다.

기존 거래 개별 해제를 무스키마로 제공하려면 서버의 배포 통제된 allowlist/외부 검증 기록 같은 추가 운영 수단이 필요하다. 거래ID만의 영구 allowlist는 DB 복원·재생성에 잘못 적용될 수 있으므로 환경·불변 거래 식별/검증 당시 buyer·seller·상품·price를 함께 대조하고 불일치 시 닫는다. 미검증 기존 거래가 많으면 운영 부담이 크며 새 스키마 없이 자동 해결된다고 주장하지 않는다. 허용 목록의 포맷·수정 권한·검증 자료·해제 절차는 **아직 확정/구현되지 않은 별도 구체 선택**이다. 개별 해제를 구현하지 않는 최소안도 가능하며 그때는 확인된 기존 거래라도 해당 해제 수단을 승인·배포하기 전 계속 차단한다.

### 확인 근거와 추가 승인 경계

- 확정 정책은 거래당1회/재요청409/키·응답 저장 없음/기존 미확정 거래 차단이다. 이 정책을 다시 사용자에게 선택시키지 않는다.
- 기술 설계는 기존 안전 요구를 만족하도록 구현 검토할 수 있으나 **실제 운영 DB 읽기 조사, writer 정지·배포 cutover, 기존 거래별 해제/금전 보정은 대상·절차·증거가 구체화된 뒤 해당 실행 허용 범위를 확인**한다. 이번 문서 작업은 이를 실행하지 않는다. DB schema·신규 의존성/대규모 구조는 기존 별도 승인 규칙을 유지한다.
- 배포 전 데이터 검증이 자동으로 일어나거나 담당자 확인이 이미 끝났다는 주장은 금지한다. 자료 부족 시 기존 거래 차단 유지가 선택된 정책이다. 사용자 진술만으로 금전 정합성을 추정해 재결제/환불하지 않는다.
- 구현 완료 판정과 운영 안전 전환 완료를 분리한다. gate의 단위/대역 검증이 통과해도 실DB 조사·writer drain·운영 설정 적용·기존 거래 확인은 별도 잔여다. BACKLOG RF036/RF037 및 R3-운영에 추적한다.

추가 검증 계획: 경계 없음/음수·형식 오류/환경 불일치→무쓰기, H−1/H/H+1 모두 미확인 대상 차단, 과거 거래 없는 상품 차감→컷오버 후 신규 거래와 과거 미래 상품ID 차감→신규 상품 생성 반례, 검증된 허용 대상의 신규1 성공 후 응답 유실409, 기존1 최초처럼 보이는 요청409, 과거 상태2~7 무차감, 가격/구매자 검증 우회 불가, 잘못된 allowlist·거래 변경/DB 복원→차단, 구버전 writer 잔존·미완료 transaction이 있는 전환의 실패 판정, 허용 대상 부족/전체rollback 후 재시도 성공. 실제 운영 전환 증거와 원시 결과는 후일 실행 때 별도 보존한다. 이번 갱신은 문서만 수행했으며 테스트·DB·배포를 실행하지 않았다.

## 추가 사용자 확정: 신규 여부와 무관한 검증 근거 기반 허용

사용자는 **이전 차감 위험을 확실히 판별할 수 없는 거래는 신규 여부와 무관하게 차단하고, 검증 근거가 확보된 거래만 결제 허용**하도록 확정했다. 앞 절의 '검토'는 구현 수단에 관한 것으로, 이 차단 정책 자체는 결정 대기가 아니다. 확인 기록이 없는 거래는 재결제 차단 상태이며, 상태1·신규ID·신규 상품·신규 구매자만으로 자동 허용하지 않는다. RF037의 단일 결제 commit과 결합하며 과거 결제 사실을 자동 증명한다고 주장하지 않는다.

### 서버 운영 검증 allowlist의 무스키마 최소 설계안

서버 전용 읽기 전용 배포 파일을 검증 완료 대상의 명시적 목록으로 사용하는 안을 제안한다. 앱의 일반 사용자나 ADMIN HTTP 요청으로 등록하는 새 API는 만들지 않는다. 이 목록은 과거 위험을 조사한 운영자의 승인 입력이지 성공 결제 receipt나 idempotency key 저장소가 아니다. 기존 스키마를 유지하면서 구현할 수 있지만 검증 기록 보존·배포 통제가 필수다.

| 설계 항목 | 요구 동작 |
|---|---|
| 기본 차단 | 파일 부재·읽기/파싱 실패·필수 필드 누락·중복/충돌 항목·빈 승인 근거·미지원 형식/버전이면 결제 gate 닫힘. 거래가 목록에 없으면409/무쓰기. 오류를 빈 검증값이나 전체 허용으로 변환하지 않음 |
| 대상 결합 | deployment/environment ID, 별도로 검증한 DB 인스턴스/복원 세대 식별, 거래ID·productId·buyerId·sellerId·price를 정확히 결합. 잠금으로 읽은 현 거래와 전부 일치해야 허용. 범위/wildcard·ID보다 큼·날짜 이후 규칙은 허용하지 않음 |
| 증거·감사 | 항목별 verification ID, 검증자/승인자·검증 시점·근거 위치/무결성 식별·검토한 원장 범위·해결 판정 보존. 설명문 추정이나 근거 파일 해시가 있다는 사실만으로 미결제 판정을 자동 생성하지 않음. 개인정보/원장 원문을 공개 응답·일반 로그에 넣지 않음 |
| 수명 | 유효 시작/종료와 승인 목록 버전을 명시. 만료·폐기·알 수 없는 시각이면 차단. 구체 유효 기간은 운영 확인 범위에 맞춰 결정하며 임의24시간을 확정하지 않음. 만료 뒤 자동 연장·자동 재생성·새ID 자동 추가 금지 |
| 변조 방지 | 신뢰할 수 있는 배포 경로·서버 파일 권한과 검토 승인으로 목록/기대 버전을 관리. 검증 digest만 같은 수정 가능한 파일에 두는 것은 신뢰 경계가 아님. 별도 서명 체계가 필요하면 키 관리/구조 범위를 검토하고 자동 도입하지 않음 |
| 적용·철회 | 모든 결제 인스턴스의 승인 목록 버전 일치 확인 후 gate 개방. 초기 최소안은 runtime hot reload 없이 통제된 교체/재배포. 철회/교체 시 결제 요청을 차단하고 진행중 transaction을 drain하여 구 목록을 계속 쓰는 인스턴스가 없음을 확인한 뒤 재개 |
| 복원·구버전 | DB 복원/교체 또는 구버전 writer 재등장 시 기존 승인을 무효화하고 gate 차단. DB 자체 값과 목록을 함께 과거로 복원하면 상태2→1이 될 수 있으므로 외부 운영 복원 세대/배포 승인까지 확인해야 함. 자동 감지 구현이 없는 경우 운영 gate/절차의 미검증을 숨기지 않음 |
| 원자성 | allowlist는 과거 위험 확인 gate일 뿐 거래당1회를 대신하지 않음. RF037의 같은 DB transaction 안에서 최신 상태1·buyer/seller/price·목록 binding 확인→차감+상태2 commit. 목록 항목을 DB 밖에서 '소비'한 뒤 차감하는 두 단계는 도입하지 않음 |
| 성공·실패 후 | 성공 후 목록이 남아도 상태2로 재요청409. 전체rollback/잔액 부족이면 유효한 같은 승인 항목으로 재시도 가능하되 현재 상태·금액/주체·만료를 재검사. 재요청409를 '과거 결제 입증' 응답으로 바꾸지 않음 |

후보 파일의 구체 경로/포맷, 환경/복원 세대의 신뢰 출처, 수명·검증 담당 절차는 구현 계획에서 고정하고 테스트해야 한다. 검증 자료가 실제 존재하는지 현재 확인하지 않았으며 자동 검증 도구나 운영 승인 API는 범위에 추가하지 않는다. 목록 생성은 운영 대조 결과가 있어야 가능하다. 대조 기록·승인 플래그를 DB에 새로 저장하려면 별도 스키마 승인, 신규 라이브러리나 대규모 승인 시스템 역시 별도 승인 경계를 유지한다. 이미 확정된 차단 정책을 이유로 신규 스키마 승인까지 추론하지 않는다.

추가 테스트: 파일 없음/잘못된 구문/중복 대상/만료·미래 시작/근거 누락/버전·환경·복원 세대 불일치, 각 binding 한 필드씩 변조, 승인 후 거래 price/당사자 변경, 일반 사용자/ADMIN의 헤더·body 조작, 목록 교체 도중 구버전 서버, 성공 뒤 미소비 목록 재요청409, rollback 뒤 유효 목록 재시도, 복원된 status1과 과거 목록 차단. 대역 테스트로 운영 검증 자료의 진실성이나 실제 복원 통제가 입증됐다고 보고하지 않는다. 이번은 문서 갱신뿐이며 테스트·DB·운영 검증·배포는 미실행이다.

### 독립 리뷰 보완: gate 구현과 운영 개방의 분리

RF037 교차 리뷰에 따라 승인 tuple에는 **기록 sellerId도 필수**로 포함한다. 환경·독립 복원 세대·거래/product/buyer/seller/price·승인 유효기간·증거참조가 모두 일치해야 하며, seller 누락/null/불완전 또는 승인 당시 seller와 불일치하면 fail-closed다. seller는 `TransactionDetails.seller`이며 현재 상품 owner로 대체하지 않는다. 이는 RF036/037 운영 검증 gate의 완전성 조건이고 RF035 단독 buyer/price 정책을 소급 변경하지 않는다. 직접 생성 거래도 같은 gate를 적용하되 수락 요청 존재를 새 필수조건으로 넣지 않는다. seller 필드 누락·변경·owner와 다른 정상 기록 seller의 회귀 검증을 포함한다.

다음 조건은 위 allowlist 제안을 더 엄격하게 구체화한다. 목록과 거래 tuple이 현재 일치한다는 사실만으로 검증 이후의 이력 무결성을 증명하지 않는다.

1. **독립된 운영 신뢰 경로:** 기대 environment/DB 복원 세대/활성 승인 버전은 allowlist 파일 및 복원 가능한 DB와 독립된 통제 경로에서 확인해야 한다. 파일과 DB를 함께 과거로 되돌리면 상호 비교나 같은 파일에 든 hash는 정상처럼 일치한다. 별도 운영 승인·배포 제어/복원 이벤트 차단 근거 없이 자동 복원 감지를 구현했다고 주장하지 않는다. 이 control이 확보되지 않았거나 신뢰 여부를 확인할 수 없으면 gate를 열지 않는다. 구체 제공 수단은 운영 개방 전 확정하며 현재 존재한다고 가정하지 않는다.
2. **보장 기간의 writer 통제:** tuple A→B→A 변경, 거래/상품/사용자 ID 삭제·재사용, 이미 결제한 거래의 status1 복귀, 외부 SQL·구 writer 차감·DB 복원은 최종 tuple 비교로 탐지할 수 없다. 검증 증거의 기준 시점부터 승인 유효기간 종료/철회까지 이런 변경 경로를 배제·통제해야 한다. 현재 schema에는 변경 세대/결제 proof가 없어 이를 보완할 자동 이력 검출을 주장할 수 없다. 통제 불가능한 대상은 허용하지 않으며 이력/버전 저장 schema가 필요하면 별도 승인한다.
3. **검증 전 선행 차단:** 먼저 구버전 payment·관련 거래/포인트 writer와 외부 쓰기를 차단하고 inflight transaction을 drain한다. 그 뒤 원장 조사 범위·마지막 포함 commit/시점·환경·차단 상태를 기록하고 검증·승인 목록을 만든다. 검증 후 gate 개방 사이에도 구 writer 차감을 허용하지 않는다. 관측 후 writer를 막는 역순 절차는 그 틈의 차감을 누락할 수 있으므로 안전한 cutover 근거가 아니다. 승인 후에도 신규 공통 규약 밖 writer를 재개하지 않는다.
4. **구체적인 입력 규약 후보:** 구현 최소안은 UTF-8 JSON object의 `formatVersion: 1`, `approvalVersion`, `environmentId`, `databaseGeneration`, `verifiedAt`, `validFrom`, `validUntil`, `entries`를 요구한다. entries는 양수 Long 범위의 `transactionId/productId/buyerId/sellerId/price`, 비어 있지 않은 `verificationId/verifiedBy/evidenceRef`를 필수로 한다. UTC 시각 형식과 `verifiedAt <= validFrom < validUntil`을 검사하고 승인된 현재 버전만 받는다. 미지원 버전/필드·중복 JSON 필드·동일 거래의 중복 항목·범위 초과 숫자·null/빈 문자열·잘못된 시각은 전체 gate를 닫는다. 빈 entries는 허용 대상을0건으로 둔다. 파일/항목 크기 상한 등 parser 방어는 구현 시 명시하며 새 의존성을 자동 추가하지 않는다. 이 포맷은 구현 후보이며 실제 파일·검증 자료가 이미 있다는 뜻이 아니다.
5. **시계와 snapshot:** `validFrom <= now < validUntil`일 때만 유효하다. clock 신뢰가 확인되지 않거나 backward jump/시각 이상이 감지되면 gate를 닫는다. 단일 앱 시계 비교만으로 잘못 설정된 서버 시계를 완전히 검출할 수 없으므로 운영 시계 동기화/오류 감시 근거가 필요하다. 승인 파일은 시작 시 검증한 immutable snapshot으로 사용하고 runtime reload를 제공하지 않는 최소안이다. 교체·철회 때 모든 인스턴스 결제를 차단/drain하고 활성 버전을 통일한 뒤 개방한다.
6. **잠금 이후 재검사:** 요청 입력·인증 후 RF035 상품→거래 current lock을 획득한 다음 현 tuple·상태1·해당 immutable 승인 항목·독립 기대 버전/환경·유효기간을 재검사한다. 요청 진입 시의 승인 검사만으로 잠금 대기 동안의 만료를 놓치지 않는다. 차감/상태 쓰기 직전에도 유효기간을 확인하고 실패 시 전체 rollback한다. 유효기간은 이 최종 실행 승인 시점의 조건으로 정의하며 DB commit 완료가 만료 전에 끝난다는 시간 보장은 별도 제공하지 않는다. 운영 철회는 drain 완료 전 이미 승인되어 진행중인 commit을 취소했다고 주장하지 않는다.
7. **409의 프런트 처리:** 409 후 거래 상태·포인트 내역을 재조회하되 성공 결제로 단정하거나 자동 payment/상태PUT을 재실행하지 않는다. `/check`가 잔액 부족을 반환해도 상태/포인트 재조회는 가능해야 한다. 화면은 '결제 상태 확인 필요'와 재조회 결과/실패를 구분하고, 과거 상태2나6/7만으로 차감 사실을 꾸미지 않는다. 현재 onPayment의 check 선행 구조를 유지하더라도 재조회 경로는 check 성공에 종속시키지 않는다.
