# RF-007: 상품 수정·삭제의 객체 단위 인가

- 상태: 합의한 최소 구현·선택 검증·독립 리뷰 완료 (2026-11-06)
- 우선순위: P0. 역할 검사만 통과하면 경로 상품 ID로 다른 사용자의 상품을 수정·삭제하는 코드 경로(F03).
- 대상: NGNG-backend, 필요한 실패 처리에 한해 NGNG-frontend. 채팅 서버 변경 없음.
- 기준 커밋: `56d3ec21a72918dd5e6c42c018d12911f13a3345`. 분석 시작 `git status --short` 출력 없음(clean). 루트 AGENTS.md 적용, `rg --files -g AGENTS.md` 결과 하위 지침 없음.
- 사용자 지시: RF별 분석→구현·검증→독립 리뷰. 공식 근거로 기존보다 권장되는 변경은 추가 질의 없이 진행하도록 위임. 성능 검증은 별도 작업으로 유예. 아래 분석·계획 이력을 보존하고 실제 구현·검증 결과를 별도로 기록한다.

## 목표와 근거

### 확인된 현재 구조·호출

- `ProductController.update`의 `PUT /products/{productId}` → `ProductService.update` → `findById().orElseThrow()` → 기존 태그 조회·삭제 → 태그 clear → `Product.from(request)` → DTO 반환. 클래스/메서드 `@Transactional`, `@CachePut(getProduct)`를 사용한다. 검사 지점은 태그 조회·삭제보다 앞이어야 한다.
- `ProductController.updateVisibility`의 `DELETE /products/{productId}` → `ProductService.delete` → 상품 조회 → 기존 OR 조건(신고 null 또는 거래 null 또는 거래 상태6) → visible/forSale false·save 또는 -1. controller는 양수200/ID, 그 외204를 반환한다. 삭제 허용 OR 조건의 타당성은 이번 변경과 분리한다.
- `SecurityConfig`는 PUT/DELETE `/products/**`를 USER/ADMIN에 허용한다. `ProductService.update/delete`는 인증 사용자·소유자를 조회하거나 비교하지 않는다. main 코드의 두 메서드 호출자는 위 controller만 검색됐다. 소유권 누락은 정적 사실이고 운영 악용·발생 빈도는 확인하지 않았다.
- 소유자는 영속 상품의 `Product.user.userId`다. `UpdateProductRequestDTO`에는 userId가 없고 `Product.from`도 user를 변경하지 않는다. 프런트에서 보내는 userId나 path productId를 사용자 ID로 비교하면 안 된다.
- `TokenFilter`가 만든 JWT principal은 ID가 없으며 기존 `AuthService.readAuthUser`가 검증된 email로 DB 사용자를 재조회한다. 역할은 현재 SecurityConfig가 사용하는 Authentication authorities를 기준으로 유지한다. DB role로 새롭게 역할 최신화하거나 refresh 정책을 바꾸지 않는다.
- 관리자 `admin/products/page.tsx:handleDelete`는 모든 상품 목록에서 DELETE를, `admin/products/[id]/page.tsx` → `_api/api.ts:createProduct`는 PUT을 호출한다. 관리자 수정 함수의 이름은 createProduct이나 실제 요청은 PUT이다. 따라서 ADMIN 타인 상품 관리 허용 유지에 구체적인 프로젝트 근거가 있다. 현재 브라우저/프록시 실행은 미확인이다.
- 일반 사용자 `my_page/modify/[productId]/_compoents/UpdateProductId.tsx` → `modify/_api/api.ts`는 PUT 응답을 버린 뒤 무조건 my_page로 이동한다. `my_page/_hooks/useMypageSWR.ts:deleteProduct` → `_api/api.ts:deleteProductById`도 HTTP 실패를 구분하지 않고 판매 목록에서 제거한다. 새 거부 응답을 성공으로 처리하지 않는 최소 연결 수정이 필요하다.
- 채팅 서버 검색에서 이 REST 수정/삭제 호출을 발견하지 못했다. 상품 데이터가 채팅 화면에 미치는 영향은 남지만 공유 DB 전체 writer 안전성을 이번 검사로 보장하지 않는다.

### 공식 근거와 해석

2026-11-06 직접 확인한 [OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)은 객체 ID를 받고 작업하는 endpoint에서 로그인 사용자의 대상 객체 작업 권한 검사를 권고한다. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)는 서버 측 요청별 인가와 관계 기반 검사·인가 회귀 테스트를 권고한다.

이는 현재 역할 검사만으로 타인 상품을 변경하는 경로에 객체 검사를 추가할 근거다. 다만 OWASP가 NGNG의 ADMIN/USER 정책을 정하지는 않는다. **USER는 자기 상품만, ADMIN은 기존 전체 관리 유지**가 일반 사용자 판매 관리 흐름과 명시적인 관리자 수정·삭제 화면을 함께 보존하는 최소 변경이라는 프로젝트 기반 추론이다. 공신력 있는 권고를 적용하라는 사용자 위임 범위에서 이 안을 권고하며, 일반 USER의 타인 수정 허용을 보존해야 할 별도 협업/위임 모델은 저장소 조사에서 발견하지 못했다. 해당 모델의 실제 요구가 새로 발견되면 확대 구현 전에 정책을 재검토한다.

## 범위와 제약

- 운영 backend: `ProductService`의 update/delete 진입 시 공통의 작은 private 인가 검사와 기존 AuthService 주입 등 직접 필요한 변경만. DTO·controller 시그니처·SecurityConfig·TokenFilter·엔티티·repository·설정은 유지한다. 별도 정책 엔진/인터셉터/신규 라이브러리를 만들지 않는다.
- 테스트: 상품 인가 서비스/격리 MVC/실제 보안 체인 선택 테스트 및 fixture. 기존 전체 통합 테스트를 제거하거나 skip으로 바꾸지 않는다.
- frontend: 위 수정 API/호출 컴포넌트와 삭제 API/hook에서 실패 시 이동·목록 제거를 막고 실패를 알리는 최소 처리, 관련 기존 Node 대역 방식 회귀. 관리자 기능은 유지하고 경로/이미지 업로드 문제까지 수정하지 않는다.
- 기존 성공 PUT200 DTO, DELETE200 ID/204, JSON 필드, 없는 상품의 기존 예외, 태그 교체·캐시·트랜잭션·삭제 조건을 유지한다. 새 객체 인가 거부는 403이며 상태·태그·save·캐시 갱신이 없어야 한다. 인증 누락401과 역할거부403은 기존 체인을 유지한다.
- 범위 밖: 생성 userId 신뢰, 이미지/썸네일·업로드·끌올·판매상태의 객체 인가, Confirm/DropOut, 일반 캐시 정합성(RF-009), 삭제 OR 조건, 소유권 이전/위임, 거래경합, role 최신화, CSRF/CORS, 전체 브라우저·운영 DB/성능.
- 신규 의존성·DB 스키마·대규모 아키텍처·전역 인증 정책 변경은 계획하지 않는다. 필요해지면 기존 승인 규칙을 적용한다. 이 명세는 범위 밖 인가 변경을 자동 승인하지 않는다.

## 접근 및 위험

1. 실제 체인과 격리 서비스에서 변경 전 역할×소유권 표를 재현하고 소스·XML·로그를 보존한다. 기존 통합 ProductControllerTest는 addFilters=false/고정 DB·email이므로 인가 근거로 대체할 수 없다.
2. 저장소에서 상품을 얻은 직후, 태그/삭제조건/상태 변경 전 검사한다. 현 인증 authorities가 ROLE_ADMIN이면 기존 관리 허용, ROLE_USER이면 AuthService가 반환한 non-null userId와 상품의 non-null 소유자 ID를 값으로 비교한다. null/null을 소유자 일치로 허용하지 않는다. 인가되지 않은 역할·사용자/소유자 식별 불가를 안전하게 거부하며 새 DB role 정책은 도입하지 않는다.
   - 독립 계획 리뷰 보완: `AuthService.readAuthUser`는 Authentication null 검사 없이 principal을 `CustomUserDetails`로 강제 캐스팅한다. 공통 검사에서는 역할 우회 판단과 AuthService 호출 전에 Authentication 존재·authenticated 상태·지원 principal 타입과 내부 user/email 존재를 확인한다. null 인증, unauthenticated, anonymous/string 등 잘못된 principal은 ADMIN authority가 붙어 있더라도 안전하게 거부한다. 공용 AuthService의 전역 동작은 바꾸지 않는다. `NullPointerException`/`ClassCastException`을 인가 응답으로 대신하지 않는다.
3. 인가 거부를 403으로 연결하는 기존 Spring 예외 방식(AccessDeniedException 또는 좁은 ResponseStatusException)을 검토하고 필터 있는/없는 MVC에서 기대 결과를 고정한다. 광범위 catch로 500을 삼키거나 전역 오류 정책을 바꾸지 않는다. 실패 body는 실제 선택 테스트 관측을 기록하고 Boot 기본 오류 body와 동일하다고 단정하지 않는다.
4. frontend 실패 상태를 전파하고 기존 caller가 처리하도록 한다. DELETE204는 기존 사업조건 거부로서 서버 계약을 보존하며, 403과 구분해 목록 제거가 일어나지 않도록 검토한다. 이것이 기존 204 화면 동작의 부수 결함 수정이면 구현 결과에 명시한다.
   - 독립 계획 리뷰 보완: `my_page/page.tsx`는 deleteProduct Promise를 반환/await하지 않고 `SellHistory`는 먼저 모달을 닫는다. API에서 throw만 추가하면 처리되지 않은 rejection이 생길 수 있으므로 `useMypageSWR` hook 안에서 catch·오류 알림·목록 보존을 완료한다. 기존 모달 닫힘은 유지하며 모달 유지까지 범위를 늘리지 않는다. 수정 API/수정 컴포넌트/삭제 API/삭제 hook의 네 파일 안에서 해결한다. 관리자 DELETE가 응답을 검사하지 않고 재조회하는 기존 문제는 이번 신규 USER 객체거부와 구분하여 R7-범위 별도 후보로 남긴다.

관리자 우회를 없애는 대안은 기존 관리자 흐름을 깨뜨린다. controller에만 검사하는 대안은 서비스 직접 호출 시 우회되므로 서비스 내 작은 검사를 권고한다. 일반 ACL 프레임워크는 두 메서드에 과도하다. 캐시 annotation은 예외 시 갱신되지 않아야 하며 서비스 단위 대역만으로 이를 입증할 수 없어 실제 캐시 proxy 테스트가 필요하다. 동시 외부 소유권 변경·RF004 거래 writer와 경합 해결은 범위 밖이다. 성능 개선을 주장하지 않는다.

## 검증 및 완료 조건

| 실제 체인 역할/소유권 (PUT·DELETE 각각) | 변경 전 기대 특성 | 변경 후 기대 |
|---|---|---|
| USER / 본인 | 기존 사업조건에 따라 성공 | 유지; 같은 값·별도 Long 인스턴스 포함 |
| USER / 타인 | 기존 사업조건에 따라 성공 | 403, 상태·태그·save·cache 무변경 |
| ADMIN / 본인·타인 | 기존 사업조건에 따라 성공 | 유지 |
| UNCONFIRMED_USER / 본인·타인 | 역할403 | 유지, service/repository 미도달 |
| 무인증·잘못된 토큰 | 인증401 | 유지, repository 미도달 |

- before: 합성 JWT + 실제 SecurityConfig/TokenFilter/controller/service/AuthService, repository 대역으로 표를 재현한다. refresh fallback·갱신 헤더와 ID 없는 principal→email 재조회도 확인한다. 네트워크/실제 DB 없는 명시 bean context를 사용한다.
- service: 허용 시 기존 요청 필드/DTO/태그 교체, 거부 시 request 태그 접근/태그 삭제/상품 setter/save 없음, USER null 사용자/소유자/ID, 같은 값 별도 Long, ADMIN 유지, 없는 상품 예외를 검증한다. 삭제 OR 분기(null reports, null transaction, status6, 제한 상태)를 승인 조건 변경 없이 특성화한다.
- 인증 경계 보완 회귀: PUT/DELETE 서비스 직접 호출에서 null Authentication, unauthenticated 토큰(USER/ADMIN authority 포함), anonymous/string principal, null 내부 user/email을 각각 검사한다. 기대는 통제된 거부와 AuthService/태그/상태 쓰기 미도달이며 NPE/ClassCastException이 아니다. 실제 체인에서는 정상 USER/ADMIN principal과 인증 누락/잘못된 JWT·refresh를 재검증하여 앞단401/역할403과 서비스 객체403을 구분한다. 지원하지 않는 principal 타입은 실제 TokenFilter가 생성하는 입력이라고 주장하지 않고 직접 호출 방어 회귀로 기록한다.
- proxy: 작은 in-memory 캐시 manager와 실제 Spring cache interceptor로 허용 PUT 캐시 갱신/거부 PUT 기존 캐시 보존을 확인한다. Redis 실제 직렬화·장애·commit 후 일관성은 별도다.
- controller/MVC: PUT200 응답 필드와 DELETE200/204, 새403·인증401·역할403, 잘못된 path/body400. 실패 request에도 mutable fixture를 새로 만들고 서비스 대역만으로 인가 성공을 판정하지 않는다.
- frontend: 성공, 403/401/500, 네트워크 실패, DELETE204에서 이동·목록 제거 여부와 사용자 오류 처리를 확인한다. fetch/hook 대역과 실제 브라우저는 구분한다.
- frontend 삭제 회귀는 UI가 Promise를 기다리지 않는 호출 형태에서도 hook이 오류를 소비하고 알림을 표시하며 mutate를 호출하지 않는지 확인한다. 처리되지 않은 rejection이 없어야 한다. 기존 모달 닫힘은 유지하며 관리자 DELETE 실패 UI를 이 테스트가 검증했다고 확대하지 않는다.
- 실행 계획: backend `./gradlew.bat --offline test --tests 'com.ngng.api.product.authorization.*' --rerun-tasks` 후 RF005/006 및 관련 RF004 선택 회귀, `./gradlew.bat --offline assemble`; frontend 기존 package scripts와 무의존 Node 테스트 방식 확인 후 관련 테스트·lint·tsc. 실제 명령/실행·UP-TO-DATE/skip은 구현 결과에 기록한다. 테스트 수를 미리 통과로 기록하지 않는다.
- 독립 리뷰: 역할 출처/관리자 흐름 보존, null 식별 안전성, 인가 전 쓰기 부재, API·사업조건 보존, 캐시 예외 경계, 프런트 실패 전파, 문서와 원시 증빙 일치. 분석·구현과 별도 담당자가 리뷰한다.
- 완료 조건: 최소 구현과 위 합의 선택 검증·독립 리뷰 완료. 전체 서비스 보안/운영 검증 완료를 뜻하지 않는다. rollback은 기준 커밋 대비 RF007 변경만 선택 역적용하고 사용자 변경을 덮어쓰지 않는다. 자동 reset/commit/push 없음.
- 성능 테스트는 실행하지 않는다. 별도 사용자 지시와 대표 환경·데이터·측정 설계 후 R7-성능에서 재개한다.

### 해석 한계·미실행과 재개 조건

합의 선택 테스트는 정상 API 결과·역할·객체 거부·대역 무쓰기와 cache interceptor 동작의 근거다.
