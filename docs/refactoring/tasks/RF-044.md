## 인증·역할과 소비자

- SecurityConfig는 `/admin/**` ADMIN 제한이다. 신고자·신고대상·제3자가 USER/UNCONFIRMED_USER이면 관리자 읽기/PATCH에 접근할 정책은 없다. ADMIN은 신고 당사자 여부와 무관한 현행 역할 경계다. 새로운 일반 신고 조회 API나 신고자 열람 권한을 만들지 않는다.
- `/report/**` 단수 matcher와 `/reports` 생성 경로가 다르지만 TokenFilter skip에 reports가 없다. access 또는 유효 refresh 인증 경로를 통과해야 한다. `anyRequest().permitAll()`만으로 익명 공개라고 하지 않는다. 현재 생성은 세 역할에서 처리 가능한 경로이며 RF024가 입력 주체·상태를 별도로 강화할 계획이다. 토큰 role의 DB 최신화/폐기는 RF040이며 RF044에서 변경하지 않는다.
- F/app/product/_api/api.ts:createReport는 응답 `reportId`만 읽어 이미지 업로드에 사용한다. reporter/user를 읽지 않는다. 실패 반환을 무시하는 ReportModal 문제는 RF024 소유다.
- F/app/admin/reports/page.tsx는 reporter/user의 name·nickname, reportId/createdAt/reportType/isReport와 Page 메타데이터를 소비한다. 상세 `[reportId]/page.tsx`는 양쪽 name·nickname 및 **userId**를 `/admin/penalties` 생성 입력으로 사용한다. 상세 본문/상품·채팅 ID/이미지·날짜·처리상태도 유지해야 한다. 관리자 업무의 모든 사용자정보 요구가 조사된 것은 아니지만 현재 화면의 세 필드는 구체적인 보존 근거다.
- backend main의 ReportService 호출자는 두 controller다. PenaltyTran에는 주입 필드가 있으나 실제 update는 ReportRepository로 직접 처리하고 ReportService 응답을 소비하지 않는다. 이 사실은 제재 자체의 인가·입력 정합성을 검증한 것이 아니다.
- **동명 DTO 구분:** B/product/product/dto/response/ReadReportResponseDTO는 별개이며 UserDTO(id/name/nickname)를 쓴다. ProductService.toDTO 및 ReadProductResponseDTO.from의 신고 매핑, F/ProductInfo의 `report.reporter.id`, Chatting의 isReport 소비가 있다. 이 경로까지 관리자용 userId DTO로 바꾸면 계약이 깨진다. 공개 상품의 신고자 이름/본문 공개 정책은 별도 잔여이며 이번 네 응답 축소로 해결되지 않는다.
- chat-server main 및 frontend chat 검색에서 네 신고 응답의 직접 소비를 발견하지 못했다. 저장소 밖 앱·운영 관리자 도구·구버전 클라이언트의 부재는 입증하지 않았다.

## 공식 권고와 최소 변경안

2026-11-11 [OWASP API3:2023 공식 예방 지침](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)을 확인했다. 객체 속성을 명시적으로 선택하고 업무에 필요한 최소 구조와 응답 스키마 검증을 적용하라는 권고를 따른다. 사용자 위임은 이 일반 보안 원칙을 적용한 국소 응답 축소의 근거다. 관리자 업무·신고자 익명성·외부 클라이언트 계약을 OWASP가 결정한다고 해석하지 않는다. 다음은 **아직 구현하지 않은 권고안**이며 순수 계약 보존이 아닌 의도된 보안 응답 축소다.

| 응답 | 권고 | 보존·제거 이유 |
|---|---|---|
| 생성 CreateReportResponseDTO | reporter/user 키 자체 제거, null 키로 남기지 않음. 서비스 매핑에서도 두 연관 getter 접근 제거 | 내부 소비는 reportId뿐. 최소 범위상 다른 기존 최상위 필드는 유지하고 한꺼번에 reportId-only로 축소하지 않음 |
| 관리자 목록·단건·PATCH | 신고 전용 중첩 DTO의 **userId/name/nickname**만 reporter/user에 명시 매핑 | 이름 표시·제재 대상 ID를 보존. User entity나 상품 UserDTO(id)를 그대로 재사용하지 않음 |
| 제거할 관리자 중첩 속성 | email/password/address/phoneNumber/accountBank/accountNumber/role/visible/createdAt/updatedAt | 확인한 화면에서 필요하지 않으며 엔티티 확장에 따른 자동 공개 차단. 권한이 ADMIN이어도 전체 User 반환의 업무 근거가 되지 않음 |

관리자 연관 null이면 중첩 DTO도 null로 유지하고 scalar ID로 새 User를 조회하거나 가상 이름/ID를 채우지 않는다. null→non-null 보정은 기존 의미를 바꾸고 새 조회를 만들 수 있다. non-null User의 null 이름/닉네임도 그대로 보존한다. 현재 UI의 null 연관 대응은 취약할 수 있으므로 기존·변경후 동일 fixture 결과를 분리 기록하고 업무 대응이 필요하면 별도 결정한다.

생성의 나머지 8키 `reportId/reportContents/reportType/isReport/createdAt/updatedAt/productId/privateChatId`, 목록의 기존 10키(두 중첩 키 포함), 단건/PATCH의 기존 12키(visible/reportImages 포함)를 유지한다. detail/update의 visible은 DTO에 있으나 mapper에서 설정하지 않아 null일 수 있으므로 임의 보정하지 않는다. ReportType(reportTypeId/reportType), ReportImageDTO 5키, 날짜·null 포함 여부·숫자 타입·목록 순서·Page 메타데이터·상태 코드·기존 오류 흐름은 축소 항목 외 유지한다. 타입 entity까지 DTO로 바꾸는 확장은 이번 필수 변경이 아니다.

전역 User JsonIgnore/mapper 변경은 다른 API 파급이 커 제외한다. password 한 필드만 막는 안은 나머지/미래 필드 공개를 남겨 선택하지 않는다. 현재 관리자 3필드 이외의 추가 정보가 필요하면 실제 업무 근거·필드별 권한·외부 소비자 확인 뒤 별도 전용 응답으로 논의한다. 생성 응답에 신고대상 연락처 등을 보존하는 정책을 임의 추정하지 않는다.

## 구현 범위·충돌과 위험

- 후속 최소 후보: 신고 응답 DTO 3개, 전용 사용자 요약 DTO, ReportServiceImpl 응답 매핑 및 ReadReportListResponseDTO.from, 격리 선택 테스트. 서비스 인터페이스 반환 타입·repository/엔티티·인증·필터·저장/제재 동작은 유지한다. 현재는 이들 파일 수정 금지다.
- **RF024와 ReportServiceImpl.save 및 신고 controller/MVC 테스트 파일이 충돌할 수 있다.** 입력 정책 RF024와 응답 정책 RF044를 별도 diff로 유지하고 적용 순서를 정한다. 공동 before는 기준 HEAD, 공동 after는 RF024 정책과 RF044 응답 기대를 모두 명시하여 실행한다. RF024 null 초기 상태를 RF044가 false로 바꾸거나 인증 검사를 유실하지 않도록 재검토한다.
- RF008은 패턴·검증 설계 참고이지 신고에 대한 실행 증거가 아니다. RF040 role 정책과 공개 상품 신고정보·이미지 업로드·Penalty 입력 정책, 없는 신고 오류 개선은 별도 후보다.
- 외부 소비자가 제거 속성에 의존하면 깨질 수 있다. API 소비자 목록·관리자 요구 확인과 릴리스 고지를 운영 전 조건으로 둔다. 호환 필요만으로 민감 필드를 무기한 유지하거나 신버전/관리자 예외를 임의 추가하지 않는다.
- 롤백은 기준 HEAD를 참조한 RF044 국소 역패치만 검토한다. RF024·사용자 변경 reset 금지. 민감정보 재노출 가능성이 있으므로 문제 필드만 수정하는 복구를 우선 검토한다.

## 검증 계획과 완료 조건

1. **현재 실행하지 않음.** 기존 ReportControllerTest는 filters=false, SpringBootTest·고정 사용자/행·DB transaction 의존이며 status만 검사한다. 안전 격리가 확인되지 않아 실행 대상에서 제외한다.
2. 합성 User/Role의 모든 후보 속성을 non-null로 채운 before fixture를 네 응답에 주입한다. 생성은 실제 save builder를 유지해 repository가 입력을 그대로 돌려주는 null 연관 경로와 로딩된 User 반환 대역을 나누며 후자를 실제 JPA 생성 결과라고 부르지 않는다. 단건/목록/PATCH는 로딩된 양쪽 User, 한쪽/양쪽 null, 빈/여러 항목, 이미지 유무·날짜 non-null/null을 포함한다.
3. 실제 **JacksonAutoConfiguration ObjectMapper를 MappingJackson2HttpMessageConverter에 명시 연결**한 제한 Boot MVC context를 사용한다. @EnableWebMvc가 만든 별도 mapper와 혼동하지 않게 연결을 assert한다. before write→read JSON tree를 보존하고 after에서 생성은 두 키 제거 외 동일, 관리자는 두 객체를 3키로 투영한 tree 외 동일한지 검사한다. user 중첩뿐 아니라 전체 응답의 금지 키, 정확한 allowlist/null 키/날짜 tree/숫자/페이지 metadata를 확인한다. 생성 mapper가 양쪽 연관 getter를 호출하지 않는지, 관리자 mapper가 허용 3 getter 이외에 접근하지 않는지 별도 검증한다.
4. 실제 SecurityConfig/TokenFilter/JWT 및 controller/service와 repository 대역을 조합한다(필터 off·서비스 전체 mock 결과와 구분). POST는 USER/ADMIN/UNCONFIRMED_USER, 관리자 GET 목록/단건/PATCH는 ADMIN 성공 및 같은 신고자·대상·제3자 USER/UNCONFIRMED_USER의403을 확인한다. 무토큰·잘못된 토큰401 및 적법 refresh의 성공/새 access 헤더, 불량 refresh401을 각 경계에서 검증한다. 거부 시 repository 조회·저장0과 민감 응답 없음. RF024 적용 시 실제 AuthService와 DB 사용자 대역까지 연결해 입력 주체 검사도 보존한다. 이는 실제 로그인 provider/DB/Servlet 서버 검증이 아니다.
5. 정상201/200, PATCH true 저장·DELETE 두키, 미처리 null 필터·정렬/크기/빈Page, 기존 없는 ID 오류를 특성화한다. 응답 축소 중 조회/쓰기·트랜잭션·처리상태가 달라지지 않았는지 확인한다. 기존 오류를 고치는 범위 확대는 별도 판단한다.
