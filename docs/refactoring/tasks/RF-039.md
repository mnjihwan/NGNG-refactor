업로드는 S3 작업이 이미지 DB 연결보다 먼저다. DB 서비스에서만 거부하면 이미 외부 객체가 생성될 수 있다. ThumbnailService.create만 transactional이고 두 controller의 전체 파일 루프와 이미지/썸네일/S3는 하나의 원자적 작업이 아니다. 기존 부분 실패·고아 객체를 인가 guard로 해결했다고 주장하지 않는다(RF015). 이미지 종류/크기/스트림/확장자 정책은 RF034다.

## 최소안과 승인 경계

공식 근거: [OWASP API1:2023 Broken Object Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/). 2026-11-11 통합 담당자가 직접 확인한 예방 지침은 클라이언트 ID로 DB 객체에 접근하는 함수마다 해당 주체의 객체·행동 권한을 검사하는 것이다. 단순 사용자 ID 동일 비교만으로 모든 객체 인가가 해결되지는 않으므로 상품 owner·이미지 소속·ADMIN 행동 권한을 각각 검증한다. 해당 문서는 이 프로젝트의 ADMIN 대리권이나 역할 축소 정책을 결정하지 않는다.

사용자의 공식 권고 적용 위임은 **서버가 인증된 주체와 실제 객체 관계를 검사한다는 원칙**에 적용한다. 재개 후 공통 독립 계획 리뷰에서는 기존 역할 matcher와 관리 UI를 유지하는 아래 최소안으로 구체화했다. 이는 기존 역할 검사를 유지하는 근거 기반 해석이며 새 역할 일괄 제한·관리 기능 확장을 공식 권고에서 추론하지 않는다. 이번 문서 수정은 구현·실행 완료를 뜻하지 않는다.

1. 생성은 **USER/ADMIN 모두 본인만** 허용한다. 서버 조회 ID와 body.userId가 모두 non-null이며 값이 같아야 한다. 서버 ID와 body ID를 비교한 뒤 기존 Product 생성자로 같은 ID를 저장한다. 서버 User 객체를 직접 owner에 할당하는 구현은 아니다. 불일치를 조용히 교체하지 않고 403으로 거부한다. 관리자 수정 helper 이름 createProduct는 실제 PUT이므로 대리 POST의 근거가 아니다. ADMIN 대리 생성 기능은 허용 근거가 없어 이번 최소안에서 배제한다.
2. 기존 상품 끌올·두 업로드·이미지 삭제는 실제 상품 owner 또는 기존 ADMIN 관리 권한을 검사한다. ADMIN 이미지 관리는 실제 caller 근거가 있고 끌올은 기존 역할/상품 관리 경계를 보존한다. **기존 역할 matcher를 유지**하므로 `/products/**`의 USER/ADMIN 제한을 유지하며 별칭 `/upload`·`/deleteImage`의 UNCONFIRMED_USER에는 새 일괄403 역할 제한을 추가하지 않는다. 별칭에서 UNCONFIRMED_USER도 서버 조회 본인 소유 객체만 허용하고 타인은 거부한다. 신원 없는 사용자나 알 수 없는 역할에 관리자 우회를 부여하지 않는다.
3. RF007 guard의 인증 형태/authority·email 조회 및 non-null ID 값 비교를 작은 상품 인가 협력자로 재사용할지 검토한다. RF007 USER/ADMIN 전용 guard를 별칭에 그대로 적용해 UNCONFIRMED 본인까지 거부하지 않도록 **역할 제한과 객체 관계 검사 경계를 구분**한다. DB role을 새 권한 출처로 바꾸거나 일반 인증 프레임워크·전역 Security를 재설계하지 않는다. ProductService 생성/끌올, ProductImageService create/delete/deleteImages, ThumbnailService create/update의 첫 setter/save/delete 이전에 검사한다. 서비스 직접 호출을 controller만으로 신뢰하지 않는다.
4. 두 업로드 진입에서 productId의 **Long 범위 숫자·양수·상품 존재·유효 신원 및 owner 또는 기존 ADMIN 관리 권한**을 **파일 접근(파일명/스트림 포함)·압축·S3 업로드 전 루프 밖에서** 검사한다. 빈 파일 배열·지원하지 않는 확장자에서도 이 검사를 생략하지 않는다. 잘못된 형식·0/음수는400, 존재하지 않는 상품은404, 타인 객체는403인 국소 경계를 계획하며 이 기존 오류 동작 변경을 before/after에 명시한다. Servlet multipart 파싱 자체를 이 애플리케이션 guard가 차단한다고 주장하지 않는다. 저장 서비스에서도 재검사하되 preflight와 서비스 검사 사이의 owner 변화/삭제, 외부 저장 후 실패를 원자성 보장으로 표현하지 않는다. S3 호출 동안 DB 잠금 유지·새 보상 프로토콜은 자동 추가하지 않는다.
5. image delete는 실제 상품 인가 후 **productId+body.imageURL로 조회된 이미지의 실제 상품 소속 관계**를 확인한 뒤 변경한다. thumbnail update는 요청상의 상품 주장 대신 **저장된 thumbnail.product 소유 관계**에서 권한을 확인한다. null caller/owner/ID는 일치 취급하지 않는다. 없는 이미지·썸네일의 기존 예외는 before 특성으로 확보하고 필요한 국소404 경계를 기록한다. 전역 예외 응답 통일은 범위 밖이다.
6. 정상 POST201/refresh200/업로드 Long·별칭 hihi/삭제 이미지ID, multipart 이름, RF007 PUT/DELETE·사업조건, RF009 refresh 성공 커밋 후 대상 key 무효화를 보존한다. 인가 거부 시 캐시 무효화도0이어야 한다. 기존 image/thumbnail writer에는 캐시 무효화가 없으므로 이번에 이미지 캐시 최신성이 해결됐다고 기록하지 않는다(RF010/R9-범위).
7. 프런트 국소 보완은 새 거부가 기존 성공 흐름으로 처리되지 않도록 한다. 관리자 PUT DTO 전체 text를 업로드 productId로 보내지 않고 **실제 응답 DTO의 ID 또는 검증된 기존 product ID**를 사용한다. 이미지 삭제 응답 중 하나라도 실패하면 뒤 PUT/upload를 중단하고 이미 성공한 삭제가 있을 수 있음을 알린다. refresh 비성공/응답유실은 성공 알림을 표시하지 않는다. sell은 생성 성공 후 이미지 업로드 실패·응답유실을 **생성 자체 실패와 다른 부분성공/결과불명**으로 표시하고 알려진 상품 ID를 유지해 동일 상품 POST 재생성을 막는다. 생성 응답 자체 유실로 ID가 없으면 생성 결과 미확정으로 표시하고 자동 POST 재시도하지 않는다. 업로드 응답유실 역시 자동 재업로드하지 않으며 수동 확인·후속 재조회 범위를 명시한다. 다중상품 원자성·일반 중복제출 재설계, 기존 index0 버그 수정, 비활성 이미지 수정 기능 활성화는 제외한다. `/upload`의 `hihi`와 `/products/upload`의 Long 성공 계약은 각각 유지한다. DB 스키마·신규 의존성·대규모 구조 변경·별도 기능 추가는 승인 없이 하지 않는다.

### 독립 리뷰 후 증빙 보완 (코드·테스트 재실행 없음)

독립 코드 리뷰는 차단 결함 없음으로 전달받았고, P2 증빙 지적을 반영했다. 최초 AWS key/private key/Bearer JWT 후보0 탐색은 실패로그의 개인 home 경로·XML hostname까지 확인한 증거가 아니었다. 기존 `none required` 판정은 철회한다.

1. 기존 ignore 규칙이 적용되는 `.local-runtime/rf039-evidence-20261111-raw/`에 RF039 기존 증빙85개와 이 명세 수정 전 byte를 먼저 복사했다. `git check-ignore`로 적용을 확인했다. 원본 hash 보존86개를 검증하며 원본의 값은 공유 문서에 출력하지 않는다. raw 경로는 로컬 전용이며 Git에 추가하지 않았다.
