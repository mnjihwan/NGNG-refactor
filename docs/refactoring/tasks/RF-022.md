### 별도 backend 인증과 프런트

- B/global/security/jwt/util/JwtTokenProvider는 Base64URL secret으로 HMAC 키를 만들고 access에 `Bearer `, sub=email, role, type=access, iat/exp를 발급한다. refresh는 raw JWT/type=refresh다. issuer/audience 및 userId claim은 없다. 실제 알고리즘은 키에 따른 `signWith(key)` 선택이므로 운영 키를 읽지 않고 특정 알고리즘으로 단정하지 않았다.

## 초기 안전 설계 검토 이력 (아래 최신 승인으로 갱신)

사용자가 위임한 공식 권고는 인증된 주체와 객체 권한을 검사하는 방향의 근거다. 그러나 어떤 조직이 키를 공유해도 되는지, 공개 채팅이 익명에게 공개돼야 하는지, 관리자 대화 열람권이 있는지까지 공식 문서가 결정하지 않는다. 다음은 구체적 제안이며 무근거 정책을 이미 승인됐다고 표시하지 않는다.

1. **신뢰된 주체**: REST와 CONNECT가 같은 검증 협력자를 사용하고, access의 서명/허용 알고리즘/exp/type/sub/role을 확인한 후 서버의 email→ID 조회로 principal을 만든다. 필수 claim의 형식·중복 Authorization 거부를 명시한다. client의 STOMP login/passcode/user/simpUser/native ID 및 proxy 헤더를 그 자체로 신뢰하지 않는다. 알 수 없거나 모호한 email은 인증 실패로 처리한다. 탈퇴·visible/역할 최신성은 RF040/042와 정책 연결이 필요하다.
2. **토큰 검증 방식**: 조건부 최소안은 기존 HMAC access를 chat에서도 검증하는 것. 후보 신규 의존성은 Boot 관리 `spring-boot-starter-security`, `spring-security-messaging`, `spring-security-test` 및 검증 라이브러리(기존 backend JJWT 계열 또는 Spring OAuth2 Resource Server/JOSE 중 하나)다. 수동 JWT 암호 구현이나 두 검증 라이브러리 동시 도입은 피한다. chat에 HMAC 키를 주면 검증뿐 아니라 발급 능력도 생긴다. 키 소유·회전·허용 alg가 확인되고 신규 의존성이 승인된 경우만 선택한다. 비대칭 서명/JWKS 전환은 backend 발급 계약 변경이고, 원격 introspection은 현재 endpoint가 없으며 가용성·지연·서버 간 인증이 추가된다. 이 둘은 별도 설계 없이 자동 도입하지 않는다. 신규 issuer/audience 필수화도 기존 토큰을 모두 거부하므로 자동 적용하지 않는다.
3. **CONNECT**: 브라우저 WebSocket handshake 커스텀 Authorization에 의존하지 않고 STOMP CONNECT Authorization에 기존 Bearer access를 보낸다. 인증 interceptor가 인가 interceptor보다 먼저 principal을 설정해야 한다. HTTP upgrade 허용은 인증 완료가 아니며 CONNECT 전 SEND/SUBSCRIBE는 거부한다. refresh cookie를 chat에서 수용/재발급하지 않는 안을 권고하며 만료 시 backend에서 갱신 후 새 토큰으로 재연결한다. 현재 프런트 세 연결부와 onStompError/onWebSocketClose 및 재시도 처리가 함께 바뀌어야 한다.
4. **세션 수명**: CONNECT 시점만 확인하면 만료 후 기존 구독이 계속 수신한다. token exp에서 소켓 종료·구독 해제를 예약하고 SEND/SUBSCRIBE마다 만료를 확인하는 안을 포함한다. 재연결 시 최신 토큰 사용, logout 시 연결 해제는 필수 호환 검사다. 다중 인스턴스 즉시 폐기/역할 변경 강제종료는 기존 인프라가 없어 RF040/028/030 연계 잔여이며 완전 해결로 주장하지 않는다. 참여자 변경이 가능한지 확인하고 가능하다면 기존 구독 철회/발행 직전 수신권한 검증 방식까지 확정해야 한다.
5. **REST 권한**: 방 목록 path.userId와 현재 사용자 일치. 메시지 조회는 path.userId 일치와 저장된 seller/buyer 중 하나임을 모두 확인한 뒤 DTO 매핑/읽음 갱신. 방 생성은 현재 사용자를 buyer로, 실제 상품 user를 seller로 검증하고 body와 다르면 거부; seller가 대신 방 생성 가능한 정책은 근거 부족으로 미확정. 찾기는 저장 방 참여자 또는 방 생성 전 자신의 buyerId+유효 상품 조회만 허용하는 안. 공개 수정/삭제는 실제 message 작성자만 허용하는 안이며 ADMIN 예외는 관리 UI/업무 근거가 없어 자동 부여하지 않는다.
6. **STOMP 목적지**: SEND는 명시한 `/chats/{productId}` 또는 `/chats/{productId}/{buyerId}/{sendToId}`만 허용한다. broker prefix(`/private-chats/**`, `/public-chats/**`, `/alarms/**`) 직접 SEND를 거부한다. 비공개는 body 방을 서버 조회하여 참여자, 발신자=principal, 상품/buyer=path, sendTo=저장 방의 상대임을 모두 확인한 뒤 save/읽음 변경/발행한다. 발행 목적지는 검증된 서버 값으로 만든다. 기존 주소는 유지할 수 있으며 검증 안 된 template 변수로 발행하지 않는다. SUBSCRIBE는 정확한 방 주소에 실제 참여자만, alarms는 자신의 ID만 허용. wildcard/추가 segment/유사 prefix/잘못된 숫자/미지원 목적지는 기본 거부한다.
7. **공개 채팅 정책**: 상품 화면이 로그인 없이 공개 채팅을 보여주는 현재 UI와 공개 GET을 고려하면 익명 공개 읽기/구독을 유지할지 별도 결정이 필요하다. 권고 최소안은 공개 읽기 유지, 작성은 USER/ADMIN으로 제한하되 익명 CONNECT를 허용해야 한다면 공개 SUBSCRIBE만 허용하는 별도 명확한 규칙을 둔다. 모든 CONNECT 인증 필수안과 익명 공개구독 보존안을 동시에 구현했다고 주장하지 않는다. UNCONFIRMED_USER의 채팅권은 backend `/chat/**`의 USER/ADMIN을 참고할 수 있으나 별도 chat 정책 근거는 아직 없다.
8. **응답·origin**: REST 인증 실패401/객체 권한403/대상없음404를 제안하나 미존재와 타인객체 정보노출 정책을 결정한다. STOMP는 REST status가 아닌 sanitized ERROR frame과 연결 종료를 검증한다. 정상 REST DTO 및 STOMP `.body` envelope를 유지한다. 운영 WSS와 명시 origin allowlist를 확인하고 HTTP CORS와 STOMP origin을 구분한다. `@EnableWebSocketSecurity`의 CONNECT CSRF 기본 동작을 고려해 bearer-only인지 cookie/session 기반인지 결정한 뒤 최소 설정을 선택한다. backend 설정을 복사해 전역 CSRF 비활성화하지 않는다.

공통 인증 서비스를 새로 만들거나 게이트웨이에 전부 위임하는 대규모 변경은 최소안에 포함하지 않는다. DB 스키마는 변경하지 않는다. 현재 방 데이터가 상품 seller와 불일치하거나 같은 product/buyer 방이 여러 개면 허용 방 결정이 모호하므로 기존 데이터 확인 없이 자동 보정하지 않는다. 인증 도입 이전 클라이언트와 동시 배포 순서, 만료 시 갱신 경로, 키 공급 방식이 구현 재개 조건이다.

## 공식 근거와 적용 한계

2026-11-10 직접 열람했다. 최신 문서 표시 버전은 Framework7.0.10/Security7.1.2이며 저장소 Boot3.2.4에 코드 예제를 그대로 옮기지 않는다. 구현 전 실제 관리 버전6.x의 API·기본 CSRF·interceptor 순서를 확인한다.

- [Spring Framework Token Authentication](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/authentication-token-based.html): 브라우저 handshake 헤더 제약, CONNECT header + ChannelInterceptor로 principal 설정, 인증 interceptor 선행 순서가 위 제안의 근거다.
- [Spring Security WebSocket Security](https://docs.spring.io/spring-security/reference/servlet/integrations/websocket.html): 메시지 인가, 구독 권한 및 broker 목적지로의 클라이언트 발행 구분, CONNECT CSRF 기본값 검토 근거. 애플리케이션의 특정 역할에 읽기 권한을 부여하는 근거는 아니다.
- [OWASP WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html): WSS, origin 검사, 메시지별 권한·세션 수명 검토의 근거. 운영 프록시 상태나 키 공유 승인을 증명하지 않는다.

## 단계별 검증과 완료 조건

1. 변경 전 실제 controller/service+저장소 대역으로 user/body/path/room 불일치, 공개 수정 ID 의미, GET 읽음 쓰기, ResponseEntity STOMP envelope를 특성 기록한다. 실제 `clientInboundChannel`과 simple broker를 구성한 작은 Spring context에서 익명 SEND/SUBSCRIBE와 broker 직접 SEND 도달 여부를 확인한다. 직접 메서드 호출만으로 채널 취약점 재현이라고 하지 않는다.
2. 전체 Boot component scan/실 datasource 없이 명시 bean만 등록하고 JWT는 합성 키·clock·가짜 사용자를 사용한다. JDBC/AMQP/메일/외부 호출이 없는 harness를 먼저 확인한다. 기존 ChatApplicationTests는 @SpringBootTest여서 무조건 전체 test를 실행하지 않는다.
3. 정책 확정 후 실제 REST SecurityFilterChain+필터+controller/service+저장소 대역, 실제 inbound 인증/인가 순서+broker/handler+outbound capture로 단계별 검사한다. 인증 실패에서는 업무조회/쓰기/발행0; 객체 인가 실패에서는 권한조회만 허용하고 message save/읽음 save/room save/후속 DTO 매핑 및 outbound0을 확인한다.
4. 매트릭스: 미인증/USER/ADMIN/UNCONFIRMED_USER/타인/실제 seller/buyer; 누락/빈/공백/변조/만료/refresh 교차타입/unknown alg/중복 헤더/잘못된 claim/없는 email; 자기·타인·없는 방/상품/메시지, body.userId와 principal 불일치, path와 body 방 불일치, sendTo 제3자, 자기 alarms/타인 alarms, CONNECT 전 SEND/SUBSCRIBE, 재CONNECT/동일 session 사용자 바꾸기, 무목적지/비정상 숫자/wildcard/broker 직접 SEND, 정상과 실패 후 세션 오염을 포함한다.
5. outbound capture로 정상 발행이 정확한 방과 상대 알림에만 도달하고 타인 구독자는 받지 않음을 확인한다. 만료 clock 이동 뒤 기존 구독이 닫히고 이후 SEND/SUBSCRIBE/수신이 중단되는지 검증한다. 거부 후 저장0뿐 아니라 읽음 포인터 불변·상대 알림0·부분발행0을 확인한다. 서버 시스템 발행은 클라이언트 입력 인가와 구별한다.
6. frontend 대역 테스트로 세 클라이언트의 CONNECT header, 토큰 갱신 후 재연결, 실패 시 성공 UI/JSON 오인 방지, 현재 envelope, 토큰 URL/로그 노출 없음, logout 해제·reconnect 중복을 검증한다. RF028 전체 수명 리팩토링으로 확장하지 않는다.
7. 외부 연결 없는 선택 테스트 명령은 구현된 전용 클래스 이름이 확정된 뒤 `./gradlew.bat --offline --no-daemon test --rerun-tasks --tests <RF022 전용 클래스>`로 고정하고, compileTestJava/assemble·frontend 관련 test/lint/tsc를 구분 기록한다. 실행 가능한 명령으로 가장하기 위해 존재하지 않는 클래스명을 미리 만들지 않는다.
8. 통합은 RF016 격리 환경·전용 신원·외부 발송 차단·소유 fixture/정확 cleanup이 확보되고 별도 실행 지시 후 진행한다. 실제 WebSocket upgrade/CONNECT/ERROR/구독 수신·WSS/origin/proxy direct bypass·만료 종료·브라우저 두 사용자와 저장/읽음/알림을 검사한다. mock 결과는 실제 DB rollback·네트워크·운영 보안 완료가 아니다.

분석 완료 조건은 근거/선택지/미확인 게이트와 테스트 계획을 남기는 것이다. 기능 완료는 승인된 정책 구현·before/after 원시 증빙·정상 계약/거부 무쓰기 무발행·독립 리뷰 후 별도 판정한다. 롤백은 RF022 변경만 선택 되돌리고 다른 작업을 reset하지 않는다. 인증 도입 실패 때 무인증 fallback을 롤백 전략으로 삼지 말고 노출 통제와 배포 복구를 함께 검토한다.

## 2026-11-10 사용자 결정 반영 — 최신 최소 설계

사용자는 **기존 backend JWT HMAC 검증 키를 chat 서버에 공유하여 검증**, **필요한 신규 security/JWT 의존성 추가**, **공개 채팅의 익명 조회·구독 유지**, **비공개 채팅은 인증된 참여자만 허용**을 승인했다. 초기의 키 공유/신규 의존성/공개 CONNECT 선택 대기는 해소됐다. 아래 계획의 격리 구현·검증을 위해 같은 승인을 다시 요청하지 않는다. 이번 문서 담당은 코드와 실행을 맡지 않았으며 승인 자체를 구현 또는 검증 완료로 기록하지 않는다.

### 승인 범위와 운영 잔여 구분

- HMAC 공유는 chat에 서명 생성 능력도 전달하는 구조임을 유지 기록한다. 승인된 검증 용도만 구현하며 chat에 발급·refresh endpoint는 만들지 않는다. 키 값을 문서/소스/로그에 복사하지 않고 런타임 비밀 설정으로 주입한다. 운영 키 전달·회전 동기화·폐기·접근권한, 실제 알고리즘/키 길이 확인은 배포 잔여다. 합성 키로 필터/채널 구현·회귀를 수행하는 데 운영 키를 읽을 필요는 없다.
- 최소 의존성 선택은 Boot 관리 `spring-boot-starter-security`, `spring-security-messaging`, 테스트용 `spring-security-test` 및 backend와 같은 JJWT 계열(api/impl/jackson)이다. 기존 backend 선언 버전과 실제 해석된 버전을 먼저 대조해 동일 계약을 사용하고 별도 OAuth2/JWKS 스택은 추가하지 않는다. 필요한 의존성 승인은 있으므로 추가 승인 대기는 없다. 기존 캐시에 없으면 의존성 해석·다운로드 결과를 구분 기록하고 실패를 테스트 성공으로 세지 않는다. 필요 없는 최신 라이브러리 전환을 묶지 않는다.
- JWT는 exact Bearer access/type·서명·만료·필수 문자열 sub/role을 검증하고 sub=email을 서버 조회한 사용자 ID로 연결한다. HMAC 계열만 수용하며 `none`/비대칭·서명 불일치를 거부한다. backend `signWith(key)`와 호환되는 허용 HMAC 알고리즘은 합성 키별 발급/검증 회귀로 고정하고 운영 키 설정과 대조한다. 신규 iss/aud/userId 필수화와 refresh 수용은 추가하지 않는다.
- 운영 프록시/포트 직접 노출/WSS/origin allowlist와 email 유일성/오염행은 여전히 미확인이다. 이 한계는 운영 보안 완료 판정과 배포의 검증 조건이며 외부 연결 없는 구현·검증의 승인 차단 조건이 아니다. 기존 토큰의 역할 최신성·즉시 폐기까지 해결했다고 주장하지 않는다.

### 구현할 세부 정책과 추론 근거

다음 세부사항은 사용자가 각각 직접 선택했다고 주장하지 않는다. 승인된 공개 접근 유지와 비공개 참여 제한, 기존 frontend 호출 형태 및 최소 권한 원칙에서 도출한 최소 구현 판단이다. 별도 근거가 없는 관리자 감청권이나 새 역할 제한을 추가하지 않는다.

| 경계 | 최신 선택과 근거 |
|---|---|
| CONNECT | Authorization 미제공이면 익명 세션으로 CONNECT 허용. 제공된 토큰이 빈값/형식오류/변조/만료이면 ERROR·종료하며 익명으로 강등하지 않는다. 인증 세션은 검증 principal에 묶고 이후 native 헤더로 변경 금지 |
| 공개 REST/구독 | GET `/public-chats/{productId}`, SUBSCRIBE 정확한 `/public-chats/{productId}`는 익명 허용. 토큰 없는 익명 client도 기존 공개 화면 수신 가능. 유효하지 않은 토큰을 보낸 요청은 인증 실패로 구분 |
| 공개 SEND·수정/삭제 | 작성자 식별이 필요한 행위는 인증 사용자만, body.userId=principal 검사. 수정/삭제는 기존 실제 메시지 ID 의미를 유지하고 작성자만 허용. ADMIN 특별 수정권은 추가하지 않음. 별도 USER/ADMIN role whitelist를 새로 요구하지 않고 검증된 인증 사용자 여부로 판단하여 미확인 사용자에 대한 미합의 정책 확대를 피함 |
| 비공개 REST/구독/발신 | 역할 이름과 관계없이 인증+저장된 방의 buyer/seller 참여가 필수. ADMIN도 참여자가 아니면 거부. 목록/읽음 갱신 userId는 자신만. 구독은 정확한 방, 알림은 자신의 ID만 |
| 신규 방 | 기존 구매자 UI 호출에 맞춰 buyer=현재 사용자, seller=실제 상품 소유자 검증. client 지정 seller로 상대를 바꾸지 못함. 동일 사용자 양측 생성 허용 여부 등 기존 사업조건은 인증과 무관하게 임의로 변경하지 않음 |
| 방 찾기 | 자신의 buyerId로 생성 전 방 조회는 허용하고 없는 방404 유지. 다른 buyerId는 존재하는 방의 seller/buyer 참여를 확인해야 조회 허용. 타인/미존재 구분의 상세 객체정보는 반환하지 않음 |
| 실패 | REST 미인증/잘못된 토큰401, 인증됐으나 권한 없음403, 권한 확인 가능한 정상 조회의 없는 대상404. 기존 정상 body/status/envelope 유지. 잘못된 ID/JSON은400 등 기존 MVC 계약 확인 후 고정. STOMP는 민감정보 없는 ERROR 및 연결 종료, HTTP 코드 응답으로 가장하지 않음 |
| frame 허용 | 익명·인증 모두 CONNECT 이후 자신의 UNSUBSCRIBE/DISCONNECT 및 heartbeat 등 프로토콜 정리 프레임 허용. 메시지/구독은 명시 목적지 규칙만 허용하며 broker 직접 SEND 및 미지원 frame/목적지 기본 거부 |

공개 익명 유지 때문에 모든 CONNECT에 `.authenticated()`를 걸지 않는다. 브라우저 공개 client는 토큰이 없을 때 Authorization 헤더 자체를 생략하고 인증 client는 연결 직전에 최신 access를 공급한다. 알려진 만료 토큰을 자동 익명으로 바꾸어 비공개 연결을 재시도하지 않는다. 인증 exp 도달 시 소켓/구독 정리로 기존 비공개 수신을 차단하고 새 토큰 재CONNECT를 요구한다. 익명 공개 세션에는 JWT exp가 없으므로 인증 세션 만료 처리와 구분한다.

HTTP REST와 STOMP 모두 cookie/session fallback 없이 명시 Bearer를 검증하는 최소안이다. CSRF를 기본 요구하는 `@EnableWebSocketSecurity`를 무심코 추가해 익명 공개 CONNECT를 막지 않는다. Boot3.2.4에 맞는 직접 인증 interceptor→SecurityContextChannelInterceptor→AuthorizationChannelInterceptor 구성 또는 동등한 명시 구성을 선택하고 실제 순서를 테스트한다. 필요한 bearer-only CSRF 예외는 chat 경계에 한정하며 backend 보안 설정은 바꾸지 않는다. origin allowlist는 실제 배포값을 주입하는 방식으로 계획하고 운영 도메인을 추측하여 하드코딩하지 않는다.

### 승인 후 실제 실행 계획의 고정점

1. 독립 최소 Spring context에 실제 WebSocketConfig/handler/simple broker와 대역 repository를 명시 등록한다. `clientInboundChannel`에 세션 ID·subscription ID가 있는 CONNECT/SUBSCRIBE/SEND를 순서대로 전달하고 `clientOutboundChannel`을 캡처한다. controller 직접 호출과 달리 broker routing/인가 순서까지 검사하되 실제 WebSocket wire 검증과 구별한다.
2. 익명 세션 A는 공개 구독·공개 수신 성공, 공개 SEND/비공개 REST/SEND/SUBSCRIBE/alarms 거부를 검증한다. 인증 seller B와 buyer C, 타인 D가 같은 공개 목적지를 구독하고 B/C만 비공개 목적지에 접근하도록 검사한다. ADMIN 타인과 UNCONFIRMED_USER 실제 참여자도 포함하여 위 최소 역할 정책을 고정한다.
3. 정상 메시지는 body 저장 방과 path 상품/buyer 및 상대 sendTo 일치, 실제 방 두 참여자의 수신·상대 알림만 허용한다. body.userId 위조/room 교차/path 위조/타인 alarms/broker 직접 SEND는 save0·읽음변경0·outbound 업무발행0을 검사한다. ERROR 같은 프로토콜 발행과 업무 데이터 발행을 분리한다.
4. 합성 HMAC 키와 조절 clock으로 정상/만료/변조/다른 키/교차type/unknown alg/필수claim/중복 Authorization/email 매핑 실패를 검증한다. 인증 토큰이 없는 익명 허용과 잘못된 토큰 거절을 별도 테스트한다. 만료 후 inbound 차단만으로 완료하지 않고 이미 구독한 세션의 후속 수신 중단까지 검증한다.
5. MockMvc 실제 REST chain+controller/service 대역으로 익명 공개 GET, 본인 목록/방 찾기/메시지 조회, 방 생성 seller 파생 검증, 타인 조회의 읽음 무쓰기, 메시지 소유자 수정·삭제와 정상 DTO를 확인한다. 메시징 thread 간 SecurityContext 누출도 검사한다.
6. DB/AMQP/외부 서비스 없는 최소 테스트 실행을 먼저 수행한다. 그 뒤 frontend 대역의 공개 익명/인증 CONNECT·만료 재연결·정상 envelope 및 선택 빌드를 확인한다. 로컬 wire/브라우저·운영 프록시·실DB 검증은 별도 환경 증빙이며 현재 문서 수정으로 실행한 것이 아니다. 위 핵심 승인에 대해 재승인을 요구하지 않는다.

최신 추적: RF022-신뢰는 공유/필요 의존성 승인 및 운영 공급 검증 잔여, RF022-정책은 공개 익명/비공개 참여 확정 및 최소 세부 추론 명시, RF022-격리는 구현·실행 전, RF022-연동은 운영/물리 미검증이다. 초기의 미승인 대안과 미확정 표기는 당시 분석 이력이며 이 절과 갱신한 표가 우선한다.

## 2026-11-10 승인 범위 구현·격리 검증 — chat 서버

초기 문서 전용 분석 이후 사용자 승인과 통합 담당 지시에 따라 chat source/config/dependencies/tests 및 이 명세·RF022 증빙으로 범위를 확장했다. 이 절은 chat 담당 결과이며 frontend와 최종 독립 리뷰는 아래 최종 통합 절에 기록했다. 초기의 “문서만 수정/구현 전” 상태보다 최신 구현·검증 결과가 우선한다.

### 구현과 유지한 계약

- `ChatTokenVerifier`는 backend와 같은 JJWT0.11.5 및 Base64URL HMAC 키 주입(`jwt.secret.key`)을 사용한다. exact Bearer access/type, HMAC HS256/384/512, 필수 문자열 sub/role, raw Number exp와 선택 nbf, 서명·만료를 확인한다. sub=email을 `findAllByEmail`로 서버 조회해 정확히 한 사용자 ID만 principal로 만든다. refresh·issuer/audience 신규 요구·발급 endpoint·cookie fallback은 추가하지 않았다. 잘못된 제공 토큰은 공개 GET/CONNECT에서도 실패한다. JWT parse/claim 형식 오류의 `JwtException`, `IllegalArgumentException`, JJWT0.11.5의 `IllegalStateException`만 인증실패로 변환하고 repository 장애는 해당 catch 밖에 둔다.
- REST는 실제 SecurityFilterChain의 stateless explicit Bearer 필터를 거친다. 익명 공개 GET과 WebSocket HTTP upgrade를 유지하고 다른 REST는 인증을 요구한다. 객체 guard는 controller 위임 이전에 본인 userId/저장 방 참여/상품 소유 seller/메시지 작성자를 검사한다. ADMIN 감청·추가 role 제한은 없다. 방 찾기의 본인 buyer 정상404와 공개 PUT/DELETE의 실제 메시지 ID 의미 및 정상 JSON/status는 유지한다. 읽음 쓰기보다 guard를 먼저 실행한다.
- `ChatChannelSecurity`는 실제 inbound에서 CONNECT 세션 principal을 설정하고 이후 frame native user/Authorization을 주체로 신뢰하지 않는다. 공개 익명 SUBSCRIBE, 참여자 private SUBSCRIBE, 본인 alarms, 허용된 두 application SEND만 통과한다. SEND JSON의 userId/roomId와 path product/buyer/sendTo를 저장 방과 대조한 뒤 handler를 호출하며 broker 직접 SEND와 미지원 목적지는 거부한다. controller에서도 같은 객체 guard를 적용한다. 기존 `ResponseEntity`의 STOMP `.body` envelope 및 정확한 방+상대 alarms 발행은 유지한다. 거부와 handler 실패는 민감정보 없는 ERROR와 소켓 종료로 처리한다.
- `ChatSessions`는 세션별 identity/exp와 예약 task를 보유한다. 실제 production scheduler는 exp에 소켓을 닫고 inbound DISCONNECT로 broker 구독을 정리한다. inbound, outbound business 발행과 decorated WebSocketSession의 최종 sendMessage 직전에 만료를 검사한다. 마지막 전송과 만료는 같은 세션 lock을 사용하며 큐에 들어간 메시지도 검사한다. 다른 exp의 같은 사용자 세션은 독립적이다. outbound private 수신은 현재 저장 방 참여를 다시 검사한다. 이미 시작된 네트워크 write의 회수·분산 인스턴스 즉시 폐기·운영 DB 동시 변경의 물리 일관성을 입증한 것은 아니다.
- 새 의존성은 승인된 `spring-boot-starter-security`, `spring-security-test`, JJWT api/impl/jackson0.11.5뿐이다. 사용하지 않는 security-messaging 라이브러리는 추가하지 않았다. 모든 guard는 명시 principal을 받고 메시징 thread-local SecurityContext를 생성하지 않는다. 실제 runtime report에서 Boot3.2.4, Framework6.1.5, Security6.2.3/JJWT0.11.5를 확인했다. 신규 DB schema·라이브러리 업그레이드·backend 설정 변경은 없다.
- `chat.allowed-origin-patterns`로 배포 origin을 주입할 수 있다. 기본값은 기존 `*`를 보존하며 운영 allowlist 값은 검증·공급 전이다. `jwt.secret.key`를 제공하지 않으면 서버가 시작하지 않는 구성이고 실제 운영 비밀은 읽거나 복사하지 않았다. chat `.gitignore`가 `/src/test/` 전체를 제외했으므로 RF022 `security/*.java`만 좁게 추적 허용했다. 기존 ignored `ChatApplicationTests`는 범위에 포함하지 않았다.

## 2026-11-10 서버·프런트 최종 통합 및 독립 리뷰 완료

**완료 판정은 승인된 최소 구현·합성 격리 검증·독립 리뷰 범위에 한정한다.** 서버28건/assemble, 프런트 전용42건·관련 기존 묶음91건/lint/tsc가 통과했다. 42건은91건에 포함되고 handler 추가12건은 서버28건의 부분 재실행이므로 별도 신규 검증 건수로 합산하지 않는다. 실서비스·DB·wire/브라우저·운영 배포 보안·성능 완료를 뜻하지 않는다. 이 절이 앞선 “프런트/독립 검토 대기” 이력보다 우선한다.

### 프런트 최종 구현과 소유 범위

- `chatAuth.ts`/`chatConnection.ts`와 공개 Chatting·PrivateChatting·알림의 세 실제 호출부가 연결 직전 최신 **sessionStorage** access를 읽는다. 기존 JSON.stringify된 Bearer 또는 기존 raw 저장 형태를 읽으며 Bearer를 중복하지 않는다. 공개 익명은 Authorization 자체를 생략하고 비공개·알림은 자격증명을 요구한다. effect 안에서 client를 만들고 그 client를 cleanup하며 user/destination 전환·logout·늦은 callback·이전 identity를 차단한다. 일반 네트워크 재연결은 최신 토큰을 읽고 ERROR는 재시도를 중단하며 익명으로 강등하지 않는다. debug frame 출력을 끄고 오류/비정상 body를 메시지·알림으로 취급하지 않는다. 정상 `.body` envelope와 서버 echo를 유지한다.
- `UserContext` login/logout과 기존 `setAccessToken(response)`는 같은 창의 연결을 갱신하고 logout은 sessionStorage user/accessToken을 지운다. 지원 환경에서 BroadcastChannel은 다른 팝업의 복사된 세션을 무효화하는 `{type:invalidate}` 신호만 전송한다. **JWT·사용자 profile·채팅내용을 다른 창으로 보내지 않는다.** 지원되지 않거나 차단된 환경의 다른 팝업 즉시 정리는 보장하지 않으며 서버 exp까지 남을 수 있다. 같은 창의 cleanup은 유지된다. 기존 roleToken cookie/서버 logout·폐기 전체 정책을 이번 범위에서 해결한 것은 아니다.
- 채팅 메시지/방 목록 GET과 방 find/create는 HTTP 실패를 정상 데이터로 파싱하지 않고 오류 UI를 표시한다. 정상 find404=-1과 유효 양수 room ID 계약을 보존한다. Notification 미지원·권한 실패는 STOMP 인증과 분리한다. UI의 성공 표시·알림 차단은 DB 영속 저장 보장/ACK/재전송·파일 업로드 완성을 입증하지 않는다.
- **공유 파일 소유권**: `chat/_api.ts`의 RF022 변경은 메시지/방 목록 GET의 non-ok 거부이며 `chat/[roomId]/PrivateChat.tsx`의 RF022 변경은 hook error 소비·표시다. 같은 파일의 거래 요청 create/update 실패 처리 및 모달 async/await·성공 후 종료 등 거래 요청 변경은 **RF021 소유**다. RF022 담당이 충돌 방지를 위해 대신 적용한 hunk라도 RF022 기능·신규 검증으로 귀속하지 않는다. RF021 신규 전용 테스트도 아래91건 집계에 포함하지 않았다.

chat에는 refresh endpoint를 추가하지 않았다. 만료로 닫힌 뒤 최신 토큰 재CONNECT가 필요하며 잘못된 credential의 ERROR에서는 재시도를 멈춘다. 이후 **기존 backend 보호 HTTP 요청**의 기존 재발급 헤더 소비 또는 재로그인으로 access가 바뀌면 연결을 다시 시작한다. 임의 업무 GET을 refresh 목적으로 새로 호출하지 않는다. 다른 backend 요청 없이 access가 만료되면 UI는 로그인/권한 상태를 확인하도록 안내한다. 실제 브라우저의 만료→닫힘→재발급·재연결은 미검증이다.

### 공유 증빙·잔여 상태

[증빙 README](../evidence/RF-022/README.md)와 [ARTIFACT_SHA256.tsv](../evidence/RF-022/ARTIFACT_SHA256.tsv)는33개 공유 artifact의 원본 SHA256·공유본 SHA256·변환·원본 보존 여부를 구분한다. home 경로는 `<USER_HOME>`, XML hostname은 `REDACTED_HOST`로 치환했고 XML 파싱과 공유본 hash를 확인했다. 프런트 원본은 공유본 밖의 로컬 `.tmp/rf022-frontend`에 남아 있으며 일부 서버 redacted artifact는 치환 전 bytes를 별도 보존하지 않아 원본 hash만 남는다. 치환하지 않은 artifact는 bytes가 동일하다. compact JWT/email/home 경로 패턴 재검색과 선택 source/console 검토에서 실제 토큰·개인정보를 발견하지 않았으며 운영 비밀은 수집하지 않았다. fixture literal과 검증 재현에 필요한 합성 source는 실제 사용자 데이터가 아니다. 패턴 점검은 저장소 전체 비밀 감사가 아니다.
