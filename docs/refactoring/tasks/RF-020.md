## 목표와 근거

경로 약어 B=`NGNG-backend/src/main/java/com/ngng/api`, F=`NGNG-frontend/src`.

1. `B/user/user/controller/ConfirmController.accountConfirm`: `PUT /confirm/account`, body `userId/accountBank/accountNumber`, 필수 `refreshToken` 쿠키, servlet response를 service에 전달한다. service 실패 DTO는 400 빈 body, 성공은 204 빈 body다. DTO의 accessToken을 JSON으로 반환하지 않는다.
2. `B/global/security/config/SecurityConfig`는 정확한 `/confirm/account`에 `UNCONFIRMED_USER`만 허용한다. USER/ADMIN 타인 관리 우회는 현재 없다. `TokenFilter.shouldNotFilter`는 이 경로를 제외하지 않으며 access 유효성 검사 또는 refresh fallback을 수행한다. 따라서 무인증 공개 취약점으로 기술하지 않는다.
3. `B/user/user/service/ConfirmService.accountConfirm`은 body userId로 대상을 조회하고 계좌 기등록 또는 계좌번호 중복이면 fail한다. 그 외 `User.accountConfirm`으로 bank/number/role(USER)을 변경하고 대상 `CustomUserDetails`로 access/refresh 토큰을 만든다. caller와 target 비교가 없다. JPA dirty checking을 전제로 한 `@Transactional`이며 명시 save는 없다.
4. `CustomHttpServletResponseWrapper.setHeader`는 원래 response에 그대로 위임한다. 성공 access는 `Authorization: Bearer ...`, refresh는 `Set-Cookie`(path=/, domain=localhost, HttpOnly, Secure)로 전달된다. `JwtTokenProvider`의 subject는 대상 email, claim은 대상 role/type이다. refresh 기존 토큰 삭제 코드는 주석이고 service는 전달받은 쿠키 값을 사용하지 않는다.
5. `TokenFilter` principal은 email/role만 가진 User이며 ID는 없다. `AuthService.readAuthUser`가 검증된 email로 `UserRepository.findUserByEmail`을 수행한다. AuthService 자체는 인증 null/type 방어가 없으므로 호출 전 검사가 필요하다.
6. F `ConfirmAccount` → `useMypageSWR.updateAccount` → `my_page/_api/api.ts:updateUserAccount`는 sessionStorage user.id를 body userId로 보낸다. `/api/confirm/account`는 `next.config.mjs` fallback rewrite로 backend에 전달된다. `setAccessToken`은 응답 Authorization을 sessionStorage 및 roleToken 쿠키에 저장하고 성공 때 Done으로 모달을 닫는다. 헤더 저장은 res.ok 검사 전이다. 실제 proxy 전달/브라우저 refresh 쿠키 수락은 미검증이다.

확인 사실은 위 소스 분기와 호출이다. 타인 미등록 계좌 대상·미중복 번호·유효 UNCONFIRMED_USER·요구 쿠키가 갖춰지면 타인 상태 및 대상 토큰 발급까지 도달할 수 있다는 것은 정적 추론이며 실제 chain 재현·운영 악용/피해는 확인하지 않았다. 유효 access가 있으면 필터가 refresh 쿠키 내용을 검사하지 않지만 MVC에는 해당 쿠키가 있어야 한다.

[OWASP API1:2023 BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)를 2026-11-10 조회했다. 요청 ID로 객체를 다루는 모든 함수에서 인증 주체의 해당 작업 권한을 검사하고 인가 회귀 테스트를 작성하라는 권고를 적용한다. OWASP가 NGNG 역할 정책을 정하는 것은 아니다. 여기서는 기존 UNCONFIRMED_USER 역할 제한과 본인 계좌 등록 UI에 근거해 **유효 UNCONFIRMED_USER가 자기 사용자 행만 계좌 확인 가능**을 최소 정책으로 선택한다. 단순 ID 비교가 모든 객체 인가의 일반 해법이라는 뜻은 아니며 이 객체 자체가 사용자 계좌라는 좁은 범위에 적용한다.

- 유지: endpoint/body 필드, 필수 refresh 쿠키, 본인 정상 204 빈 body와 두 인증 헤더, 기등록/중복 400, USER/ADMIN 역할403, 미인증401, 기존 계좌 저장/USER 승격/트랜잭션. 새 불일치·주체 해석 불가에는 403 빈 body를 의도한다.
- 제외: 주소 RF-041, 탈퇴 RF-042, PII 로그 RF-033, 토큰 폐기/DB role 최신화 RF-040, 은행 실소유 인증, 계좌 형식 정책, 중복 계좌 동시성/스키마, CORS/CSRF/쿠키 배포 정책, 글로벌 AuthService 개편, frontend UI 개편, 성능. 본 계획은 잔여 작업의 자동 착수를 승인하지 않는다.
- 신규 의존성·DB 스키마·관리자 대리 등록·광범위 역할/토큰 정책은 필요 시 별도 승인 대상. 현재 최소 본인 제한은 공식 권고 적용 위임과 기존 UI/역할 증거에 근거하며 별도 승인 대기 항목이 아니다.

## 접근 및 위험

1. 변경 전 합성 JWT 및 두 사용자 fixture로 본인 성공·타인 성공 후보와 역할/쿠키 거부 경계를 재현하고 before 소스/XML/로그를 보존한다. 현 단계에서는 실행하지 않는다.
2. service 진입 시 authentication 존재/authenticated/non-anonymous, CustomUserDetails 및 내부 user/nonblank email을 확인하고 ROLE_UNCONFIRMED_USER를 요구한다. 그 뒤 AuthService로 실제 caller를 해석한다. caller와 caller ID/body userId가 non-null이고 ID 값이 같아야 진행한다. null/null은 허용하지 않고 boxed Long 참조 비교를 사용하지 않는다. 새 정책 엔진이나 전역 인증 변경은 하지 않는다.
3. 검사 실패는 기존 RF-007의 좁은 `ResponseStatusException(HttpStatus.FORBIDDEN)` 방식 등으로 403을 연결한다. 검사 통과 후 기존 대상 조회·계좌 중복 검사·승격·토큰 발급 순서를 유지한다. 타인 ID, 존재하지 않는 타인 ID, null ID는 대상 조회 전에 거부하여 대상 존재·계좌 여부를 노출하지 않는다. DB caller 부재도 403이다. 정상 일치 ID의 조회 실패/DB 장애는 광범위 catch로 삼키지 않는다.
4. 직접 service 호출 방어도 확보한다. JWT가 ID 없는 principal을 만드는 사실을 무시해 principal.userId와 body를 바로 비교하는 방식, UI 검사만 하는 방식, 관리자 우회 추가는 채택하지 않는다.
5. 거부 시 caller/target 계좌·역할 무변경, 대상 조회/중복·role 조회 및 계좌용 토큰 발급 미도달을 확인한다. **refresh fallback은 service 이전 필터에서 호출자 access를 발급할 수 있다.** 따라서 fallback 거부 응답의 Authorization은 기존 호출자/기존 role로 허용하되 대상 토큰·새 refresh Set-Cookie는 없어야 한다. 유효 access로 거부한 경우 새 Authorization도 없어야 한다.

현재 frontend는 403을 throw하지 않아 SWR populateCache가 제출 계좌를 일시 반영할 가능성이 있다. revalidate 결과와 실제 UI는 미검증이며 본인 정상 흐름 유지와 서버 무쓰기 보호를 우선한다. 실패 UI 개선은 근거/범위 합의 후 별도 추적하며 이 문서만으로 변경하지 않는다. 이메일 유일성/동시 변경, stale role, 동시 계좌 등록, 커밋 실패 시 이미 설정된 헤더는 기존 구조 위험으로 남기고 전체 해결을 주장하지 않는다.

## 2026-11-10 승인된 1A 구현·격리 검증 결과

후속 사용자 1A 실행 지시로 앞선 분석 전용 제한을 갱신했다. 기존 본인 계좌 등록·UNCONFIRMED_USER 역할 경계를 유지하며 타인 대상 거부만 좁게 추가했다. 독립 계획 리뷰에서 `CustomUserDetails.getAuthorities()`의 내부 role NPE 가능성을 확인하여 내부 user/email을 먼저 검사하고 `Authentication.getAuthorities()`를 사용했다. caller DB role 재검증, 주소 guard 공통화는 범위 밖이다.

- before 실제 chain14건에서 본인뿐 아니라 타인 요청도204 및 그 대상 subject/USER의 access·refresh 발급을 재현했다. 역할4·필수 쿠키1·인증 실패5·본인400 두 경계도 확인했다. 네트워크/실DB 없이 합성 fixture·실제 SecurityConfig/TokenFilter/JWT/controller/service와 repository 대역을 사용했다. 당시 소스/XML/console을 보존했다.
